## 概要

`features/student/InterviewDetail` の `index.tsx` から、手書きのローディング(`CircularProgress`)と、再試行のないエラー表示(`ErrorState` に `onRetry` なし)を取り除き、`AsyncBoundary` に置き換える。取得処理は `useApiQuery` に載せず、既存の `useInterviewDetail` を残して `data` / `error` / `refetch` を返す形に整える。

TSK-215 で範囲外にした画面の1つ。`useApiQuery` を拡張せずに済む最小の形を取る。

## 背景(調査結果)

- 取得は「面談の詳細」と「メッセージの全ページ」を `Promise.all` で行う(メッセージは古い順にページングされるため、残りのページもまとめて取る)。単一 URL の取得を前提にする `useApiQuery` では表せない。
- 送信・キャンセルの成功後、および 409 / 422 の失敗後に、`fetchDetail` で面談とメッセージを取り直す。つまり、フックにはすでに「取り直し」の関数がある。
- 現状の `index.tsx` は `loading` なら `CircularProgress`(`100vh`)、`!interview || error` なら `ErrorState`(`onRetry` なし)。**取得に失敗すると、再試行できず、再読込するしかない。**
- **409 / 422 のあとの取り直しは、すでに実装されている**(`sendMessage` / `cancel` が `isStaleInterviewError` のとき `fetchDetail` を呼ぶ。テストもある)。TSK-215 の草案が InterviewDetail の別チケットの利点に挙げた「422 後に古い状態が残る問題を直せる」は、コード上すでに解消済みで、**このチケットの価値ではない**(TSK-215 の文言は直す)。
- したがって、このチケットが生徒にもたらすのは**取得失敗時の再試行と、401 でログイン画面に遷移するあいだのエラー表示の一瞬の出現の解消**(現行は `finally` で `loading` が `false` になり、`interview` が `null` のままなので、リダイレクト前に `ErrorState` が出る)の2つである。開発側には、`index.tsx` の直書きの除去(TSK-216 の許可リストの削減)がある。
- `loading` の初期値は `true` なので、`index.tsx` の初回描画でエラーが一瞬出ることはない(TSK-215 の対象画面の多くとは違う)。
- `index.test.tsx` は無い。フックのテスト(`useInterviewDetail.test.ts`)は、取得・送信・キャンセル・409/422 の取り直しを細かく見ている。

## 設計

- `useInterviewDetail` を整える:
  - 内部の `loading` を削除する(`AsyncBoundary` は「`data` も `error` もない状態」をローディングとみなすため)。
  - `interview`・`messages`・`error` に加えて、**`refetch`** を返す。`refetch` は、`fetchDetail` をそのまま渡さず、次の薄いラッパーにする。
    1. `setError(false)`、`setInterview(null)`、`setMessages([])` で、**表示を初期状態(スピナー)に戻す。**
    2. `fetchDetail` を呼ぶ。
    - **再試行中は、初回の失敗でも、送信・キャンセルのあとの取り直しの失敗でも、必ずスピナーに戻る。再び失敗すれば、またエラー表示に戻る。** 理由: 送信・キャンセルのあとの取り直しの失敗で再試行したとき、最後に取得できた(更新前の)内容を出すと、送った本文が載っていないスレッドや、キャンセル前の面談(キャンセルボタンつき)が、更新済みのように見えて、生徒が「送信できなかった」と思って再送したり、キャンセル済みの面談をもう一度キャンセルしようとしたりするため。エラー表示になった時点で `Presenter` はすでにアンマウントされているので、スピナーに戻しても追加の損は無い。
    - **重複呼び出しの抑止は `refetch` にだけ置く。** `refetch` の中で、`useRef` の「再試行中」が立っていれば何もしない。立っていなければ、立てて、`setError(false)`・`setInterview(null)`・`setMessages([])` を行い、`try { await fetchDetail() } finally { 再試行中を下ろす }` とする。**解除は `refetch` の中の `finally` だけで行い、`fetchDetail` には ref を持ち込まない**(`fetchDetail` は例外を内部で握るので、401 のリダイレクトで `return` する場合も、`refetch` 側の `finally` に必ず届く)。表示を初期状態に戻す処理は、guard を通った1回目だけが行う(2回目以降は何もしない)。`fetchDetail` 自体には guard を入れない(送信・キャンセルの成功後の取り直しが、取得中に呼ばれて黙って捨てられるのを避けるため)。`sendMessage` など既存の呼び出し経路には触れない。
  - 401 のリダイレクト、送信・キャンセル、409 / 422 の取り直しは**変更しない**。
- `index.tsx` は、`AsyncBoundary` の `data` に `interview` を渡し、子の中で `messages` といっしょに `Presenter` を描画する。`onRetry` に `refetch` を渡す。`ErrorState` の import と `CircularProgress` の import は不要になる。
- `useApiQuery` と `AsyncBoundary` は**変更しない**。
- **利用者に見える変化**:
  - 取得に失敗したとき、再試行ボタンが出る(**これが主な機能面のメリット**)。
  - 401 でログイン画面に遷移するあいだ、現行は一瞬エラー表示(`ErrorState`)が出る(`finally` で `loading` が `false` になり、`interview` が `null` のままだから)。変更後は、スピナーのままで遷移する。
  - ローディングが、画面中央(`100vh`)から共通のスピナー(`minHeight: 240`)に変わる。
  - 送信・キャンセル後の取り直しに失敗したときは、現行どおり画面全体のエラー表示になり、再試行ボタンが付く。再試行を押すとスピナーに戻り、成功すれば最新の面談とメッセージが出る。

## 比較した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| A: `useApiQuery` に任意の取得関数を渡せる拡張を入れて、InterviewDetail を載せる | 不採用 | 共通部品の拡張と画面の移行が1つのチケットに混ざる。今回の目的(再試行と直書きの除去)には過剰。**見直す条件**: 同じように複数の取得を合成する画面が、ほかにも出てきたとき(そのとき拡張を別チケットにして、乗せ替える)。今は、この1画面だけなので起票しない。`useInterviewDetail` は `useApiQuery` を使わない例外として残る |
| B: 面談だけ `useApiQuery`、メッセージは別フックのまま | 不採用 | 2つの取得状態を合成することになり、送信・キャンセル後の取り直しと 409 / 422 の扱いが複雑になる |
| C: 何もしない(TSK-216 の許可リストに載せたままにする) | 不採用 | 取得に失敗しても再試行できないまま残る。許可リストの例外も1件残る。ただし、**やらなくても致命的ではない**(利用者の損は、まれな取得失敗のたびの手動再読込だけ) |
| D: 取り直しの失敗を、画面全体ではなくメッセージ欄のエラーに留める | 不採用(別件) | 現行の挙動を変える。送信は成功したのに画面全体がエラーになる点の改善だが、このチケットの範囲を超える。必要なら別チケットにする |
| F: 再試行の間、最後に取得できた内容の `Presenter` を出す | 不採用 | 取り直しの失敗のあとで再試行すると、送った本文が載っていないスレッドやキャンセル前の面談が更新済みのように見え、再送・再キャンセルを誘う。初回の失敗と同じスピナーに戻すほうが、表示の分岐も減る |
| E: `fetchDetail` をそのまま `onRetry` に渡す | 不採用 | 失敗状態で押しても、成功するまで画面が変わらない(押しても何も起きないように見える)。連打すると取得が並列に走る |

## やること

### Red(現行で失敗する。実装前にテストだけを書いて落ちるのを確認してからコミットする)

`index.test.tsx` を新設し、`apiClient` をモックして通しで確かめる(`mockResolvedValueOnce` の消化漏れを避けるため、`beforeEach` で `mockReset` する)。連打だけは、フックのテストで確かめる。
- 「再試行直後にスピナー」を確かめるテストは、再試行の `get` の戻りを**手動で解決できる promise**にして、`progressbar` を確認してから解決する(解決を待つと、スピナーを見逃して偽陽性になる)。
- 「取り直しだけ失敗」の準備(初回の取得 → POST 成功 → 取り直しの GET 失敗 → 再試行の GET)は、`mockResolvedValueOnce` / `mockRejectedValueOnce` の並びではなく、**URL と呼び出し回数で分岐する `mockImplementation`** で作る(消化漏れや順序のずれを避けるため。TSK-212 の教訓)。

- [ ] 取得に失敗すると再試行ボタンが出て、押すと再取得し、成功すると復帰する(現行は再試行ボタンが無い)
- [ ] 再試行を押した直後に、エラー表示が消えてスピナーが出る(`refetch` が先に表示を初期状態に戻す)
- [ ] 送信(またはキャンセル)は成功したが、そのあとの取り直しが失敗してエラー表示になったあと、再試行を押すと、更新前の内容ではなくスピナーが出て、成功すると最新の内容が出る。再び失敗すればエラー表示に戻る
- [ ] 再試行を連打しても、取得が並列に走らない(フックのテスト。`act` の中で、1回目の完了前に `refetch` を2回呼び、取得が1回だけ呼ばれることを確かめる)
- [ ] **401 のとき、`/login` に遷移し、エラー表示(`alert`)が出ない**(現行は、`finally` で `loading` が `false` になり `interview` が `null` のままなので、リダイレクト前に `ErrorState` が一瞬出る。変更後はスピナーのまま。**現行で失敗するので Red**)
