# 第1周の対応(InterviewDetail)

第1周の判定: **直せば進めてよい**

| 指摘 | 重大度 | 対応 | 理由・草案のどこを直したか |
| --- | --- | --- | --- |
| 1. `fetchDetail` は成功時にしか `setError(false)` しないので、そのまま `onRetry` に渡すと、押しても画面が変わらない。連打で並列に走る | 重要 | 採用 | コードで確認した(`useInterviewDetail.ts` の `try` の末尾でだけ `setError(false)`)。案 E として比較表に追加して退けた。`refetch` は「先に `setError(false)` してから取得する薄いラッパー」にし、取得中の重複呼び出しは無視する。再試行中の表示(初回失敗はスピナー、取り直し失敗は最後に取得できた内容の `Presenter`、再び失敗すればエラー表示)を設計に書き、Red のテストにした |
| 2. TSK-215 が挙げた「422 後に古い状態が残る問題を直せる」が消えて、価値が「再試行だけ」に下がっている | 重要 | 採用(事実の整理つき) | コードを確認すると、409 / 422 のあとの取り直しは**すでに実装済み**(`sendMessage` / `cancel` が `fetchDetail` を呼ぶ。テストもある)。つまり TSK-215 の文言のほうが古く、このチケットの価値ではない。背景に「価値は再試行だけ」と正直に書き、TSK-215 の文言を直すことを「やること」に入れた(オーナーの承認が要る)。「やらない」場合は致命的でないことも比較表の案 C に書いた。チケットにする価値があるかは、オーナーに聞く |
| 3. Red と回帰防止の区別が「初回描画」だけにしか書かれていない | 重要 | 採用 | 「やること」を「Red」と「回帰防止」に分けた。`ErrorState` は `Alert`(`role="alert"`)を出すので、失敗で `alert` が出るのは現行でも通る回帰防止。Red は、再試行ボタン、再試行で復帰、再試行直後の表示、連打の抑止、フックが `refetch` を返す、の5つ |
| 4. 取り直しの失敗で二重送信を誘う恐れ。スピナーの高さの変化 | 軽微 | 採用 | 二重送信は推測として未検証表に書き、バックエンド側の別件として確認する。スピナーの高さの変化は完了条件の PR 説明に書く。取り直しの失敗を画面全体のエラーにしない案は、案 D として別件に残した |
| 5. 実画面の確認が完了条件に無い。許可リストの項目は TSK-216 が未実装だと測れない | 軽微 | 採用 | 完了条件に実画面の確認(オーナーの了承が前提。無ければ「未検証」と明記)を足した。許可リストは「TSK-216 が未マージなら、外す旨を TSK-216 側にコメントする」に直した |
| 6. 案 A を退ける理由が「過剰」だけで、拡張をいつ入れるかが無い | 軽微 | 一部採用 | 「見直す条件」を書いた(同じように複数の取得を合成する画面が、ほかにも出てきたとき)。今は1画面だけなので、拡張のチケットは起票しない。`useInterviewDetail` が `useApiQuery` を使わない例外として残ることも明記した |
