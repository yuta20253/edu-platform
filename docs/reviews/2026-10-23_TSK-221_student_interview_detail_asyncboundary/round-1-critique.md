# 批判：student/InterviewDetail の AsyncBoundary 移行（第1周）

## 総評
「拡張せず最小で載せる」という方針は筋が通っています。ただ、**生徒へのメリットが「失敗時の再試行ボタン」だけ**です。しかも、その再試行は押しても何も起きないように見える設計になっています。TSK-215 が約束した「422 後に古い状態が残る問題を直せる」は、案 D で別件に回されて消えています。

## 判定
**直せば進めてよい**。やる価値は小さいがあります。理由は後述します。ただし、再試行の挙動と、メリットの書き方を直す必要があります。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒） | 面談詳細の取得に失敗したとき、再読込せずに再試行できる | ローディングが `100vh` 中央から `minHeight:240` に変わる（草案に記載あり）。取り直し失敗時は、送信は成功しているのに画面全体がエラーになる点が現行のまま残る（草案に記載あり） |
| 開発チーム | `index.tsx` から直書きが消える。TSK-216 の許可リストから 1 件外れる。フック内の `loading` が不要になる | `useApiQuery` を使わない「例外」が 1 つ残る（`useInterviewDetail` は 401 処理・中断・再取得を自前で持つ）。Go 移行には無関係 |

- 両方にメリットがあるか：**利用者に損がない内部整理に、小さな実益（再試行）が付く形**です。草案はこれを「再試行と直書きの除去」と書いています。ただし再試行が実際に効く設計になっているかは、指摘1で疑問です。
- やらないことのデメリット：
  - 利用者が失うもの：取得失敗のたびに手動で再読込が必要になる。ただし、面談詳細の取得失敗は頻度が低いと推測します（未検証）。
  - 開発チームが失うもの：TSK-216 の許可リストに例外が 1 件残る。ただしチケットが消化されれば外れるので、恒久化はしません。**「やらない」を選んでも致命傷はありません。つまり、やる価値は限定的です。**
- 草案に無いメリット・デメリット：
  - 【草案に無い】TSK-215 の草案は、InterviewDetail の別チケットの利点を「取得失敗と、422 後に古い状態が残る問題を直せる」と書いていました（`TSK-215/draft.md` 120行）。今回の草案は後者を案 D で外しています。そのため、TSK-215 の約束より価値が下がっています。この差分を明記してください。
  - 【草案に無い】取り直し失敗で `Presenter` がアンマウントされます。`Presenter` は `cancelOpen`・`detailOpen`・メニューなどの state を持っています（`Presenter.tsx` 79〜82行）。再試行に成功して戻ると、開閉状態がリセットされます。入力途中のメッセージ本文が消える可能性もありますが、推測です（`components` 配下を未確認）。

## 確かめた事実
- `index.tsx`・`useInterviewDetail.ts`・`AsyncBoundary.tsx`・`useApiQuery.ts` を読みました。草案の記述とは一致しています（`loading` の初期値 `true`、`ErrorState` に `onRetry` なし、`AsyncBoundary` はエラーを先に判定する）。
- **食い違い**：`fetchDetail` は開始時に `setError(false)` を呼びません。`useApiQuery` は呼んでいます。成功時にだけ `setError(false)` を呼びます。
- `useApiQuery` の `refetch` は state の変更で動きます。一方、`fetchDetail` は async 関数で、`Promise<void>` を返します。`onRetry?: () => void` に渡すのは型の上では問題ありません。
- `useInterviewDetail.test.ts` は 49 行と 117 行で `loading` に依存しています。草案の「フックのテストを更新する」と一致します。
- `index.test.tsx` は存在しません。

## 残すべき強み
- 案 A（拡張）と案 B を、理由つきで退けています。共通部品の拡張と画面移行を混ぜない方針は、TSK-213 の教訓と一致しています。
- 「未検証の前提」を表にして、確かめ方を添えています。
- 送信・キャンセル・409/422 のロジックを触らない、と範囲を絞っています。
- 初回描画のテストを「現行でも通る回帰防止」と正直に書いています。

## 指摘

### 指摘1【重要】（観点：事実か推測か／利用者のメリット）
- 何が問題か：**再試行を押しても、成功するまで画面が変わりません。**
  - `fetchDetail` が `error` を落とすのは成功時だけです。失敗状態でボタンを押すと、`ErrorState` が出たまま、通信中の表示が何もありません。
  - 連打すると `fetchDetail` が並列に走ります。`useApiQuery` にある中断（`AbortController`）もありません。
  - これが唯一のメリットなので、ここが弱いと価値が成り立ちません。
- 根拠：`useInterviewDetail.ts` の `fetchDetail`（`catch` では `setError(true)`、`try` の末尾でだけ `setError(false)`）。
- 直し方の提案：
  - `refetch` は `setError(false)` してから `fetchDetail` を呼ぶ薄いラッパーにします。
  - 初回失敗時は `interview` が `null` なのでスピナーに戻ります。取り直し失敗後は `interview` が残っているので、一瞬 `Presenter` が出ます。
  - 後者は「古い状態が一瞬見える」ので、許容できるかを明記してください。許容できないなら、`refetch` 専用の `retrying` 状態を使わず、失敗時は `interview` を `null` に戻す案もあります。
  - どちらかを選び、テストで固定してください。
  - 並列実行の対策として、最低限、取得中の重複呼び出しを無視する方針を決めてください。

### 指摘2【重要】（観点：利用者のメリット／スコープ）
- 何が問題か：チケットの価値が、TSK-215 の説明から目減りしています。
  - TSK-215 は「422 後に古い状態が残る問題を直せる」を InterviewDetail 別チケットの価値にしていました。
  - 草案はこれを案 D「不採用（別件）」にしました。
  - これでは「再試行だけ」です。それでもやる価値はありますが、**オーナーが納得して決めるべきです。**
- 直し方の提案：
  - 「生徒にとって何が良くなるか」を、再試行だけだと正直に書き直します。
  - 422 後に古い状態が残る件は、別チケットとして Notion に起票済みか、起票予定かを草案に書いてください。TSK-215 の「各別チケットに生徒のメリットを1行書く」の記述も、更新が必要です。
  - 「やらない」選択（許可リストに残す）との比較は、軽く済ませています。上の「やらないことのデメリット」を、そのまま書けます。

### 指摘3【重要】（観点：テスト計画）
- 何が問題か：Red になるテストとならないテストの区別が、「初回描画」の 1 項目にしか書かれていません。
  - Red のはず（現行で失敗する）：失敗時の再試行ボタン、再試行で `fetchDetail` が呼ばれて復帰する、`refetch` がフックから返ること。
  - 現行でも通る（回帰防止）：取得中のスピナー（`CircularProgress` は `progressbar`）、成功で表示、401 で `/login`、送信・キャンセル後に `progressbar` が出ない（現行は `loading` を戻さない）。
  - 「失敗で `alert`」は、現行の `ErrorState` にも `role=alert` があれば通ります。`ErrorState` を確認してください。
- 直し方の提案：やることの各項目に Red／回帰を付けます。Red の項目は、先に失敗を確認してから実装に入ってください。
- 補足：指摘1で決めた挙動（再試行中の表示）を Red のテストにしてください。

### 指摘4【軽微】（観点：失敗の想定）
- 何が問題か：「リリース 1 ヶ月後に困るとしたら」を考えると、次の 2 つがあります。
  - 送信は成功したのに取り直しだけ失敗して、画面全体がエラーになります。生徒が「送信できなかった」と思って再送し、同じメッセージを二重に送る可能性があります。推測です。
  - `index.tsx` でスピナーが `100vh` から `minHeight:240` に変わり、モバイルで高さが変わります。
- 直し方の提案：
  - 前者は草案の判断どおり維持して構いません。維持する根拠を「現行どおり」だけにせず、リスクとして書きます。別チケットの起票とセットにします。
  - 後者はスクリーンショット確認を完了条件に入れます。

### 指摘5【軽微】（観点：完了条件）
- 何が問題か：
  - 「実画面で、取り直しだけを失敗させて確かめる」が未検証前提の欄にだけあり、完了条件に入っていません。TSK-217 の教訓は、単体テストで分からないことは実画面で確かめることでした。
  - 「TSK-216 の許可リストから外せる」は、TSK-216 が未実装なら測れません。
- 直し方の提案：
  - 完了条件に、実画面での確認（初回失敗→再試行、送信後の取り直し失敗）を足します。
  - 許可リストの項目は「TSK-216 がマージ済みなら外す。未マージなら TSK-216 側に外す旨をコメントする」と書きます。

### 指摘6【軽微】（観点：共通化の方針）
- 何が問題か：案 A を退ける理由が「過剰」です。TSK-215 では、同じ画面を「`useApiQuery` の拡張を先に検討する」としていました。草案の「拡張が将来入れば乗せ替えられる」は、いつ・どのチケットで入れるのかが書かれていません。このままだと例外が恒久化します。
- 直し方の提案：「`useApiQuery` に取得関数を渡す拡張」を別チケットとして起票するか、Notion 上で TSK-218／TSK-219 などに該当するものがあるか確かめて、草案に書いてください（私は Notion を確認していません）。
