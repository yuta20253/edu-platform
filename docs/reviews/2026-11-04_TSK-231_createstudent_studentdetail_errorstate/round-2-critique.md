## 確かめた事実
- 合成の設計を `useApiQuery.ts` に照らして検証した。結論は「成立する」。
  - 各フックは `data`・`error`・`reloadKey` を独立して持つ。失敗した側だけ `refetch` しても、もう一方の `data` と `error` は変わらない。
  - 再取得の開始時に消えるのは `error` と `errorStatus` だけ。`data` は残る。初回失敗側の `data` は元から `null` なので、再試行中は「error なし、data が null」になり、スピナーに戻る。成功側の `data` は残る。
  - 2 本が同時に失敗した場合は、「error の側だけ」を両方呼ぶので、2 本とも再取得される。
  - 片方が失敗して、もう一方がまだ取得中の場合は、失敗した時点でエラー表示になる。再試行は失敗側だけ呼ばれ、遅れて来た側の結果は state に入るだけで、エラー表示を壊さない。
  - 規約3（再取得中に前回の data を残す）は、`CreateStudent` では実害が無い。エラー表示からしか `refetch` を呼べないためで、草案の記述は正しい。
- `CreateStudent/index.tsx`・`useCurrentTeacher.ts`・`useGradeOptions.ts` は、草案の記述どおり。
  - `useGradeOptions` は初期値 `[]` で、401 以外を握りつぶす。
  - `Presenter` の `gradeOptions` は `GradeOption[]` で、`null` は受けない。`AsyncBoundary` の `children(data)` 経由なら問題ない。
- `grep "表示規約の例外(一時)"` の現状は 4 行。内訳は `CreateStudent/index.tsx` に 3 行（3・21・40 行目）、`StudentDetail/Presenter.tsx` に 1 行（120 行目）。草案どおり。
- `frontend/CLAUDE.md` に `TSK-231` や `CreateStudent` が出る箇所は 3 つ。23 行目、115 行目、130 行目。草案が挙げているのは 23 行目と 130 行目だけで、**115 行目が漏れている**。
- `lint/displayRules.test.ts` の 244 行目に `REASON = "…TSK-231 で移行予定"` があるが、これは lint のテスト用の文字列で、画面のコードには依存しない。壊れない。
- `Teachers/hooks/useGradeOptions.ts` という別のフックが存在する（名前が同じ。`apiClient.get` を使うかは未確認で、推測）。今回の対象外。ただし grep で混同しないように。

## 指摘（重要な順）

### 指摘1【重要】（観点：テスト計画 — 利用者に見える変化にテストが無い）
- 何が問題か：「`/me` が返っても学級一覧が未着なら、フォームを出さずスピナーのまま」は、今回の設計の核になる新しい挙動で、利用者に見える変化にも書いてある。しかし Red にも特性化にも入っていない。この挙動は現行のコードでは逆（フォームが先に出る）なので、**本物の Red にできる**。入れないと、`data` の合成を「`/me` だけ見る」実装に崩しても全テストが緑のままになる。
- 根拠：草案「やること 子項目 1」の手順 1・2 に該当テストが無い。現行の `index.tsx` は `teacherLoading` だけでスピナーを判定する（確認済み）。
- 直し方の提案：手順 2 の Red に次を足す。
  - 「`/me` は成功、学級一覧は未解決のあいだは、フォームを出さずスピナー。学級一覧が解決するとフォームが出る」。
  - 「学級一覧が 401 のとき、エラーを出さず、`/login` に push する。フォームは出ない」。これは現行が空のフォームを出すので、変化が固定される。

### 指摘2【重要】（観点：テスト計画 / 規模 — コミット単位で lint が落ちる）
- 何が問題か：手順 3（`index.tsx` を `AsyncBoundary` に置き換える）と手順 4（`eslint-disable` と未使用 import の除去）が別手順になっている。手順 3 で `loading` 分岐が無くなった時点で、`eslint-disable` は不要になり、`reportUnusedDisableDirectives` で lint が落ちる。使わない `Alert`/`Box`/`CircularProgress` の import も残るので、TypeScript/ESLint の警告も出る。第1周の指摘2 で直した「途中で落ちるコミット」と同じ型の問題が、lint 側で残っている。対応表は「3 と 4 を 1 手順にした」と書いているが、草案には反映されていない。StudentDetail の手順 2 と 3 も同じ構造。
- 根拠：草案 手順 3・4 と、子項目 2 の手順 2・3。CLAUDE.md の「違反を直したら、その行の `eslint-disable` も消す。消さないと `npm run lint` が落ちる」。
- 直し方の提案：`eslint-disable` と import の除去は、置き換えと同じ手順（同じコミット）に入れる。草案から手順 4 と子項目 2 の手順 3 を消して統合する。

### 指摘3【重要】（観点：完了条件が測れるか — 数え方が読み違えやすい）
- 何が問題か：完了条件が「4 行 → CreateStudent の移行で 3 行減って 1 行 → StudentDetail の移行で 1 行減って 3 行 → 両方マージ後は 0 行」と並んでいる。順に読むと、1 行から 1 行減って 3 行になるように読める。実際は「どちらを先にマージしても、先にマージした側の分だけ減る」という意味。測定の基準としては曖昧。
- 根拠：草案「完了条件」5 項目目。
- 直し方の提案：表にする。
  - 現在：4 行。
  - CreateStudent だけマージ後：1 行（StudentDetail の分）。
  - StudentDetail だけマージ後：3 行（CreateStudent の分）。
  - 両方マージ後：0 行。
- PR を 1 本にするなら「0 行」だけでよい。オーナーの問い 2 の答えで、この項目を 1 つに絞る。

### 指摘4【軽微】（観点：規約・ドキュメントとの整合 — CLAUDE.md の更新漏れ）
- 何が問題か：草案の更新対象は 23 行目と 130 行目だけ。次の 3 点が漏れている。
  - **115 行目**：`{/* eslint-disable-next-line … TSK-231 で移行予定 */}`（例: `features/teacher/CreateStudent/index.tsx`）。その `eslint-disable` を外すと、**例として挙げたファイルから例そのものが消える**。同じ節にある `StudentDetail/Presenter.tsx` の例（複数行の開始タグ、三項演算子の中）も同様。両方の例を外すと、置き場所の規則の実例が無くなる。
  - 「データ取得画面の移行は完了していて、手書きの表示が残るのは下の『例外の扱い』の画面だけ」（規約5の直後）。移行後は例外が 0 件で、この文が実態とずれる。
  - 130 行目のフォローアップ表記（TSK-231）を「なし」にしたとき、115 行目の `TSK-231` の例示文字列が残ると、grep しても出てこない過去の番号になる。
- 根拠：`frontend/CLAUDE.md` 23・115・130 行目、および規約5直後の文。`git grep` で確認済み。
- 直し方の提案：次のいずれかを決める。
  - 115 行目の例のファイル名を「過去の例」として削除し、`lint/displayRules.test.ts` の該当テストを実例の代わりに指す。
  - 例の文章は残すが、「例: TSK-231 で外した `CreateStudent/index.tsx`」のように履歴であることを明記する。
- 「手書きの表示が残るのは…」の文は、移行後に「現在は例外なし」の形に直す。

### 指摘5【軽微】（観点：失敗の想定 — 新しい `data` の参照の安定性）
- 何が問題か：合成した `data`（絞り込み後の選択肢）を、レンダリングのたびに `filter` で新しく作ると、`Presenter` の `useEffect` が参照の変化で何度も走る可能性がある。`Presenter` は `useEffect` を使っている（48 行目、依存は未確認で推測）。現行は `useGradeOptions` が `useMemo` を持っている。
- 根拠：`useGradeOptions.ts` は現行で `useMemo`。草案の「戻り値の選択肢は `GradeOption[] | null`」の合成部分に、メモ化の記述が無い。
- 直し方の提案：絞り込みは `useGradeOptions` の中の `useMemo` に残し、`null` もその中で返す（「`useMemo` を残す」と一行書く）。`index.tsx` で組み立てる合成値も `useMemo` にするか、フックの側に寄せる。確認は、特性化テスト（`own_grade` の選択肢）が移行後も緑であること、実画面でフォームの入力が消えないこと。
