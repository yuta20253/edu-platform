# 批判:TSK-231 CreateStudent の AsyncBoundary 移行 / StudentDetail の ErrorState 化(第1周)

## 総評
範囲の切り方、並列取得を保つ判断、特性化テストを先に書く進め方は筋が良い。穴は「2 本の合成の細部」「テスト順のコミット単位」「CLAUDE.md を子項目ごとに触る衝突」「完了条件の数え方」に集中している。致命的なものは無い。

## 判定
直せば進めてよい。利用者に見える改善が 2 つあり、設計の骨格は正しい。直すのは重要 3 件と軽微 3 件。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者(教師) | ・生徒新規作成画面(`/teacher/students/new`)で、教員情報か学級一覧の取得に失敗したとき「再試行」で復帰できる。<br>・学級一覧の失敗で学年が空のフォームが出て、生徒を作れない理由も分からない、という状態が無くなる。<br>・生徒詳細のタブ(目標・タスク)切替後の失敗でも「再試行」できる。 | ・ローディングの見た目が変わる(`height:100%` 中央寄せから `minHeight:240`)。<br>・**草案に無い変化**:現在は `/me` が返れば学級一覧が未着でもフォームが先に出て、選択肢があとから埋まる。移行後は 2 本そろうまでスピナーになる。ほぼ利点だが、利用者に見える変化なので書くこと。 |
| 開発チーム | ・手書きの取得・表示が 2 画面から消え、「一時の例外」が 0 件になる。<br>・401 以外を握りつぶす `useGradeOptions` が消える。<br>・TSK-216 の lint と整合する。 | ・フックのテスト 2 本の書き換え。<br>・CLAUDE.md の更新が子項目ごとに衝突しうる(指摘 3)。 |

- 両方にメリットがあるか:ある。どちらも利用者に見える不具合の修正(規約 4 違反)なので、内部整理ではない。
- やらないことのデメリット:
  - 利用者が失うもの:失敗時に画面を再読み込みするしかない状態が続く。学級一覧の失敗は理由が出ないままになる。
  - 開発チームが失うもの:「一時の例外」が恒久化する。TSK-216 で例外を一時と呼んだ根拠が崩れる。
- 草案に無いメリット・デメリット:上記「利用者のデメリット」の 2 本そろうまでスピナー、が草案に無い。

## 確かめた事実
- `CreateStudent/index.tsx`、`useCurrentTeacher.ts`、`useGradeOptions.ts` の記述はすべて草案どおり。
  - 2 本とも最上位で並列に呼ばれている。
  - `useGradeOptions` は 401 以外を握りつぶす。
  - `index.test.tsx` は無い。
- `useApiQuery` は再取得の開始時に error を消し、data を残す。401 は `router.push("/login")` して return する。
- `StudentDetail/index.tsx` は `refetch` を持ち、`Presenter` に渡していない。`Presenter` の error 分岐は草案のとおり手書きの `Typography`。
- `InterviewDetail/Presenter.tsx` は `<Box sx={{ mx: -3, mt: -3 }}><ErrorState onRetry/></Box>` の形。
- `ErrorState` は `p:3` の `Box` + `Alert`。
- `StudentDetail` の `Presenter` は最外が `p:3` の `Box` で、`Tabs` は `mb:3`。
- `CreateStudent/Presenter.tsx` の `gradeOptions` は `GradeOption[]` で `null` を受けない。
- `CLAUDE.md` の 23 行目と 130 行目に、草案が言う該当記述がある。
- `StudentDetail/index.test.tsx` は `Presenter` をモックしていて、`onRetry` を受け取る形になっていない。

草案との食い違い:
- 「上が詰まるかもしれない」(未検証の前提 1)は、構造を読む限りたぶん外れ。指摘 5 を参照。これは推測で、実画面で確かめる。

## 残すべき強み
- `useGradeOptions` を入れた理由(握りつぶしの発見)を、案 A と比べて問いに出している。
- 並列取得を保つ理由と、内側コンポーネントに移すと直列になるという比較(案 B)。
- 検証済み・未検証の前提表と、見える変化の明記。
- 特性化テスト → Red → 移行の順。これは TSK-224 で当たった進め方。
- 子項目を独立にしたこと。
- 先例(`InterviewDetail`、`SchoolClassRequestDetail`、`CreateSchoolClassRequest`)が実在する。

## 指摘

### 指摘1【重要】(観点:対策の重複 / 失敗の想定 — 2 本の合成)
- 何が問題か:合成の仕様が「つもり」止まりで、次の 3 点が決まっていない。
  1. 再試行で `onRetry` が「両方の `refetch`」だと、成功している側も無駄に再取得し、その間 `data` は残るが、失敗側が戻るまでスピナーになる。失敗した側だけ再取得する案と比べていない。
  2. 401 のとき、どちらの `useApiQuery` も `router.push("/login")` する(二重 push)。`error` は立たず、`data` も null のままなのでスピナーで止まる。これは現行と同じで害は小さいが、**テスト(`/me` が 401)で push の回数まで固定すると、片方だけの 401 を取りこぼす**。
  3. 取得前の `null` と、取得できた空配列 `[]` の区別。草案は `useGradeOptions` の戻り値で区別すると書くが、合成の `data`(選択肢か `null`)の型を書いていない。学級が 0 件の学校では `[]` が正しい値なので、`AsyncBoundary` に渡す `data` を `gradeOptions ?? ...` や `length` で判定すると、永久スピナーになる。
- 根拠:`AsyncBoundary.tsx` は `data === null || undefined` だけを見る。`useGradeOptions.ts` は初期値が `[]` で、「取得前」と「空」を区別していない(確認済み)。
- 直し方の提案:
  - 合成値を「`me.data` と `grades.data` の両方が `null` でなければ `{ gradeOptions: 絞り込み後, ... }`、それ以外は `null`」と型で書く。
  - 再試行は「error になっている側の `refetch` だけ」を推す。両方呼ぶ案は、実装が単純な分、無駄な再取得が増える。どちらにしても理由を書く。
  - 空配列のケース(`school-classes` が `[]` を返す)の特性化テストを 1 本足す。
  - 401 のテストは「少なくとも 1 回 `/login` に push し、エラーが出ない」にとどめる。

### 指摘2【重要】(観点:テスト計画)
- 何が問題か:3 点ある。
  1. 並列の 2 本を `mockResolvedValueOnce` の順で返すと、呼び出し順に依存して壊れやすい。TSK-212 の教訓(モックの漏れ)の再来になりうる。
  2. 手順 3 で本体を移行したあと、手順 4 まで**フックのテストが落ちたまま**になる(`loading` が無くなるため)。コミット単位で緑にしたいなら、フックの書き換えは移行と同じコミットにするしかない。
  3. 特性化テストの「`/me` が 500 のときフォームを出さない」は、現行でも緑になる(これは意図どおり)。だが、**学級一覧が失敗したときの現行の挙動(空の選択肢のフォーム)を固定するテストを書かない**ことを明記すること。バグを特性化すると、Red と混ざる。
- 根拠:`useCurrentTeacher.test.ts` が `result.current.loading` に依存している(確認済み)。`index.test.tsx` が無いので、モックの形はこれから決める。
- 直し方の提案:
  - `apiClient.get` を `mockImplementation((url) => …)` で URL ごとに返す。
  - 手順 3 と 4 を 1 コミット(または 1 手順)にする。
  - 「学級一覧の失敗の現行挙動は特性化しない」と一行書く。

### 指摘3【重要】(観点:スコープと依存 / 完了条件が測れるか — CLAUDE.md と grep)
- 何が問題か:3 点ある。
  1. 子項目を別々にマージすると、`CLAUDE.md` の同じ箇所(130 行目の「現在の一時の例外」)を両方の PR が編集する。後からマージする側は、必ずコンフリクトする。草案の「マージする分だけ直す」は手順になっていない。
  2. 完了条件「移行した画面の分だけ減っている」は、数字が無く測れない。
  3. 子項目 1 と 2 が結局「近い日に 2 本マージ」になるなら、分ける意味が薄い。TSK-216 のレビューで指摘された「性質が違う 2 件」の懸念の答えは、PR を分けることであって、チケット内の子項目では足りない。
- 根拠:`CLAUDE.md` 23 行目と 130 行目、TSK-216 の答え合わせ(最終行、未確定)。`grep -rn "表示規約の例外(一時)" frontend/features` の現在の件数は、`CreateStudent/index.tsx` に 3 行、`StudentDetail/Presenter.tsx` に 1 行の合計 4 行(確認済み)。
- 直し方の提案:
  - 完了条件を「4 行 → `CreateStudent` 移行後 1 行 → 両方で 0 行」と数字で書く。
  - PR を 2 本にするなら、`CLAUDE.md` の 130 行目の更新は「先にマージするほうが `CreateStudent` か `StudentDetail` のどちらか片方の名前に書き換え、後のほうがその行を消す」と順序を決める。1 本の PR にまとめる選択肢も比べて、理由を書く。
  - 23 行目の StudentDetail の注記は、「再試行は未対応」だけを消し、「ヘッダーを残すための例外」という説明は残す(恒久の説明として今も正しい)。

### 指摘4【軽微】(観点:セキュリティ / 事実か推測か — 学年制限の fail-open)
- 何が問題か:草案は「学年制限を不明なまま扱わない」と言うが、`own_grade` で `grade` が `null` の教員は、`restrictedGradeId = null` になり、**全学年が選べる**。これは現行の仕様で、移行しても残る(そのまま受け継ぐ)。ただし、特性化テストの「`own_grade` は自分の学年だけ」にこのケースを入れていないので、固定されるのかどうかが不明のまま。
- 根拠:`useCurrentTeacher.ts` の `scope === "own_grade" ? (grade?.id ?? null) : null`(確認済み)。サーバー側でも弾かれるかは**未確認**。
- 直し方の提案:今回は直さない(スコープ外)。特性化テストに「`own_grade` で `grade` が `null`」を足して現行の挙動を固定するか、フォローアップとして書き残す。サーバー側の認可(`students` 作成時の学年検証)はこのチケットで確かめなくてよいが、「確かめていない」と書くこと。

### 指摘5【軽微】(観点:事実か推測か — 余白と実画面の確認方法)
- 何が問題か:「タブの下では上が詰まるかもしれない」は、構造を読むとたぶん外れ。`Tabs` が `mb:3` を持ち、`ErrorState` の `p:3` の上辺を `mt:-3` で打ち消すので、タブの下は 24px で、`InterviewDetail` の見出し下と同じ間隔になる。左右も `mx:-3` で外側の `p:3` を打ち消し、`Alert` が内容の幅にそろう。**これは推測**で、実画面で確かめる。確認方法の `page.route` で `tab=goals` だけ 500 にする案は現実的(ブラウザ側の `fetch` なので傍受できる。プロフィールの初回は `tab` が付かないので、URL で区別できる)。ただし、BFF の `app/api/teacher/students/[studentId]/route.ts` のステータスが素通しである確認(500 のまま返るか)は書いていない。
- 根拠:`StudentDetail/Presenter.tsx`(最外の `Box p:3`、`Tabs sx mb:3`)、`ErrorState.tsx`。
- 直し方の提案:未検証の前提 1 を「たぶん合う(構造から推測)。実画面で確認」に書き換える。確認には、再試行で成功する経路(`page.route` を 1 回だけ 500 にして、次を通す)も入れる。合わなければ `mt` だけ調整、と決めておく。

### 指摘6【軽微】(観点:テスト計画 — StudentDetail の index テスト)
- 何が問題か:`index.test.tsx` の `Presenter` モックに `onRetry` を足して「同じタブを再取得する」を確かめる計画は、`useStudent.test.ts` に既に同種のテスト(「`refetch` を呼ぶと同じ条件で再取得する」)があるので、重複気味。ただし、**`index.tsx` が `refetch` を `Presenter` に渡す配線**は index のテストでしか守れない。これは Red として正しい(現行は渡していないので落ちる)。
- 直し方の提案:テストの主眼を「配線(`Presenter` に `onRetry` が渡り、押すと `apiClient.get` が同じ `tab` で再度呼ばれる)」と明記する。`useStudent` の再取得そのもののテストは足さない。

## 本人に確認すべき問い
1. 案 A(`useGradeOptions` を対象外にする)ではなく、学級一覧も同じチケットで直す方針でよいか。私は、握りつぶしを残した画面を「移行済み」と呼べないので、採用でよいと考える(判断はオーナー)。
2. PR は 2 本に分けるか、1 本にまとめるか。分けるなら、`CLAUDE.md` の更新順を決めたい(指摘 3)。
3. `own_grade` で `grade` が `null` の教員に全学年を選ばせる現行の挙動は、仕様か、既知の不具合か。今回は直さず、特性化テストで固定するだけでよいか(指摘 4)。
4. 再試行は、失敗した側だけを再取得するか、両方を再取得するか(指摘 1)。
