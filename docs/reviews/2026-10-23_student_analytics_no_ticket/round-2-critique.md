## 確かめた事実

`origin/feature/TSK-206_student_analytics_dashboard` を fetch して確認しました。

- `index.tsx` は、`usePeriodQuery` と3つの取得フックを呼び、`Presenter` に渡すだけです。渡すのは、summary、gradeAverage、understandingScore、rank の4系統の `data` / `error` / 再試行と、rank の絞り込み状態です。`CircularProgress` と固定文言はありません。草案の改訂後の記述は事実どおりです。
- `git grep` に当たるのは、`useFetchAnalyticsSummary.ts` 14 行目のコメント（「loading フラグを持たない」）だけです。草案の「コメント1行のみ」と一致します。
- `AsyncBoundary` の使用は、`Presenter.tsx` の 78 行目と 155 行目、`RankContent.tsx` の 42 行目の3か所です。旧 `useAnalytics.ts` はありません。
- `useFetchAnalyticsSummary` は、`apiClient` の直接呼び出し、中断、401 → `/login`、`reloadKey` を自前で持ちます。422 を理由にしたコメントも草案どおりです。422 のときは `Presenter` 側で `validationErrors.length === 0` のときだけ `AsyncBoundary` を描画します。そのため 422 でスケルトンのまま止まることはありません。
- `useApiQuery` は `enabled` と `keepPreviousData` を持ち、失敗は `error: boolean` だけです。草案の記述と合います。
- 確かめていないもの：`gh pr view` の PR 状態、Notion 上の TSK-219 の仕様。

## 指摘（重要な順）

### 指摘1【重要】（観点：共通化の方針・規約との整合／事実か推測か）

- 何が問題か：改訂で入った「見直す条件」が狭すぎます。条件は「TSK-219（`errorStatus`）がマージされ、422 を扱える形になったとき」です。ところが、このフックを `useApiQuery` に寄せられない理由は 422 だけではありません。
  - `periodKey` で「どの期間の結果か」を持ち、`refreshing` を出しています。`useApiQuery` にはこれがありません。
  - 失敗時に前の期間のデータを `setResult(null)` で消します。`useApiQuery` は失敗時もデータを残します。
  - 422 のときは `error` を立てず、`validationErrors` を別に持ちます。
  - TSK-217 の教訓は、「表せない」ではなく「拡張が必要」でした。今回は「`errorStatus` で足りる」と決め打ちしている恐れがあります。
- 根拠：`useFetchAnalyticsSummary.ts` の `result` / `periodKey` / `refreshing` / `setResult(null)`（コード）。`useApiQuery.ts`（失敗時に `data` を残す）。「`errorStatus` だけでは足りない」は推測です。確かめる方法は、TSK-219 のマージ後に両者を見比べることで、草案の未検証表の4行目がすでに指しています。
- 直し方：見直す条件を「TSK-219 のマージ後に、`errorStatus` に加えて `refreshing` と失敗時のデータの扱いも含めて寄せられるかを見比べて判断する」に直します。未検証表の4行目にも同じ範囲を書きます。

### 指摘2【重要】（観点：完了条件が測れるか／スコープと依存）

- 何が問題か：完了条件の3・4が、他の人の PR とその動作確認に依存しています。やることに、動作確認をする人の項目がありません。
  - 3系統の再試行を誰が、いつ、どの PR（#206 か #199 か）で見るのかが書かれていません。「#199 に一文コメント」までが草案の作業で、結果を確かめる項目がありません。
  - 「Analytics を対象外にして進める」を選んだ場合、条件3・4が永久に満たされません。終わり方がありません。
  - 数え方も揃っていません。背景は「4系統」、動作確認は「3系統（summary・累積・rank）」です。累積には gradeAverage と understandingScore の2枚が独立して再試行します。
- 根拠：draft.md の「やること」「完了条件」。数え方の不一致は同じ文書内の食い違いで、事実です。
- 直し方：
  - やることに「#199 のマージ前に、取得失敗 → 再試行を4つの取得（累積は2枚）で実画面確認する。確認者は〇〇」を足します。確認者はオーナーに聞いてください。
  - 完了条件に「Analytics を対象外にした場合は、条件3・4を『対象外を TSK-216 に記録した』に置き換える」と書きます。
  - 「3系統」と「4系統」のどちらかに統一します。

### 指摘3【軽微】（観点：失敗の想定）

- 何が問題か：`useFetchAnalyticsSummary` の見直しが、チケットでもカンバンでもなく、この文書のチェックボックスにしかありません。1か月後に困るとすれば、TSK-219 がマージされても誰も戻ってこず、例外が恒久化するケースです。第1周の「追跡が消える」と同じ構図が、一段小さく残っています。案 D を退けた判断自体は妥当です。
- 直し方：TSK-219 の本文に「マージ後に summary フックの寄せ直しを判断する」と一行足すことを、オーナーへの確認事項に入れます。草案には「例外一覧に載っていること」を書けば足ります。

### 指摘4【軽微】（観点：移行計画との整合／テスト計画）

- 何が問題か：未検証表の3行目「TSK-216 の走査テスト・ESLint は `useFetchAnalyticsSummary` を問題にしない」は、このフックを機械的に守る仕組みが無いことを意味します。草案はこれを「実装時に確かめる」で済ませています。
