# 批判：student/Analytics の移行チケットを起票しない判断（第1周）

## 総評

結論（別チケットは作らない）は妥当。ただし根拠が「未マージ・ドラフトの PR の現状」に寄りかかっているのに、確認の担当・時期・外れたときの動きが決まっていない。また、起票しないことで「useFetchAnalyticsSummary を共通部品に寄せる」作業の行き先が消える点が書かれていない。

## 判定

**直せば進めてよい**。起票しない判断は正しい。直すのは(1)確認を TSK-216 の着手条件・TSK-206 の動作確認に繋ぐこと、(2) summary フックの寄せ直しの行き先を決めること、(3) 草案の事実誤記と完了条件の測り方。

- 草案に無いメリット・デメリット：上記のとおり。

## 確かめた事実

- #199 は OPEN のドラフト（base は `feature/TSK-206_student_analytics_base`）、#206 は base が main の OPEN。草案どおり。
- 「手書き分岐が無い」は正しい。`Presenter.tsx`（78・155 行付近の2か所）と `RankContent.tsx` が `AsyncBoundary` を使い、`CircularProgress` と「取得に失敗」の直書きは main の `index.tsx` にだけある。#199 側の実装には無い。
- **草案の誤記**：「`index.tsx` は `Presenter` に `data` / `error` / `onRetry` を渡すだけ」と書いてあるが、実際は summary・gradeAverage・understandingScore・rank の4系統に分けた `*Error` / `onXRetry` を大量に渡す構成。判断は変わらないが根拠の文章として不正確。
- `useFetchAnalyticsSummary` は `apiClient` を直接使い、AbortController、401 → `/login`、`reloadKey` による再取得を自前で持つ。`useApiQuery` とほぼ同じ機能の再実装。これは「手書きの分岐」ではなく「手書きの取得フック」なので、草案の grep（`CircularProgress` / 固定文言 / `loading`）では検出できない。
- フック冒頭のコメントが使わない理由を「422 を見分ける必要があるため」としている。README の TSK-219（`errorStatus` の拡張）で解決できる可能性がある。

## 指摘

### 指摘1【重要】（観点：事実か推測か／失敗の想定）

- 何が問題か：根拠が未検証の前提（#199 がこのままマージされる）に全面的に乗っている。外れたときの手当てが無く、「TSK-206 のマージ後に grep」を誰がいつやるかも未定。起票しないとカンバンにも載らない。1か月後に困るなら、「確認し忘れたまま TSK-216 が先に着手され、Analytics が許可リストに入った」か「#199 のレビューで summary 周りの分岐が増えた」。
- 根拠：草案「未検証の前提」「やること」。推測：TSK-216 の着手がマージより先に来る可能性を草案は排除していない。
- 直し方：確認項目を「TSK-216 の着手条件」に書く（TSK-206 がマージ済みであること、または Analytics を対象外にして進めること）。#199 の PR に「TSK-215 の観点を満たしていることをマージ前に確認する」と一文を残す（案 C の軽い形）。

### 指摘2【重要】（観点：代替案の比較／共通化の方針・規約との整合）

- 何が問題か：`useFetchAnalyticsSummary` の `useApiQuery` への寄せ直しが、起票しないことで行き先を失う。草案は「TSK-216 と矛盾しない」とだけ書いて終わっている。TSK-217 で当たった「使わない理由が『表せない』ではなく『拡張が必要』」と同じ構図の可能性がある（TSK-219 の `errorStatus` で 422 を扱えるかもしれない）。
- 根拠：`useFetchAnalyticsSummary.ts` 13〜14 行のコメント。README 答え合わせ TSK-217 の行。
- 直し方：比較表に案 D「summary の寄せ直しだけ、TSK-219 後の別チケットとして残す」を足す。採用しないなら「例外として残す。理由は〜、見直す条件は〜」を一文で残す。採否はオーナー判断。

### 指摘3【重要】（観点：テスト計画／完了条件が測れるか）

- 何が問題か：完了条件が grep の結果だけ。固定文言を別の文言に変えれば通ってしまう。Analytics の「再試行ボタンが出る」「初回に止まらない」の実画面確認も計画に無い（TSK-217 の教訓）。
- 根拠：草案「完了条件」。
- 直し方：完了条件に、TSK-206 の PR の動作確認で summary・累積グラフ・順位の3系統それぞれの取得失敗 → 再試行を見ることを足す。grep は補助と位置づける。

### 指摘4【重要】（観点：スコープと依存の切り方／代替案の比較）

- 何が問題か：案 B を「grep 1回で済む」と退けているが、B の価値は手間ではなく追跡できること。案 C は「要検討」のままで採否が未決。
- 直し方：A + C の併用を採用と明記する。B を捨てる理由は「追跡の必要性は TSK-216 の着手条件で担保する」に書き換える。

### 指摘5【軽微】（観点：事実か推測か）

- 何が問題か：`index.tsx` の説明が実態と違う（確かめた事実の項）。
- 直し方：「4系統の取得結果を `Presenter` に渡すだけで、固定文言と `CircularProgress` は無い」に直す。

### 指摘6【軽微】（観点：移行計画との整合）

- 何が問題か：grep は暫定の確認で、TSK-216 の ESLint・走査テストが入れば（Analytics を許可リストに載せない限り）自動で担保される。人手の確認が残り続けるように読める。
- 直し方：「TSK-216 の ESLint・走査テストが入った後はそちらが担保する。それまでの暫定確認」と位置づけを書き、やることのチェック項目を TSK-216 の成果物に吸収する。
