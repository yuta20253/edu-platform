## 確かめた事実
- `bullet-8.1.3/lib/bullet/rack.rb`：`perform_out_of_channel_notifications`（raise が起きる場所）は、HTML へ差し込むかどうかの条件の外にある。そのため JSON 以外のレスポンスでも raise されます。CSV の `send_data` を返す `import_histories#export` も対象です（ストリーミングではないので、`end_request` の後にクエリが走ることもない）
- `start_request` はレジストリを毎回作り直す（bullet.rb 151〜159 行目）。草案の「request spec は Rack が区切り直す」は正しいです
- `spec/requests/api/v1/teacher/school_class_requests_spec.rb` 125〜154 行目：テーブル名の grep ではなく、基準 1 件と 4 件で**総クエリ数**（`queries.size`）を比べている。バッククォートに依存せず、関連以外の N+1 も拾える
- `dashboards_spec.rb` 54 行目・`interview_request_messages_spec.rb` 41 行目・`import_histories_spec.rb` 172 / 233 行目は、`FROM \`tasks\`` などのテーブル名の grep。草案の動機（SQL 文字列への依存）が当てはまる
- `spec/jobs` と `spec/services` で、クエリ数を検査しているのは `task_progress_service_spec.rb` だけ。ジョブを明示的に守るテストは無い
- `Bullet::ActiveJob` は opt-in（`include` が必要）。今は `ApplicationJob` に入っていない
- `current_user.high_school.grades` 以外で HighSchool から grades を引くのは、`Admin::GradesController`（`school.grades`、1 件）と `Teacher::SchoolClassesController`（1 件）。今のところ HighSchool を複数件並べて grades を引く画面は無い
- 依存は `rails/tmp/ticket_rails_ci_ruby_3_4_12.md`（git の管理外）を指していて、Notion のチケット ID になっていない
- Notion の重複・依存は、ツールが無いため確かめていません

## 残すべき強み
- 「書き換えた後に `includes` を外して落ちることを確かめたものだけ書き換える。落ちなければ残す」という手順。偽陽性の教訓（TSK-211）にきちんと沿っている
- 案 B（フック）と案 B'（消す）を、どちらも根拠つきで不採用にした比較表
- 「Bullet で代われない」テストを型ごとに分けた表
- 検知の範囲（request spec・2 件以上・関連のみ）を、概要と完了条件の両方に明記したこと
- コミットを分け、書き換えたテスト・残したテストを PR 本文の表で示す運用

## 指摘（重要な順）

### 指摘1【重要】（観点：テスト計画／事実か推測か）
- 何が問題か：`teacher/school_class_requests_spec.rb` の「件数によらずクエリ件数が増えない」を「関連の読み込み（要確認）」に分類し、書き換えの候補にしています。しかしこのテストは、テーブル名の grep ではなく総クエリ数の比較で、草案の動機（SQL 文字列への依存で壊れやすい）が当てはまりません。しかも、Bullet が見ない「レコードごとの自前の `where` / `count`」の N+1 も拾います。草案の確かめ方（`includes` を外して Bullet が落ちるか）では「Bullet が関連の分を代われる」ことしか分からず、このテストが余分に守っていた分が消えることには気づけません。
- 根拠：`school_class_requests_spec.rb` 125〜154 行目（`queries.size` を `base_count` と比べている）
- 直し方の提案：書き換えの基準を、「見ているもの」ではなく「テストの型」で決める。
  - テーブル名を grep して件数を見る型（`FROM \`users\`` など）→ 書き換えの候補（今の手順どおり）
  - 総クエリ数を基準と比べる型 → SQL 文字列に依存しないので**残す**。表の「Bullet で代われるか」を「代われない（関連以外の N+1 も見ている）」に変える

  問い 1 をオーナーに聞くときも、この区別を添えてください。

### 指摘2【重要】（観点：失敗の想定）
- 何が問題か：書き換えた後のテストは「3 件あっても全件返す」という見た目になり、「件数が 2 以上であることが N+1 の守りになっている」ことがコードから読めません。1 か月後、誰かが「件数の多い例は冗長だ」と思って `create_list` を 1 件に減らしたり、他の例とまとめたりすると、Bullet は黙って何も見なくなります。これは第 1 周の指摘1と同じ「黙って守りが消える」失敗が、形を変えて残る形です。
- 根拠：草案の設計 4「複数件のデータを作る例そのものが守り」。今のテストは名前とコメント（「N+1 ならメッセージ数に比例して増える」）でこの意図を示しているが、書き換えると数え方と一緒に消える
- 直し方の提案：書き換えの規約を草案に書く。例として、it 名を「複数件でも全件を返す（N+1 は Bullet が検知する）」に揃え、`# Bullet は 2 件以上を読み込んだときだけ N+1 を検知する。件数を 1 にしないこと` のコメントを残す。「やること」の書き換えの項目に 1 行足せば済みます。

### 指摘3【軽微】（観点：失敗の想定／対策の重複）
- 何が問題か：`Bullet.add_safelist class_name: 'HighSchool', association: :grades` は、アプリ全体に効きます。今は HighSchool を複数件並べて grades を引く画面はありません。ただ将来、管理者の高校一覧に学年を出すような画面を作ると、そこで本物の N+1 が出ても検知されません。また、誤検知の原因（なぜ HighSchool が possible object に入るのか）が分からないまま safelist すると、同じ原因で別の関連も誤検知され、safelist が増え続ける恐れがあります。
- 根拠：Bullet の safelist はクラスと関連の組で、全体に効く。`grades_spec.rb` は 1 件の高校で 1 リクエストしかしていない（34 行目）。それでも検知されたので、原因はアプリ側の読み込み（認可・認証の途中など）にあると推測します
- 直し方の提案：やることの順番を「原因を特定する → 原因の読み込みが不要なら直す → 直せない、または直す得が無い場合だけ safelist」と明記する。safelist のコメントには、原因と「HighSchool を複数件並べて grades を引く画面を作るときは外すこと」を書く。

### 指摘4【軽微】（観点：事実か推測か／代替案の比較）
- 何が問題か：概要の「ジョブ・サービス・model の spec は対象外で、これまでどおり明示的なテストで守る」は事実と違います。ジョブの N+1 を検査するテストは 1 つもありません（`spec/jobs` に該当なし）。また Bullet には `Bullet::ActiveJob` という仕組みがあり、`perform` のたびに `Bullet.profile` で計測を区切ります。そのため、factory で作ったデータが対象外になる問題も起きず、ジョブの spec でも検知できる見込みです（推測。`Bullet.profile` は `start_request` で作り直すので、草案の sanity spec と同じ理屈で効くはず）。
- 根拠：`bullet-8.1.3/lib/bullet/active_job.rb`、`bullet.rb` 238〜256 行目（`profile`）、`app/jobs/application_job.rb`（未導入）
- 直し方の提案：まず概要を「ジョブ・サービスの N+1 は今も守られておらず、このチケットでも対象外」と正直に直す。`Bullet::ActiveJob` は、比較した案に「F：ジョブにも広げる（別チケット）」として載せ、採用しない理由を書く。採用しない理由は、bullet が production の Gem グループに無いので `ApplicationJob` に `include Bullet::ActiveJob if defined?(Bullet)` が要る、通知系ジョブの spec の件数を確かめる必要がある、など。

### 指摘5【軽微】（観点：スコープと依存の切り方）
- 何が問題か：依存が git の管理外のファイル名（`ticket_rails_ci_ruby_3_4_12.md`）になっていて、Notion のチケットに移すと辿れません。また、この依存が着手を止めるのか、マージを止めるのかが書かれていません。`raise` がテストに届くことも、`includes` を外して落ちることも、ローカルの rspec で確かめられます。
- 根拠：草案の「依存」の節
- 直し方の提案：CI チケットの TSK 番号に置き換える。そのうえで「着手はすぐできる。マージ（と CI で赤を見る確認）は CI チケットの後」と書き分ける。
