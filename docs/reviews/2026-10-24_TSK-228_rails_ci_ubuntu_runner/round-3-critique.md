## 指摘（重要な順）

### 指摘1【重要】（観点：事実か推測か／失敗の想定）
- 何が問題か：`FROM ruby:3.4.12` は Debian 13（trixie）のイメージです。今の `ruby:3.4.4` は Debian 12（bookworm）なので、Ruby の更新と同時に開発環境の OS も更新することになります。草案はこれに触れていません。
  - Dockerfile の `apt-get install -y ... yarn` は、bookworm では仮想パッケージで解決できていました。trixie には `yarn` がありません。そのため「やること」の 2 つ目（`docker compose build`）で失敗する可能性が高いです。
  - 仮にビルドが通っても、`gem_data` ボリューム（`/usr/local/bundle`）には bookworm でビルドした mysql2 などのネイティブ拡張が残ります。これを trixie の上で動かすことになります（ABI は 3.4.0 で同じですが、リンク先のシステムライブラリの版が変わります。動くかどうかは推測で、未確認です）。
- 根拠：Docker Hub の digest の一致（上の「確かめた事実」）。packages.debian.org の trixie の `yarn` のページ。`rails/Dockerfile` の 3〜8 行目。`docker-compose.yml` の `gem_data:/usr/local/bundle`。`yarn` が実際に失敗するかはビルドしていないので、推測です（確度は高い）。
- 直し方の提案：
  - 設計とやることの Dockerfile の行を `FROM ruby:3.4.12-bookworm` にしてください。OS は今と同じで、Ruby のパッチだけが上がります。関心事は「Ruby のパッチ更新」1 つにそろいます。
  - 比較した案にも 1 行足してください。例：「`ruby:3.4.12`（trixie）：ベース OS も変わり、`yarn` が無くビルドが通らない見込み。Debian の更新（と、API には要らないと思われる nodejs・yarn の整理）は別チケット」。
  - 検証済みの前提の表には「`ruby:3.4.4` は bookworm、`ruby:3.4.12` は trixie（Docker Hub の digest）」を足してください。

### 指摘2【重要】（観点：スコープと依存の切り方／利用者・開発チームのデメリット）
- 何が問題か：イメージを 3.4.12 で作り直すと、Gemfile が `ruby '3.4.4'` のままのブランチでは、Bundler が「Your Ruby version is 3.4.12, but your Gemfile specified 3.4.4」で止まります。rails と sidekiq の両コンテナが起動しません。草案が main の取り込みを書いているのは #213 だけです。しかし #212（教員のお知らせ編集）と #199（生徒の学習分析）も、画面を確かめるにはバックエンドを動かす必要があります。逆に、作り直していない人が main を pull すると、3.4.4 のコンテナが Gemfile の 3.4.12 で止まります。
- 根拠：`rails/Gemfile` の `ruby` 指定と `docker-compose.yml` の `command: bundle exec ...`。`gh pr list` で開いている PR は #213・#212・#199。Bundler の挙動は仕様に基づくもので、手元では試していません。
- 直し方の提案：
  - やることの「マージ後」の行を「#213・#212・#199（と作業中のローカルブランチ）に main を取り込む」に広げてください。
  - PR 本文の手順には、症状と対処を 1 行ずつ書いてください。症状は「`Your Ruby version is ..., but your Gemfile specified ...` で起動しない」、対処は「main を取り込む、または `docker compose build`」です。
  - 完了条件の「開発環境で 3.4.12 で起動」の確認方法も書いてください（例：`docker compose exec rails ruby -v` で `3.4.12`、`sidekiq` も起動している）。

### 指摘3【軽微】（観点：事実か推測か）
- 何が問題か：未検証の 3 つ目（「一度ビルドされた Ruby が新しい実行環境から消えるか」）は、今確かめられます。`ruby-3.4.11` のリリースには ubuntu-26.04 向けのビルドがあり、3.4.12 が出たあとも残っています。つまり、パッチが出るたびに CI が落ちるという心配はありません。CI が落ちるのは、次に `ubuntu-latest` の OS が切り替わったときだけです。
- 根拠：`gh api repos/ruby/ruby-builder/releases/tags/ruby-3.4.11` の assets に `ruby-3.4.11-ubuntu-26.04-x64.tar.gz`（2026-09-23）。
- 直し方の提案：この項目を「検証済みの前提」の表に移してください（確かめた方法：ruby/ruby-builder の `ruby-3.4.11` のリリースに 26.04 向けのビルドが残っている）。設計の「次に OS が切り替わって同じことが起きたら…」は、そのままで整合します。

### 指摘4【軽微】（観点：テスト計画／完了条件が測れるか）
- 何が問題か：「コンテナ内で `bundle install` して `RUBY VERSION` を更新する」とありますが、`bundle install` だけで `RUBY VERSION` が書き換わるかは、Bundler の版によって挙動が違います（推測）。書き換わる保証が欲しいときのコマンドは `bundle update --ruby` です。更新が漏れると、CI では `setup-ruby` の `bundler-cache` が deployment（frozen）モードで動くので、Gemfile とロックファイルのずれでエラーになる可能性があります（推測）。あわせて、3.4.12 に同梱の Bundler が 2.6.9 より新しい場合に `BUNDLED WITH` も書き換わるかどうかも、差分で見ておくと安心です。
- 根拠：`rails/Gemfile.lock` の 451〜455 行目。Bundler の `bundle update --ruby` オプションの存在。挙動は手元では確かめていません。
- 直し方の提案：やることを「`bundle install` 後、`git diff rails/Gemfile.lock` で `RUBY VERSION` が `ruby 3.4.12p…` になったことを確かめる。変わっていなければ `bundle update --ruby`」に直してください。`BUNDLED WITH` が変わった場合は、残すか戻すかを PR 本文に書いてください。

### 指摘5【軽微】（観点：失敗の想定）
- 何が問題か：ロールバックの手順がありません。本番が無いので影響は小さいのですが、3.4.12 で予期しない不具合が出たときに戻す手段は書いておくべきです。案 B で戻すと、Ruby が 3.4.4 になり、CI が 26.04 で再び全滅します。つまり「単純な revert」は戻し先として成り立たず、実質的な戻し先は案 A（3.4.4 のまま `runs-on: ubuntu-24.04`）になります。
- 根拠：比較表の案 A と、失敗ログ（26.04 には 3.4.4 が無い）。
- 直し方の提案：設計に 1 行足してください。例：「戻す場合：PR を revert し、CI は案 A（`runs-on: ubuntu-24.04`）で一時的にしのぐ。開発環境は再度 `docker compose build`」。案 A を比較表に残しておく価値も、ここで生まれます。
