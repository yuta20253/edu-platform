# 批判：Rails CI を Ubuntu 26.04 の実行環境でも失敗しないようにする（第1周）

## 総評
原因の特定と検証はしっかりしていて、方針（OS を固定し、Ruby の更新とは分ける）も妥当です。ただし、ワークフローの変更だけでは Rails CI が動かない作りをそのままにしています。そのため検証の手順が回りくどく、Ruby 更新の先送りも「候補」のままで期限がありません。

## 判定
直せば進めてよい
（案 A は正しい。直すべきは検証のしかたと、先送りする負債の回収方法の 2 点）

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒・教師・管理者） | 直接は見えない。間接的には、Rails の変更（例：#213 の教員の面談一覧・申請）が RSpec・Brakeman を通ってからリリースされる。テストされていない変更が本番に出ることを防ぐ | 見た目・挙動の変化はない。強いて言えば、Ruby 3.4.4 を使い続ける期間が延びる（本番の Ruby が 3.4.4 なら、3.4.5〜3.4.12 の修正が入らないまま。推測） |
| 開発チーム | Rails CI の 4 ジョブが元どおり通り、#213 が進められる。毎回出ていた `Unexpected input(s)` の警告が消える | OS を固定するので、ubuntu-latest に自然に追従しなくなる（負債）。24.04 の廃止時期に依存する |

- 両方にメリットがあるか：利用者に損がない内部整理
  利用者に見える変化はありません。CI が止まったままだと、テストされていない変更がリリースされうるので、利用者を守る意味もあります。開発チームのメリットははっきりしています。
- やらないことのデメリット：
  - 利用者が失うもの：main にはブランチ保護がありません（`gh api .../branches/main/protection` → 404 "Branch not protected"）。CI が赤のままでもマージできてしまうので、テストを通っていない Rails の変更がリリースされる危険があります。
  - 開発チームが失うもの：Rails を触るすべての PR で、RuboCop・RSpec・Brakeman・Bundler Audit が動きません。レビューの品質保証がなくなります。
- 草案に書かれていなかったメリット・デメリット：
  - 「草案に無い」：CI は必須チェックではなく、マージは止まりません。本当の損失は「マージが止まる」ことではなく、「検証されていない変更がマージされうる」ことです（指摘 4）。
  - 「草案に無い」：bundler-audit は gem しか検査せず、Ruby 本体の脆弱性は検知しません。Ruby を固定し続けるリスクは、今の CI では見えません（指摘 2）。

## 確かめた事実
- `rails-ci.yml`：4 ジョブとも `runs-on: ubuntu-latest`、`ruby-version-file: rails/.ruby-version`、トリガーは `pull_request.paths: 'rails/**'` だけ。草案のとおり。
- Ruby 3.4.4 を 4 か所で固定していることを確認した（`.ruby-version` = `ruby-3.4.4`、`Gemfile` 5 行目、`Gemfile.lock` 452 行目 `ruby 3.4.4p34`、`Dockerfile` 1 行目）。草案のとおり。
- run 40076128057：4 ジョブとも `Unavailable version 3.4.4 for ruby on ubuntu-26.04` と、`ruby-3.4.12 is available on ubuntu-26.04` の案内が出ていた。`Unexpected input(s) 'ruby-version-file'` の警告と、有効な入力の一覧（`ruby-version-file` は含まれない）もログで確かめた。`action.yml` の inputs にも無い。草案のとおり。
- 最後に成功した run は 39030222693（10/17、TSK-104）で、`Image: ubuntu-24.04`。草案のとおり。
- `rails-ci.yml` の最終変更は #171（a4a451ba）。草案のとおり。
- `ruby-builder.js` の `unavailableVersionHint`：コメントは「Newer runner images usually only have builds of the latest patch release of each series」。草案の説明と一致する。
- 草案との食い違いが 1 つある。「Rails を触る PR はすべてマージ前のチェックが通らない」とあるが、main はブランチ保護がなく、Rails CI は必須チェックではない。チェックは赤になるが、マージは止まらない。

## 残すべき強み
- 検証済みの前提と未検証のことを表で分けている。どの前提もログ・`git log`・setup-ruby の実装で裏が取れていて、改訂で消さないでほしい。
- 「CI を直すこと」と「本番の Ruby を上げること」を分けた判断が良い。CI の修正に本番の実行環境の変更を混ぜないのは正しい。
- 案 C（CI だけ `'3.4'`）を「Gemfile の `ruby '3.4.4'` と食い違い、Bundler がエラーにする」という具体的な理由で退けている。
- 無効な入力 `ruby-version-file` の削除を「動作は変わらず、警告が消えるだけ」と、影響と一緒に書いている。
- frontend-ci を変えない理由が書かれている。

## 指摘（重要な順）

### 指摘1【重要】（観点：テスト計画／完了条件が測れるか）
- 何が問題か：ワークフローを変えても Rails CI が動かない構造をそのままにしているため、検証に「#213 を rebase する」か「空変更を入れて外す」かが要ります。前者は検証が別 PR 頼みになり、後者は消し忘れの危険があります。別チケット候補で「CI の OS を戻す」ときも、同じ問題が繰り返し起きます。
- 根拠：`rails-ci.yml` の `on.pull_request.paths` が `'rails/**'` だけ。
- 直し方の提案：`paths` に `'.github/workflows/rails-ci.yml'` を追加します。この PR 自体で 4 ジョブが動き、完了条件を「この PR の Rails CI の 4 ジョブが `Image: ubuntu-24.04` で成功する」と、この PR の中で測れる形にできます。#213 の rebase は、検証ではなく後続の作業として扱えます。

### 指摘2【重要】（観点：やらないことのデメリット／失敗の想定）
- 何が問題か：Ruby を上げるチケットが「別チケット候補」のままで、ID も期限もありません。1 か月後に困るとすれば、「24.04 固定が忘れられて、Ruby 3.4.4 を使い続ける」か「24.04 の廃止告知が来て、慌てて Ruby を上げる」かのどちらかです（推測）。さらに bundler-audit は Ruby 本体の脆弱性を検知しないので、3.4.4 を使い続けるリスクは CI に出ません。
- 根拠：草案の「依存」の欄。`rails-ci.yml` の bundler-audit は `bundle exec bundler-audit check --update` だけ（gem の検査）。
- 直し方の提案：
  - (a) Ruby 更新のチケットを、このチケットと同時に Notion に起票し、依存の欄に ID を書く。
  - (b) `runs-on: ubuntu-24.04` の横に、固定した理由と回収先のチケット ID をコメントで残す。後で誰かが「なぜ latest じゃないのか」と迷わないようにするため。
  - (c) 24.04 の廃止日の確認は、Ruby 更新チケットの期限で回収すると書けば十分です。

### 指摘3【軽微】（観点：事実か推測か／代替案の比較）
- 何が問題か：案 B を退ける理由の 1 つ、「3.4.12 が最新でなくなると、新しい実行環境で同じことが起きる」はおそらく外れています（推測）。setup-ruby の文言は「新しいイメージには、各系列の最新パッチだけをビルドする」で、一度ビルドされた 26.04 向けの 3.4.12 が後から消えるとは読めません。困るのは、もっと新しいイメージ（次の OS）が出たときです。
- 根拠：`ruby-builder.js` 103〜136 行目。消えるかどうかは推測です。確かめるには、ruby/ruby-builder のリリースで、24.04 のイメージが出た後のリリースに、24.04 向けの古いパッチが残っているかを見ます。
- 直し方の提案：案 B を退ける理由は「CI の修正に、本番の Ruby の更新を混ぜない」で十分です。この理由は削るか、「未検証」の表に移してください。

### 指摘4【軽微】（観点：利用者にとってのメリット・デメリット）
- 何が問題か：概要の「マージ前のチェックが通らない」は、マージが止まるように読めますが、実際は止まりません。利用者にとっての本当のリスクは、「テストされていない Rails の変更がマージされうる」ことです。
- 根拠：main のブランチ保護が無いことを API で確認した（404）。
- 直し方の提案：概要と背景の該当文を「CI が赤のままでもマージできるため、テストされていない変更がリリースされうる」に直し、利用者のメリットとして書きます。必須チェックにするかどうかは、別の判断としてオーナーに聞きます（問い 3）。

### 指摘5【軽微】（観点：代替案の比較）
- 何が問題か：比較表に、「OS に左右されない」方向の案がありません。例えば、ジョブを `container: ruby:3.4.4`（Dockerfile と同じイメージ）で動かす案です。OS を固定する必要がなく、CI と開発環境の Ruby が必ず一致します。
- 根拠：`rails/Dockerfile` 1 行目の `FROM ruby:3.4.4`。
- 直し方の提案：採用は勧めません。`bundler-cache` が使えず、キャッシュを自前で書くことになり、サービスへの接続先（`127.0.0.1` → サービス名）も変わって変更が大きくなるためです。ただ、比べたことと不採用の理由を 1 行足しておくと、Ruby 更新チケットで同じ議論を繰り返さずに済みます。

## 本人に確認すべき問い
1. 本番（予定を含む）の Ruby のバージョンとデプロイ先はどうなっていますか。Cloudflare 構築計画と Go 移行の時期によっては、「Rails の Ruby を上げるチケット自体をやらない（Go 移行まで 24.04 で持たせる）」という判断もありえます。どちらにするか決めてください。
2. Ruby 更新のチケットは、いつまでに着手しますか。期限か、着手のきっかけ（例：24.04 の廃止告知、Go 移行の延期）を決めてください。
3. Rails CI（と frontend CI）を、main の必須チェックにしますか。今回のように CI が全滅してもマージは止まらない状態が、意図したものかどうかを確認したいです。このチケットの範囲外で構いません。
