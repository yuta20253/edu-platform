## 確かめた事実

- `EditGoal/index.tsx`、`EditTask/index.tsx`:草案どおり。`useForm` などは早期 return の前にあります。
- `useFetchGoal.ts`:404 は「目標が見つかりませんでした」、それ以外は「目標の取得に失敗しました」、401 は `router.push` のみ。`useApiQuery` の 401(`push` して error を立てない)と同じなので、401 の特性化テストは移行前後で同じ結果になります。
- `useFetchGoal` / `useFetchTask` は、`features/student/Edit*` の外から参照されていません(`grep` で確認)。削除の影響範囲は2画面の中です。
- `hooks/useCourses.ts` は `apiClient.get` を呼びます。つまり EditTask の `index.test.tsx` で `apiClient.get` をモックすると、呼び出しは task の取得だけではありません。
- `AsyncBoundary` は `errorMessage` と `onRetry` を受け取り、`children` は `(data) => ReactNode` の関数、error を先に判定します。草案の使い方と合います。
- `Question/index.test.tsx` に `renderToString` で初回描画を見る前例があります。草案の「サーバー描画の初回描画のテスト」はこれに倣った書き方で、現行のコードで通るはずです。

## 指摘(重要な順)

### 指摘1【軽微】(観点:完了条件/規模)「着手」の定義が揺れていて、実画面確認の順序が2か所で書かれていない
- 何が問題か:
  - やることの先頭は「(TSK-219 のマージ後に再評価して着手)」です。その直後に、特性化テストは「TSK-219 を待たずに書ける」とあります。先頭の項目が「全体の着手」を指すなら、特性化テストだけ先行できる、という例外が読み取りにくいです。
  - 概要と未検証表には、実画面確認が「置き換えの後、PR の前」だという順序が書かれていません。判断節、やること、完了条件の3か所は一致しています。5か所のうち2か所が曖昧、という状態です。矛盾はしません。
- 直し方の提案:
  - 先頭の項目を「(置き換え本体は TSK-219 のマージ後に再評価して着手。特性化テストだけは先行できる)」に直す。
  - 未検証表の2行目の「確かめる方法」に「置き換えの後、PR の前に」を足す。概要の1文は不要です。

### 指摘2【重要】(観点:テスト計画)EditTask の特性化テストで `mock.calls[0][0]` が URL の指定として信用できない
- 何が問題か:
  - 草案は「URL だけ(`mock.calls[0][0]`)を見る」と書いています。EditTask は `useCourses` も `apiClient.get` を呼びます。どちらが先に呼ばれるかは、hook の宣言順と effect の実行順に依存します。移行後は `useApiQuery` の effect が `useCourses` と並ぶので、順序の前提が崩れる可能性があります。特性化テストが「移行で壊れる」のでは、目的に反します。
  - EditGoal は取得が1本なので影響は小さいです。
- 根拠:`hooks/useCourses.ts` に `apiClient.get`。EditTask の `index.tsx` で `useFetchTask` の次に `useCourses` を呼んでいます。
- 直し方の提案:`calls[0][0]` ではなく、「呼び出しの中に、task の URL を第1引数に持つものがある」(`mock.calls.some(([url]) => url === ...)` など)と書く。または URL でモックの戻り値を振り分けて、`useCourses` の URL にも別の応答を返す(これは EditTask のテストのモックに必要になるはずです)。

### 指摘3【軽微】(観点:完了条件)完了条件の6ケースが、やることのケースと揃っていない
- 何が問題か:やることにある「サーバー描画の初回描画」と「EditTask の選択済み単元の反映」が、完了条件の `index.test.tsx` の内訳(スピナー、成功、500→再試行→成功、401、404、ネットワークエラー)に入っていません。完了条件を満たしても、この2つが落ちる余地があります。
- 直し方の提案:完了条件に「(任意)初回描画、EditTask の選択済み単元」を足すか、やるべきなら必須に入れる。小さいものなので、「やることに書いたケースを含む」の一文でも足ります。

### 指摘4【軽微】(観点:テスト計画)「移行前の現行コードで緑だった」ことの示し方
- 何が問題か:PR 説明に書くだけだと、あとから検証できません。
- 直し方の提案:特性化テストのコミットを、置き換えのコミットより前に独立して置く(`test:` のコミットと `feat: ...(green)` のコミットを分ける)と書く。コミット名の規約は草案のままで妥当です(`(red)` を付けない)。`Question` の前例は `(red)` → `(green)` の並びなので、同じ並びで `test:` → `feat:` になります。
