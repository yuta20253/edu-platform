# 批判：student/EditGoal・EditTask の AsyncBoundary 移行（第1周）

## 総評
分割後の草案は、利用者への効果が小さいことを正直に書けています。設計の中身（フォームを外に置く、404 文言の維持）もコードと矛盾しません。ただし「今チケットにする価値」の根拠が弱く、テスト計画に Red が1つも無いのが問題です。

## 判定
直せば進めてよい（ただし起票は Backlog 止まり）。
- 設計は成立しています。
- 利用者に機能面の効果が無く、TSK-219 待ちです。いま Open で起票する理由が無いため、起票先は Backlog が妥当です。
- 草案の記述上の欠点（指摘1〜4）は、直せば済みます。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒） | 機能面は無し。エラー表示の見た目が `ErrorState` に揃うだけ。 | ローディングが `100vh` 中央から `minHeight: 240` に縮み、フォームの表示時に画面が動く可能性がある。404 でも再試行が出るのは現行と同じ。 |
| 開発チーム | 手書きの取得フック2本（`useFetchGoal` / `useFetchTask`）と、そのテスト2本の削除。手書きの `Alert` 2か所の削除。TSK-216 の許可リストから2画面を外せる。Go 移行時に、見るべき取得ロジックが減る。 | TSK-219 のマージ待ち。新規テスト（`index.test.tsx` が両画面とも無い）を一式書く負担。 |

- 両方にメリットがあるか：**どちらも弱い**（開発側にはコード削減という確かなメリットがあるが、利用者側はゼロかマイナス）。「利用者に損がない内部整理」とも言い切れない。スピナーの縮みが実画面で確かめられておらず、損の有無が未確定のため。したがって「いま着手すべき」とは言えない。**Backlog 止まりが妥当**（理由は下の「やらないことのデメリット」と指摘1）。
- やらないことのデメリット：
  - 利用者が失うもの：ほぼ無い。再試行は現行でもでき、404 の文言も出る。
  - 開発チームが失うもの：TSK-216 の許可リストに2画面が残る。手書きの取得フックが2本残る。ただし `AsyncBoundary` に寄せ切れていない例外が2画面あるだけで、動作上の害は無い。
- 草案に無かったメリット・デメリット：
  - 草案に無いメリット：`useApiQuery` の利用画面が1つ増える。TSK-219 の `errorStatus` が実際の「404 出し分け」で使われると証明される（TSK-219 の存在意義の裏付けになる）。
  - 草案に無いデメリット：なし。

## 確かめた事実
- `EditGoal/index.tsx` / `EditTask/index.tsx`：草案どおり。`useForm` と `EditTask` の `useCourses` / `useUnitSelection` / `useEffect` は、早期 return（エラー、ローディング）の**前**に置かれています。`AsyncBoundary` の外（上）に置く設計は、フックの呼び出し順の規則に反さず、現行コードと矛盾しません。ここは正しい。
- `useFetchGoal.ts` / `useFetchTask.ts`：404 は「…が見つかりませんでした」、それ以外は「…の取得に失敗しました」。401 は `/login`。草案どおり。
- `useApiQuery.ts`：`error: boolean` のみで、`errorStatus` は無い。草案どおり。
- TSK-219（Notion、未着手）の仕様案：`errorStatus?: number`、`error: boolean` は維持、再取得の開始時に消す、401 は入れない。**草案の404出し分けと整合します。** 現行の `setFetchError(null)` も再取得の開始時に消していて、挙動も同じです。
- **食い違い（草案に無い事実）**：
  - `EditGoal/hooks/useFetchGoal.test.ts` と `EditTask/hooks/useFetchTask.test.ts` はあります。一方、`EditGoal/index.test.tsx` も `EditTask/index.test.tsx` も**どちらも存在しません**（`Presenter.test.tsx` のみ）。草案の「各画面に `index.test.tsx` を追加する」は、現状ゼロからの新規作成です。
  - `EditGoal/hooks/` には `useFetchGoal` と `useSubmit` があり、`EditTask/hooks/` には `useFetchTask` と `useSubmit` があります。削除の対象は取得フックだけで、草案の範囲どおり。
- `CreateTaskConfirm/useFetchGoal.ts` は別物（別ディレクトリ）なので、混同して消さないよう注意が必要です。

## 残すべき強み
- 「再試行は現行でもできる。機能面の改善は無い」と正直に書いている点。
- 案A（404 文言を捨てる）を退け、TSK-219 を必須の依存にしている点。
- スピナーの縮みを「未検証の前提」に入れ、実画面で確かめる方法と、`fallback` に要素を渡す案Dまで用意している点。
- 404 でも再試行が出るのを「現行と同じ。別件」として、移行に混ぜていない点（スコープが小さい）。

## 指摘（重要な順）

### 指摘1【重要】（観点：やらないことの検討／代替案の比較）案Cの検討が浅く、起票の判断材料が足りない
- 何が問題か：草案は案Cを「要検討」としたまま終わっています。オーナーが判断できる形になっていません。
- 判断（私の意見）：
  - **Backlog で起票するのが最も妥当**です。
  - 「起票しない」は避けるべきです。理由は、TSK-216 の許可リストに理由なく2画面が残るためです。許可リストは、恒久的な例外ではなく移行予定の一覧として機能させるべきです。
  - 「案C（許可リストに残す）」を選ぶなら、チケットは立てずに、リストに「TSK-219 後に移行予定。理由：利用者への効果が小さい」と書きます。この場合の欠点は、2画面が忘れられることです。
  - 「Backlog 起票 + 許可リストにチケット番号を注記」が、忘れず、かつ優先度を下げる最も安い選択です。
- 直し方の提案：「優先度 Backlog。TSK-219 マージ後に再評価し、スピナーの縮みを実画面で確かめて問題なければ着手」と判断条件を書く。案Cとの違いを「Backlog 起票は、許可リストに残るチケットを紐付ける点だけが違う」と明確にする。

### 指摘2【重要】（観点：テスト計画）Red が1つも無いのに、Red と回帰防止の区別が書かれていない
- 何が問題か：
  - 草案は「現行で Red になるか回帰防止かを区別して書く」と言っています。区別は実際にはしていません。
  - **この移行の「取得中のスピナー」「成功」「失敗 → 再試行」「401」「404 の文言」は、現行のコードでもすべて満たしています。** `index.test.tsx` を現行に対して書いても、すべて通ります。つまり、**この移行には真の Red がありません**。全部が回帰防止のテストです。
  - 例外は、`role="progressbar"` のスピナーだけです（`CircularProgress` は同じだが、サーバー描画の挙動は `AsyncBoundary` 側の実装次第）。それも現行でも通るはずです（推測。確かめる方法は、テストを先に書いて現行で走らせること）。
  - 「401 のテスト」は `router.push("/login")` が呼ばれることを確かめる。これも現行で通ります。
- 根拠：`useFetchGoal.ts` / `useFetchTask.ts` の分岐。
- 直し方の提案：
  - 「やること」を「回帰防止テスト（移行前に `index.test.tsx` を先に書き、現行で緑になることを確かめる → 移行後も緑のまま）」と明記する。**先に書いて現行で緑にする**ことで、移行で挙動が変わらないことが示せる。Red/Green の TDD ではなく「特性化テスト」の手順だと書く。
  - 唯一の Red 候補は、移行後に新しく生じる差（例：`ErrorState` の文言・見た目）だけです。それ以外を「Red」と呼ばないこと（TSK-211 の教訓）。
  - フックのテスト2本の削除は、`index.test.tsx` が同等のケース（404、401、500、再試行）を網羅してから行う。順序を守らないと網羅が落ちる。

### 指摘3【重要】（観点：事実か推測か／テスト計画）「再取得でフォームの入力が消えないか」が未検証
- 何が問題か：
  - `useApiQuery` は再取得中も data を残し、成功すると新しい data で置き換えます。EditTask の `useEffect` は `task?.units` が変わると `setSelectedUnitIds` を呼びます。現行の `useFetchTask` でも `refetch` で同じ動きなので差は無いはずです（推測）。ただし**参照が変わるタイミング**は同じとは限りません。
  - `useApiQuery` の url 変更時の注意書き（古い data が残る）も、`goalId` / `taskId` が変わる場合に関わります。App Router がページごと作り直すなら問題にならない（TSK-217 の実画面確認で確認済み）ですが、草案はそれに触れていません。
  - 再試行が走る場面は失敗時の1回だけで、その時 data は `null` です。入力が消える恐れは小さいと思います。ただし「確かめた」とは書かれていません。
- 直し方の提案：「未検証の前提」に「`taskId` / `goalId` が変わってもページが作り直される（TSK-217 で確認済み）」と、「`task?.units` の参照変化による `selectedUnitIds` のリセットは、現行と同じ」を書く。後者はテストで、`refetch` 後も `selectedUnitIds` が維持されることを確かめる。

### 指摘4【重要】（観点：スコープ／完了条件）完了条件に、404 の仕組みと TSK-219 の依存の確認が足りない
- 何が問題か：
  - `errorMessage` は `AsyncBoundary` の props 上は固定の文字列です。`errorStatus` から作った文言を渡す設計は成立しますが、**`errorStatus` が `undefined` のとき（ネットワークエラー）の文言**（「…の取得に失敗しました」）が、完了条件に入っていません。「それ以外は…」に含めるなら明記が必要です。
  - 完了条件の「取得に失敗すると再試行できる」は、現行でもできることをもう一度書いているだけで、移行の完了を測っていません。
  - TSK-219 が未マージのうちは、この草案の前提（仕様案）が変わる可能性があります。「マージ後に `useApiQuery.ts` を読んで確かめる」と書いてあるのは良いですが、`errorStatus` の型・名前が違った場合の扱いが無いです。
- 直し方の提案：完了条件に「ネットワークエラー（`errorStatus` なし）でも『取得に失敗しました』が出る」を追加し、その確認テストも「やること」に入れる。「再試行できる」は残してよいが、「テストで 500 → 再試行 → 成功が確かめられている」に書き換える。

### 指摘5【軽微】（観点：利用者のデメリット）スピナーの縮みの確認が「オーナーの了承を得てから」で止まっている
- 何が問題か：実画面での確認が、了承待ちの条件付きになっています。TSK-217 の教訓から、確認は計画の必須項目です。しかも、この確認が案Dの要否を決めるので、着手の前提になります。
- 直し方の提案：「実画面確認」を「やること」のチェックボックスに入れる。確認の手順を書く（開発サーバーで遅いネットワークにして、スピナーからフォームへの切り替えを見る）。問題があれば `fallback` に高さ（`100vh` 相当）を保つ要素を渡す。その場合、`index.tsx` に例外が出ると TSK-216 の走査に引っかかるので、要素を別ファイル（`LoadingScreen.tsx` など）にする手もある。

### 指摘6【軽微】（観点：完了条件）TSK-216 との整合の書き方
- 何が問題か：「TSK-216 が未マージなら…コメントする」は、手順が曖昧です。
- 直し方の提案：「`index.tsx` に `CircularProgress` の import が無い」を条件にする。許可リストの更新は、TSK-216 の状態に応じて「PR 内で外す／TSK-216 にコメントする」のどちらかを、着手時に決める。
