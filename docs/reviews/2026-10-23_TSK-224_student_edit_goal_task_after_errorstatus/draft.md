## 概要

`features/student/EditGoal` と `EditTask` の `index.tsx` で、手書きのローディング(`CircularProgress`)とエラー表示(`Alert` + 再試行ボタン)を、`AsyncBoundary`(+ `useApiQuery`)に置き換える。404 のとき「見つかりませんでした」と出し分ける現行の文言は維持する。

**この移行には、真の Red が無い。** 取得中のスピナー、成功、失敗 → 再試行、401、404 の文言は、現行でもすべて満たしている。そのため、**特性化テスト(移行前に書き、現行のコードで緑になることを確かめ、移行後も緑のままであるテスト)を先に書く**ことで、挙動が変わらないことを示す。

**TSK-219(`useApiQuery` が `errorStatus` を返す)のマージ後に着手する。** 利用者への機能面の効果が無いため、**Backlog で起票する**。

元は CreateTaskConfirm / Calendar といっしょの草案だった。レビューで、「価値の中心は CreateTaskConfirm の不具合修正で、EditGoal / EditTask は TSK-219 待ちで価値も小さい」と指摘されて分けた。

## 背景(調査結果)

- EditGoal / EditTask は、取得に失敗すると、手書きの `Alert` と「再試行」ボタンを出す。**再試行はすでにできる。**
- 失敗時の文言は、404 のとき「目標(タスク)が見つかりませんでした」、それ以外は「…の取得に失敗しました」と出し分けている。
- ローディングは `CircularProgress`(`100vh`)。`index.tsx` に `CircularProgress` の import がある(TSK-216 の走査・ESLint の対象)。
- 取得は `hooks/useFetchGoal.ts` / `hooks/useFetchTask.ts`。`useApiQuery` は失敗を `error: boolean` でしか返さないため、404 の出し分けを移せない。
- **両画面とも `index.test.tsx` は無い**(`Presenter.test.tsx` と、取得フックのテストだけがある)。

## 設計

- `useFetchGoal` / `useFetchTask` を `useApiQuery` の呼び出しに置き換える。`index.tsx` を `AsyncBoundary` で包み、`onRetry` に `refetch`、`errorMessage` に `errorStatus` から作った文言(404 は「見つかりませんでした」、それ以外と `errorStatus` が無い場合は「取得に失敗しました」)を渡す。
- フォーム(`react-hook-form` の `useForm`)と、EditTask の `useCourses` / `useUnitSelection` / `useEffect` は、`AsyncBoundary` の外(上)に置く。これまでと同じ。
- `hooks/useFetchGoal.ts` / `hooks/useFetchTask.ts` とそのテストを削除する。**削除は、`index.test.tsx` が同等のケース(404、401、500、再試行)を網羅してから行う**(順序を守らないと網羅が落ちる)。
- **利用者に見える変化**: 手書きの `Alert` が `ErrorState` の見た目に変わる。ローディングが `100vh` から共通のスピナー(`minHeight: 240`)に変わる。**再試行は現行でもできるので、機能面の改善は無い。**
- **404 のときも「再試行」が出る**のは、現行と同じ(404 は再試行しても直らない)。直すかどうかは別件。

## 他のチケットの文言の直し

Notion の TSK-215 には、EditGoal / EditTask について「再試行できるようになる」と書いてあるが、**現行でも再試行はできる**(手書きの `Alert` に再試行ボタンがある)。事実と合わないので、TSK-215 の文言を「見た目の一貫性とコードの削減(機能面の改善は無い)」に直す(オーナーの承認を得てから)。

## 利用者へのメリット(正直に)

見た目の一貫性と、コードの削減(手書きの取得フック2本と、`Alert` の実装2か所)が中心で、**利用者への機能面の効果はほとんど無い**。ローディングの縮みで、むしろ体験が悪くなる可能性がある(未検証)。したがって、**今すぐ着手する理由は無く、Backlog で起票する**。

## 判断: Backlog で起票する

- 「起票しない」(案 C)は選ばない。TSK-216 の許可リストに、理由もチケットも無い例外が2画面残るため。許可リストは、恒久的な例外ではなく、**移行予定の一覧**として機能させたい。
- **Backlog 起票は、許可リストに「このチケット(番号)で移行予定。TSK-219 のあと。利用者への効果が小さいため優先度が低い」と注記できる点だけが、案 C との違い。** 忘れず、かつ優先度を下げる最も安い選択。
- **着手の条件**: TSK-219 がマージされ、再評価したうえで着手する。スピナーの縮みは、**置き換えの後、PR の前に実画面で確かめる**(着手の条件にはしない。移行後のコードでないと確かめられないため)。同じ縮みは、TSK-215 で「teacher・admin の移行済み画面と同じ扱いとして許容する」と決めている(2026-10-23)。このチケットで聞くのは「フォーム画面でも同じ扱いでよいか」だけ。問題があれば、同じ PR の中で案 D(`LoadingScreen.tsx`)を足す。
