## 確かめた事実

- `EditGoal/index.tsx` と `EditTask/index.tsx`:草案の記述どおり。`useForm`、`useCourses`、`useUnitSelection`、`useEffect` は早期 return の前にあります。再試行ボタンは現行でもあります。
- `useFetchGoal.ts` と `useFetchTask.ts`:404 は「…が見つかりませんでした」、それ以外は「…の取得に失敗しました」、401 は `/login`。草案どおり。
- `useApiQuery.ts`:`error: boolean` のみ。401 は `router.push` して error を立てません。現行フックも 401 では何も表示せずスピナーのままで、挙動は同じです。
- Notion の TSK-219:`errorStatus?: number`。ネットワークエラーでは undefined。`error` は維持。再取得の開始時に消す。401 は入れない。草案の 404 出し分けと整合します。未着手(Open)です。
- `AsyncBoundary` の `errorMessage` は文字列 prop で、error を先に判定します。現行の分岐順と同じです。`ErrorState` の `Alert` は再試行ボタンの文言も同じ「再試行」です。
- **Notion の TSK-215 と食い違う記述があります(草案に無い)。** TSK-215 の「各別チケットに生徒にとって何が良くなるか」には、EditGoal / EditTask について「再試行できるようになる」と書かれています。現行コードで再試行は既にできるので、この文は事実と合いません。TSK-215 側の記述を直すか、新チケットの本文で訂正を明記してください。
- 既存の `useFetchTask.test.ts` は `apiClient.get` が `"/api/student/tasks/1"` だけで呼ばれることを確かめています(`toHaveBeenCalledWith`)。`useApiQuery` は第2引数に `{ params, signal }` を付けて呼びます。

## 指摘(重要な順)

### 指摘1【重要】(観点:完了条件／事実か推測か)実画面確認の順序と着手条件が循環している
- 何が問題か:
  - 「やること」は「実画面確認」を、特性化テストと置き換えの前に置いています。しかし確認したいのは、移行後の `minHeight: 240` のスピナーからフォームへの切り替えです。移行前のコードでは確かめられません。
  - 「判断」節の「スピナーの縮みを実画面で確かめて問題なければ着手する」も、同じ理由で成立しません。着手の条件に、着手しないとできない確認が入っています。
  - さらに、同じスピナーの縮みを TSK-215 では 2026-10-23 に「teacher・admin の移行済み画面と同じ扱いとして許容する」とオーナーが決めています。この判断を参照すれば、オーナーへ聞き直す必要は軽くなります。フォーム画面は一覧とは違うので、「フォーム画面でも同じか」だけが論点です。
- 根拠:draft.md の「やること」「判断」節、Notion の TSK-215「利用者に見える挙動の変化」。
- 直し方の提案:
  - 実画面確認を「`AsyncBoundary` への置き換えの後」に移す。
  - 着手の条件を「TSK-219 のマージ後に再評価して着手」にする。
  - 縮みの確認は、実装後の PR で行うものと書く。問題があれば同じ PR 内で案Dを追加する(別ファイル `LoadingScreen.tsx`)。
  - オーナーへの問いは「TSK-215 と同じ扱いでよいか」に狭める。

### 指摘2【重要】(観点:完了条件)特性化テストの変更が、完了条件と概要に届いていない
- 何が問題か:
  - 「やること」には特性化テストと削除順序が反映されています。しかし完了条件には、次の項目がどれもありません。
    - `index.test.tsx` が両画面に存在すること
    - 401 で `/login` へ行くテスト(「やること」にはあります。TSK-215 の完了条件にはあります)
    - 取得フックとそのテストの削除
    - 特性化テストが移行前の現行コードで緑だったこと
  - これらが無いと、「テストが緑」だけで完了にできてしまい、削除の順序も守られているかどうかが測れません。
  - 概要も「何に置き換えるか」しか書いておらず、テストの方針が読み取れません。
- 直し方の提案:
  - 完了条件に「両画面の `index.test.tsx` がある(取得中・成功・500→再試行→成功・401・404・ネットワークエラー)」を足す。
  - 「`useFetchGoal` / `useFetchTask` とそのテストが削除されている」を足す。
  - 「特性化テストを移行前のコミットで緑にした」ことを PR 説明に書く、とする。コミット名は `(red)` を付けず、`test:` + 「特性化」と書くと、(red) 規約と混ざりません。
  - 概要に一行足す。

### 指摘3【重要】(観点:テスト計画)特性化テストが移行後に不必要に壊れる書き方になり得る
- 何が問題か:
  - 特性化テストの価値は「移行後も緑のまま」であることです。移行の前後で変わるものを断言すると、その価値が失われます。
  - 現行フックのテストは `apiClient.get` の呼び出し引数を完全一致で確かめています(`useFetchTask.test.ts`)。`index.test.tsx` で同じ書き方をすると、`useApiQuery` が `{ params, signal }` を付けるため、移行で壊れます。
  - これを直してしまうと「移行前に緑だった」という保証が弱まります。
- 直し方の提案:
  - 呼び出し引数は URL だけを見る。例:`expect(vi.mocked(apiClient.get).mock.calls[0][0]).toBe(...)`。
  - または、見た目に出る振る舞い(`alert` の文言、`progressbar`、`router.push`)だけを検証する。
  - 「やること」に「呼び出し引数の完全一致を使わない」と一行足す。

### 指摘4【軽微】(観点:スコープと依存の切り方)特性化テストは TSK-219 を待たずに書ける
- 何が問題か:
  - 「やること」の先頭は「TSK-219 のマージ後に再評価し、問題なければ着手」です。しかし特性化テストの作成は現行コードに対して行うので、TSK-219 に依存しません。
  - テストを先に入れれば、取得フック2本が将来壊れても気づけます。ただし Backlog で優先度が低いので、これを必須にする必要はありません。
- 直し方の提案:「テストの先行作成は TSK-219 を待たなくてよい」と書くだけにする。PR を分けるかどうかは着手時の判断でよい。

### 指摘5【軽微】(観点:テスト計画)`selectedUnitIds` の確認が、実質的に意味のないテストになりそう
- 何が問題か:
  - 草案が書くとおり、失敗 → 再試行が走るとき data は null です。フォームは描画されていないので、利用者の入力はありません。
  - よって「失敗 → 再試行 → 成功のあとも、`selectedUnitIds` が現行と同じ」というテストは、成功後に `task.units` の id が選択されていることを確かめるだけになります。移行前後で差が出ません。
  - 草案も「入力が消える恐れは小さい(推測)」と書いており、この理解は正しいです。テストを書くなら、成功後に初期値が入る確認として、短く済ませる程度で足ります。
- 直し方の提案:テスト名を「初回取得で選択済み単元が反映される」に直し、再試行の絡みは削る。

### 指摘6【軽微】(観点:共通化の方針)`errorMessage` の組み立てが2画面に重複する
- 何が問題か:
  - 「404 なら…見つかりませんでした、それ以外は…取得に失敗しました」を、`EditGoal` と `EditTask` の `index.tsx` で別々に書くことになります。
  - 文言が「目標」「タスク」で違うだけです。2画面分なので共通化の必要はありませんが、書かれていません。
- 直し方の提案:「共通化しない(2画面だけで、名詞が違うだけのため)」と一言書く。
