# 批判：student/UserProfile・EditUserProfile の取得失敗時の表示（サーバーコンポーネント）（第1周）

## 総評
方向（redirect に揃える、範囲を絞る）は妥当だが、「通常は到達しない」という見立ての根拠が弱い。EditUserProfile には、この草案の変更では直らない本物の不具合（getPrefectures の例外）が残る。

## 判定
直せば進めてよい。チケットにする価値は「小さいが有る」。ただし TSK-216 に含める案 E のほうが軽い可能性もある（下記）。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒） | profile・profile/edit で、セッション切れや一時的な失敗のときにスピナーのまま止まらず、ログイン画面に出る | 5xx の一時的な失敗でもログイン画面に飛ぶ（再読込で復帰できたはずの人が、ログインし直しになる）。草案に書かれていない |
| 開発チーム | 静的スピナーが消え、TSK-216 の許可リストから 2 画面を外せる。親と同じ扱いで分かりやすい | 「5xx を /login に飛ばす」という既知の不正確な挙動を、2 箇所に複製する。Go 移行後にもう一度直す対象が増える |

- 両方にメリットがあるか：**利用者に損がない内部整理に近い**。ただし利用者のメリットは「起きたら助かる」止まりで、起きる頻度は未確認。実質は、開発チームの許可リスト削減が主。
- やらないことのデメリット：
  - 利用者が失うもの：起きたときだけ、スピナーのまま止まり、手動リロードしか手がない。頻度は不明。
  - 開発チームが失うもの：TSK-216 の許可リストに恒久例外が 2 つ残る（案 D）。それだけ。
- 草案に無かったメリット・デメリット：
  - 草案に無いデメリット：5xx を認証切れと同じ扱いにして、一時障害の利用者をログイン画面へ送る。
  - 草案に無いメリット：profile 系 2 画面の挙動が親と揃う。

## 確かめた事実
- layout.tsx は `getMeFromBackend` が null なら `redirect("/login")`。草案の通り。
- me.ts は 401 も !ok も null。草案の通り。
- UserProfile/index.tsx と EditUserProfile/index.tsx は、静的な Box+CircularProgress を返す。草案の通り。`app/` に error.tsx は無い。middleware.ts / proxy.ts も無い（確認済み）。
- **食い違い（重要）**：EditUserProfile は `getMeFromBackend` の後、`!user` の判定より前に `await getPrefectures()` を呼んでいる。`getPrefectures` は `backendFetch` 経由で、401 は `BackendUnauthorizedError`、非 2xx は `BackendFetchError` を投げる。つまり**セッション切れ（401）のときは、`!user` に到達する前に例外になる**。草案の `redirect("/login")` は、edit 画面では 401 の主要ケースを救えない。
- 「実害が小さい」の根拠は、「レイアウトが同じ取得をしている」というコード上の事実のみ。「通常は到達しない」は推測（草案も未検証表に入れている点は誠実）。

## 残すべき強み
- 未検証の前提を表に分けて、確かめ方まで書いている（TSK-217 の教訓に沿っている）。
- 当初の「実害あり」を下方修正する誠実さ。
- 範囲を絞り、cache() 統合や 401/5xx の区別を別件に切り出している。
- 案 B を「レイアウトの挙動と揃わない」で退ける理由は筋が通っている。

## 指摘

### 指摘1【重要】（観点：事実か推測か）
- 何が問題か：「通常は到達しない」の根拠が弱い。レイアウトとページは**別々のリクエスト（同じ /me を 2 回）**で、片方だけが一時的に 5xx になれば、ページ側だけ null になる。さらに推測だが、App Router はクライアント遷移（Link / router.push）で共有レイアウトを再レンダリングしないので、セッション切れ後に別画面から profile へ遷移した場合、**レイアウトのガードは走らず、ページの `!user` が唯一のガードになる**。この場合は「到達しない分岐」ではなく「セッション切れの主経路」になりうる。
- 根拠：layout.tsx は サーバーコンポーネントで、Cookie 取得からの `/me` 呼び出し。Next 15 の layout の部分レンダリング挙動は私の知識に基づく推測。
- 直し方：実画面（`npm run dev`）で、ログイン後に Cookie を削除（または期限切れ）して、サイドバー等から /profile へクライアント遷移し、スピナーで止まるかを確かめる。止まるなら、草案の見立て（実害小）を戻し、背景の記述を書き換える。止まらないなら（例：遷移時にレイアウトも再取得される）、その確認結果を根拠として書き、案 D/E に倒す。

### 指摘2【重要】（観点：対策の重複／失敗の想定）
- 何が問題か：EditUserProfile で `getPrefectures()` が `!user` より前にある。上の事実の通り、401 のとき redirect に届かず例外になる。「getPrefectures の失敗は範囲外」にすると、**このチケットは edit 画面の主要な失敗ケースを直さないまま完了条件を満たしてしまう**。また、未ログインでも先に prefectures を取りに行く無駄がある。
- 根拠：EditUserProfile/index.tsx の 16–17 行目付近の順序。
- 直し方：最小の修正として、`!user` の判定を `getPrefectures()` より前に移す（2 行の並べ替え。範囲拡大ではない）。そのうえで、getPrefectures 自体の例外（5xx、error.tsx 無し）は別件に残してよい。完了条件に「edit 画面で `me` が null のとき `getPrefectures` を呼ばない」を加え、テストで確かめる。`BackendUnauthorizedError` を redirect に変換するかは別件でよいが、「401 は例外で Next の既定エラー画面になる」ことをチケットの「その他」に事実として書く。

### 指摘3【重要】（観点：利用者のデメリット／代替案の比較）
- 何が問題か：5xx でも /login へ飛ばす点は、利用者に不利益がある（バックエンドが落ちていると、ログイン済みでもログイン画面へ。ログイン画面から入り直しても同じ失敗）。「親と揃える」は理由になるが、親が不正確な挙動を複製する根拠にはならない。案 B を退ける理由に「ここだけ違う」とあるが、本当の判断軸は「そのデメリットを許容できるか」。
- 根拠：me.ts が 401 と 5xx を区別しない。
- 直し方：デメリットを草案に明記する。許容する理由（Go 移行で `/me` の扱いを見直す時に、レイアウトとまとめて直す）を書き、別件として「me の 401/5xx 区別（cache() 含む）」を実際に Notion のチケットか TSK-216 のメモに残す。「別件として記録」だけで、記録先が決まっていないのが弱い。

### 指摘4【重要】（観点：スコープと依存の切り方／代替案の比較）
- 何が問題か：チケットにする価値の判断。変更は実質 2 ファイルの数行で、テストも「null なら redirect」だけ。独立チケット（PR 1 本、レビュー 1 回）にするコストに見合うか。他の取得画面が `!user` をどう扱っているかも草案で確かめていない（student の他画面は同じ構成のものがあるか）。
- 根拠：`grep` では、`if (!user)` の分岐を持つ index.tsx は、この 2 つだけだった（他の getMeFromBackend 利用画面は別の使い方）。
- 直し方：指摘1 の実画面確認の結果で決める。
  - スピナーで止まる（実害あり）→ 独立チケットで可（案 A + 指摘2 の並べ替え）。
  - 止まらない→ 案 E（TSK-216 の中で 2 行直す）に倒す。許可リスト（案 D）は、恒久例外を作るので、避けたい。
  いずれにせよ、案 D/E の「要検討」を草案内で決着させてから確定する（今は未決のまま）。

### 指摘5【軽微】（観点：テスト計画）
- 何が問題か：Red の書き方が不明。Next の `redirect()` は例外を投げる実装なので、サーバーコンポーネントの単体テストでは、`next/navigation` をモックして呼び出しを確かめるのか、`rejects.toThrow` で確かめるのかが未定。モック漏れ（`mockResolvedValueOnce` の消化漏れ。TSK-212）にも注意が要る。現状は「静的スピナーを返す」ので、redirect を期待するテストは確かに実装前に落ちる（Red は成立する）。
- 直し方：テストの方式を 1 行書く。EditUserProfile では、「null のとき getPrefectures が呼ばれない」も含める。

### 指摘6【軽微】（観点：完了条件が測れるか）
- 何が問題か：「スピナーのまま止まらず /login に遷移する」は単体テストでは測れない（遷移はルーティング）。実画面での確認が完了条件に入っていない（TSK-217 の教訓）。
- 直し方：完了条件に「Cookie を消した状態で /profile と /profile/edit を開き、/login に出る」を手動確認として追加する。

## 本人に確認すべき問い
1. 5xx の一時障害でもログイン画面に飛ばすことを、許容するか（案 B のほうが親切だが、Go 移行までは揃えるのを優先するか）。
2. 指摘1 の実画面確認を、開発サーバーで行ってよいか（草案が「オーナーの了承を得てから」と書いている件）。
3. 確認の結果が「止まらない」だった場合、チケットにせず TSK-216 に 2 行として含める（案 E）でよいか。私は、結果が止まらないなら案 E、止まるなら独立チケットを勧める。
