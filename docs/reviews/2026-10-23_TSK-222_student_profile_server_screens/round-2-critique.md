## 指摘（重要な順）

### 指摘1【重要】（観点：事実か推測か／テスト計画）
- 何が問題か：未検証表の2行目（34行目）と完了条件（85行目）は、`/profile/edit` を「開く」「直接開く」ことで確かめる想定に読めます。直接開くと、`layout.tsx` と page が同じリクエストで描画され、レイアウトの `redirect("/login")` が先に効いて、`getPrefectures` の例外が見えない可能性があります。レイアウトと page の描画順は推測です。すると、「edit の例外は起きない」と誤って結論しかねません。TSK-217 と同種の、確認方法のせいで前提を取り違える失敗です。
- 根拠：`layout.tsx` と `EditUserProfile/index.tsx` を読んだ結果。描画順は推測。
- 直し方：確認手順を次のように分けて書く。
  1. 通常ページ（例：ダッシュボード）にログインした状態で、Cookie を削除する。
  2. 画面内の `Link` または `router.push` で `/profile` と `/profile/edit` へ遷移する。
  3. 直接開く確認は「レイアウトの `redirect` が効くことの確認」として、別項目にする。
  あわせて、prefetch やクライアント側キャッシュで遷移が再取得されない場合に偽の「問題なし」が出ないよう、遷移直前に画面を読み込み直さないこと、遷移後の Network で RSC リクエストが出たことを確認することを一言添える。

### 指摘2【重要】（観点：事実か推測か）
- 何が問題か：未検証表の2行目（34行目）の「`getPrefectures` の例外で既定のエラー画面になる」は、コードを読んだ事実（401 で例外）と、画面の観察（既定のエラー画面）が混ざっています。例外が投げられるのは事実で、「検証済み」にできます。未検証なのは、経路（クライアント遷移で起きるか）だけです。
- 直し方：「401 で例外」は検証済みの表（26行目）に既にあるので、未検証側は「クライアント遷移で `/profile/edit` に来たとき、その例外に届く」だけに絞る。

### 指摘3【軽微】（観点：テスト計画）
- 何が問題か：テストの記述は十分です。ただ、次の2点が書かれていません。
  - `redirect` モックが投げる例外を、page 側で握りつぶさないこと。現状の実装は握りつぶさないので問題ない。
  - Red の確認方法です。「現行はスピナーを返す」ので、Red は実装前に確かに落ちます。それでも、`rejects` を使うテストが実装前に「resolves して失敗」することを、`red` コミットで確かめる旨を1行書くと安全です（TSK-211 の偽陽性対策）。
- 直し方：Red コミットの時点で、2本とも失敗することを確かめる、と書き足す。

### 指摘4【軽微】（観点：スコープと依存／完了条件）
- 何が問題か：
  1. 「判断」の節（52行目）の「独立したチケットにするコストは小さくない」は、実際は逆（コストは小さい）と読めます。文意が曖昧です。
  2. 完了条件の最終行（87行目）は TSK-216 に触れている一方、「依存」は「他のチケットには依存しない」としています。許可リストが未マージなら、この行は「確認事項」にとどまるはずで、完了条件にしないほうが測りやすいです。
- 直し方：「コストは小さいが、チケットにする理由は次のとおり」と書き換える。TSK-216 の行は「やること」側に移す。
