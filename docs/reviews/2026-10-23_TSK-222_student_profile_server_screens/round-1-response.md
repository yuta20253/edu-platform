# 第1周の対応(UserProfile / EditUserProfile)

第1周の判定: **直せば進めてよい**

| 指摘 | 重大度 | 対応 | 理由・草案のどこを直したか |
| --- | --- | --- | --- |
| 1. 「通常は到達しない」の根拠が弱い。クライアント遷移では共有レイアウトが再描画されず、ページの `!user` が唯一のガードになりうる | 重要 | 採用 | 背景の書き方を直した。「ほぼ到達しない」を取り下げ、「クライアント遷移では、ページ側が唯一のガードになりうる(推測。Next.js の仕様に基づく)」と書いた。実画面で確かめる方法を未検証表に書いた。確認はオーナーの了承が先なので、勝手には行わない |
| 2. `EditUserProfile` は `getPrefectures()` が `!user` の判定より前にあり、401 のとき `redirect` に届かず例外になる | 重要 | 採用 | コードで確認した(`index.tsx` の順序、`backendFetch` が 401 で例外)。設計に「`!user` の判定を `getPrefectures()` より前に移す(2行の並べ替え)」を入れ、Red のテスト(「null のとき `getPrefectures` が呼ばれない」)と完了条件にした。`getPrefectures` 自体の失敗は別件のまま、「その他」に事実として書いた |
| 3. 5xx でも `/login` に飛ばすデメリットが書かれていない。別件の記録先が決まっていない | 重要 | 採用 | 「利用者に見える変化とデメリット」に、一時障害でもログイン画面に飛ぶことを明記し、許容する理由(親のレイアウトと同じ。Go 移行などで見直すときにまとめて直す)を書いた。記録先は、このチケットの「その他」にした。別チケットにするかは、オーナーに聞く |
| 4. チケットにする価値の判断と、案 D / E が未決のまま | 重要 | 採用 | 「判断: チケットにする」の節を足し、決着させた。実画面の確認の結果にかかわらず価値が残る(親と揃う、`getPrefectures` の順序、`CircularProgress` の除去、許可リストの例外を増やさない)ため、独立したチケットにする。案 D / E は「不採用」にした |
| 5. テストの書き方(`redirect` は例外を投げる実装)が不明 | 軽微 | 採用 | 「やること」に、`next/headers`・`getMeFromBackend`・`getPrefectures` をモックし、`redirect` を「呼ばれたら例外を投げる」モックにして `rejects` で確かめること、`mockReset` で消化漏れを避けることを書いた。Red と回帰防止も区別した |
| 6. 遷移は単体テストで測れず、実画面の確認が完了条件に無い | 軽微 | 採用 | 完了条件に、実画面での確認(Cookie を消して直接開く、クライアント遷移で開く)を足した。オーナーの了承が前提で、行わなければ「未検証」と明記する |

## 本人に確認すべき問い(手順5で聞く)

1. 5xx の一時障害でもログイン画面に飛ばすことを、許容するか(親のレイアウトと揃える)。
2. 実画面の確認(Cookie を消した状態での遷移)を、開発サーバーで行ってよいか。
3. 「/me の 401 と 5xx の区別」「`/me` の二重取得」を、別チケットとして起票するか。
