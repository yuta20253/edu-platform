## 確かめた事実
- **擬似要素の `inherit` は、親（originating element）から値を引き継ぐ**。`::after` の場合、引き継ぐ元はタイトルの `Typography` で、カードではない。タイトルには `borderRadius` が無いので、`borderRadius: "inherit"` は 0 になる。CSS の仕様どおりの動作で、実画面で試すまでもない
- **`sx` の `borderRadius` に数値を渡すと、`theme.shape.borderRadius` を掛けた値になる**。`app/theme/theme.ts`・`studentTheme.ts` とも `shape` を上書きしていないので、既定の 4 が使われる。草案の代わりの書き方「`radius.md` を直接書く」（`radius.md = 14`）は 14×4 = **56px** になる。カードは文字列の `` `${radius.md}px` `` で書いている（`Goals/Presenter.tsx:19`、`studentTheme.ts:17`）。`styleOverrides` の中の数値（`studentTheme.ts:39,52`）は素の CSS なので px になり、混同しやすい
- `studentTheme.ts:15-19` は既に `cardSx`（角丸 `${radius.md}px` を含む）を export している。Home と Goals はそれぞれ自前で同じものを定義している
- **負のマージンの値は妥当**：見出しの `subtitle2` は 14px × 1.57 ≒ 22px（テーマで上書きしていない）。リンクは 44 −（12×2）= 20px で、行の高さ 22px を超えないので、行は伸びない。押せる範囲は行の上下に 11px はみ出すが、見出し行の `mb: 1.5`（12px）に収まり、下の目標カードには重ならない。ただし余裕は 1px しかない。`mx: -1` + `px: 1` で、文字の右端の位置も変わらない
- `globals.css:33` に `a { color: inherit; text-decoration: none; }` があるので、`Box component={Link}` に変えても下線などの見た目は変わらない
- MUI の Chip の root には `position` の指定が無い。DOM ではタイトルより前にあるので、`::after` の下になる（押すとリンクになる）。草案の意図どおり
- **IconButton の横幅**：目標一覧は 30+2+30 = 62px が 44+2+44 = 90px になり、+28px。ホームは +14px

## 残すべき強み
- 背景の表で、各値が「計算値」か「推定」かを書き分けている
- 「見出し行の高さを変えない」ための負のマージンの値が計算で裏付けられている。`::before` 方式を採らない理由（隣の要素と重なる）も書かれている
- `gap` を広げない判断の理由（押し外して詳細へ移る範囲を増やさない）が、利用者への影響と一貫している
- 戻るリンクを外して 1 チケット 1 関心事に絞った判断
- 実画面の確認項目と完了条件が 1 対 1 で対応している

## 指摘（重要な順・最大7個）

### 指摘1【重要】（観点：事実か推測か／失敗の想定）
- 何が問題か：`stretchedLinkSx` の `borderRadius: "inherit"` は 0 になり、フォーカスリングは四角のままになる。代わりの書き方として挙がっている「`radius.md` を直接書く」は、`sx` では 56px の角丸になり、カードより大きく丸まった枠が出る。どちらも第1周の指摘 7 を直せていない
- 根拠：擬似要素は親（タイトル）から値を引き継ぐ。`sx` の数値の `borderRadius` には `theme.shape.borderRadius`（既定の 4）が掛かる（`app/theme/theme.ts` で `shape` は未設定）
- 直し方の提案：`borderRadius: `${radius.md}px`` と文字列で書く。もっと良いのは `borderRadius: cardSx.borderRadius`（`studentTheme.ts` の export を参照する）。これならカードの角丸を変えたときにも一緒に変わる。草案の「`inherit` が効かなければ」という未検証の分岐は消し、未検証の項目からも外す。4-e の確認はそのまま残す

### 指摘2【重要】（観点：完了条件が測れるか／利用者にとってのメリット・デメリット）
- 何が問題か：完了条件「変更前後で、文字の位置のずれが 4px 以内（4-d）」は、IconButton を 44px にすると必ず満たせない。目標一覧では右の列が 28px 広がり、進捗%が 28px 左に動く。タイトル欄も 28px 狭くなって、375px 幅では長いタイトルの折り返しが増え、カードが高くなりうる。ホームでも省略表示（…）になる位置が 14px 早まる。草案は、この見た目の変化を利用者への影響に書いていない
- 根拠：`Goals/Presenter.tsx:135-161`（進捗%と 2 つのボタンが `flex: none` の右の列にある）、`Home/Presenter.tsx:106,136`。幅の計算は「確かめた事実」のとおり
- 直し方の提案：4-d の対象を「見出し行と『目標一覧』リンク」に絞る。IconButton については「右の列が広がり、タイトルの折り返し・省略が増える」を利用者への影響に書く。そのうえで、確認項目に「375px で長いタイトル（例：30 文字）のカードを変更前後で比べる」を足す。なお、ボタンにも負のマージン（`m: "-7px"`）を付けて見た目を保つ案もある。ただしボタンの間隔が 2px しかないので、2 つの押せる範囲が約 12px 重なり、その部分は後ろの削除ボタンが拾う。このため採らないほうがよく、比較した案の表に理由つきで載せることを勧める

### 指摘3【軽微】（観点：失敗の想定）
- 何が問題か：「目標一覧」リンクの押せる範囲は、見出し行の下に 11px はみ出す。下の目標カードまでは 12px で、余裕は 1px しかない。将来 `mb: 1.5` を詰めると、リンクと先頭カードの stretched link の押せる範囲が重なる
- 根拠：上記の計算（`Home/Presenter.tsx:65` の `mb: 1.5`）
- 直し方の提案：大きな対応は要らない。設計 2 に「見出し行の `mb` は 12px 以上を保つ（押せる範囲が 11px はみ出すため）」と一行書くか、実装時にコメントを残す

### 指摘4【軽微】（観点：スコープと依存の切り方）
- 何が問題か：戻るリンクを「別チケットにする」と書いているが、チケットの ID も起票の予定も無い。このまま確定すると、戻るリンクの改善（第1周の背景の 3）がどこにも残らない
- 根拠：草案の「対象外」の欄。Notion に該当するチケットは無い（新規のフローのため）
- 直し方の提案：このチケットを Notion に作るときに、`BackLink` 共通化のチケットも Backlog に起票する（または、起票は `/draft-ticket` を別に回すと明記する）。対象外の欄にはその ID を書く

### 指摘5【軽微】（観点：共通化の方針・規約との整合）
- 何が問題か：`stretchedLinkSx` の置き場所が「`features/student/` の中で、実装時に決める」のままになっている。指摘 1 で `cardSx` と組み合わせることを考えると、置き場所は今決められる
- 根拠：`studentTheme.ts` に、生徒 UI 共通の `cardSx` と `radius` が既にある
- 直し方の提案：`app/theme/studentTheme.ts` の `cardSx` の隣に置き、角丸は `cardSx.borderRadius` を参照する。Home と Goals が自前で持っている `cardSx` を共通のものに置き換えるのは別の関心事なので、このチケットには混ぜない（混ぜないことを一行書いておく）
