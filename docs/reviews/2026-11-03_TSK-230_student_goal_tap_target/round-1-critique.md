# 批判：[Next.js] 生徒の目標一覧・目標詳細への導線のタップ領域を広げる（第1周）

## 総評
目的は具体的で、スマホ前提の生徒画面で効果が見えやすい。代替案の比較も筋が通っている。ただし、数値の前提に誤りがあり、草案どおりの値（`p: 1.25`）では自分の完了条件（44px）を満たせない。テスト計画も、Red と呼べるテストが 1 本もない。

## 判定
直せば進めてよい
（方向は正しい。寸法の計算違い、Red のないテスト計画、レイアウトのずれの扱いの 3 点を直せば、実装して後悔しない設計になる）

## 確かめた事実
- `Home/Presenter.tsx:71`：「目標一覧」は MUI ではない素の `next/link` に `style={{ fontSize: 12 }}` が付いたもの。**`sx` は効かない**ので、草案 2 の `display: inline-flex` などは `style` で書くか、`Box component={Link}` などに置き換える必要がある。草案はこの点に触れていない
- `GoalDetail/Presenter.tsx:49`・`EditGoal/Presenter.tsx:68`：インラインの `<Link>` の中に `Box`（inline-flex、`mb: 2`）がある構造。草案の記述と一致する
- **IconButton の寸法が草案と違う**：MUI 7.3.8 の `IconButton` の `size="small"` は `padding: 5`（`node_modules/@mui/material/IconButton/IconButton.js:136`）。アイコンの `fontSize="small"` は 20px（`SvgIcon.js:70`）。つまり**現状は 30px 四方**で、草案の「約34px」は誤り。草案が提案する `p: 1.25` は 10px なので 20+20=**40px にしかならず、完了条件の 44px を満たさない**。44px にするには `p: 1.5`（12px）が必要
- `ButtonBase` はもとから `position: 'relative'`（`ButtonBase.js:48`）。草案の `position: "relative"` は重複で、意味があるのは `zIndex: 1` だけ（DOM の順でも `::after` より後ろなので、`zIndex` なしでも上に描かれる見込み。推測。実画面で確認できる）
- 草案の「カードにある `overflow` の設定と干渉しないか」について：カード自体に `overflow` は無い。`overflow: hidden` があるのは **ホームのタイトル**（`Home/Presenter.tsx:123`）と目標一覧の進捗バーの枠（`Goals/Presenter.tsx:168`）。`::after` の containing block はカード（タイトルの外）なので、CSS の仕様ではタイトルの `overflow: hidden` で切り取られない。ただし実画面で確かめるべき対象は「カード」ではなく「タイトル」と書き直すべき
- **やることのテストはすべて既存**：`Goals/Presenter.test.tsx:101`（タイトルの href）、`:112`（編集の href）、`:126`（削除で `onDeleteClick`）。`Home/Presenter.test.tsx:72, 89-100` も同じ。つまり草案のテストは現行コードで全部緑になり、Red にならない
- 戻るリンクの `ArrowBackIosNewIcon` を使っている画面は 7 つ（GoalDetail・EditGoal・TaskDetail・EditTask・Unit・AnnouncementDetail・Question）。今回直すのはこのうち 2 つ
- Notion は未確認（新規チケットのため、重複の検索は行っていない）

## 残すべき強み
- 「カード全体を Link で包む」「CardActionArea」「onClick + router.push」「編集・削除を詳細へ移す」の 4 案を比べ、採用しない理由を HTML の妥当性・長押しメニュー・プリフェッチ・スコープで説明できている。TSK-217 の教訓（代替案の比較）がよく活きている
- アクセシブルネームを変えない方針で、スクリーンリーダーの読み上げと既存テストを守っている
- 「jsdom では `::after` の範囲を確かめられない」と明記し、375px での実画面確認と DevTools での実寸計測（前後比較）を計画に入れている。TSK-217 / TSK-222 で当たった種類の対策で、改訂でも消さないでほしい
- 推定値と未検証項目を分けて書いている

## 指摘（重要な順・最大7個）

### 指摘1【重要】（観点：事実か推測か／完了条件が測れるか）
- 何が問題か：IconButton の現状を 34px、`p: 1.25` で 44px になると見積もっているが、実際は現状 30px、`p: 1.25` では 40px になる。草案どおりに実装すると完了条件を満たさず、実画面での計測の段階で手戻りになる
- 根拠：`node_modules/@mui/material/IconButton/IconButton.js:136`（small = padding 5）、`SvgIcon.js:70`（small = 20px）。spacing は 8px
- 直し方の提案：表の 4 を「30px 四方（padding 5px + アイコン 20px。MUI の既定値から計算）」に直す。設計 3 を `sx={{ p: 1.5 }}`（12px×2+20=44px）にする。ほかの推定値（表の 1〜3）も、同じように「計算した値」なのか「当て推量」なのかを分けて書く

### 指摘2【重要】（観点：テスト計画）
- 何が問題か：「テストを先に書く（TDD）」としているが、やること 1〜3 のテストはすべて既存で、現行コードでも緑になる。Red が 1 本もないのに TDD の手順に見えている。これは TSK-224・TSK-215 で当たった指摘と同じ種類
- 根拠：`Goals/Presenter.test.tsx:101,112,126`、`Home/Presenter.test.tsx:72,89-100`
- 直し方の提案：「この変更は CSS だけで、jsdom では Red を作れない。既存テストを特性化テスト（回帰防止）として扱い、検証の本体は実画面の確認」と正直に書く。どうしても単体テストで守りたいなら、「タイトルのリンクに stretched link 用の class/sx が付いていること」「編集・削除が `zIndex` を持つこと」をスタイルの断定で書く手はある。ただし壊れやすいテストになるので、入れないほうを勧める。代わりに、実画面の確認項目（やること 5）を完了条件と 1 対 1 で対応させる

### 指摘3【重要】（観点：利用者にとってのメリット・デメリット／完了条件が測れるか）
- 何が問題か：テキストリンクに `minHeight: 44` を付けると、ホームの「目標」見出し行（h2 は約 22px）と戻るリンク（約 20px）の高さが倍ほどになり、下のコンテンツが約 20px ずれる。草案は戻るリンクの `mb` 調整にしか触れていない。完了条件の「見た目は大きく変わらない」も、何をもって大きくないかが測れない
- 根拠：`Home/Presenter.tsx:60-74`（見出し行は `alignItems: center` の flex。高さは子のうち最大のもので決まる）。戻るリンクは `GoalDetail/Presenter.tsx:49-63`
- 直し方の提案：見た目を変えずに押せる範囲だけ広げる方法を比べて、1 つに決める。(a) 負のマージンで相殺する（`minHeight: 44; my: -1.5` など）、(b) リンクに `position: relative` を付け、`::before` を `inset: -12px` などで外側に広げる。どちらも元の行の高さを保てる。完了条件は「変更前後のスクリーンショット（375px）で、文字の位置のずれが 4px 以内」など測れる形にする。ホームの「目標一覧」は素の `next/link` なので、`style` で書くか `Box component={Link}` に変えるかも設計に書く

### 指摘4【軽微】（観点：失敗の想定）
- 何が問題か：1 ヶ月後に困るとしたら、「目標一覧で削除を押し外して、詳細に移ってしまう」という生徒の声か、「カードに要素（例：締切が近いバッジのボタン）を足したら押せなくなった」という開発側の回帰だと思う。前者は壊れる操作ではないので許容できるが、草案に書かれていない。後者は単体テストで捕まらない
- 根拠：stretched link の `::after` はカード全体（ボタンの隙間も含む）を覆う。草案はボタンの `gap` を広げるので、押し外したときに詳細へ移る領域も増える
- 直し方の提案：利用者のデメリットに「ボタンの隙間・周りを押すと詳細へ移る（以前は何も起きなかった）」と書く。実画面の確認に「削除ボタンの縁を押したとき」を加える。開発向けには、stretched link の sx の横に「カードに操作できる要素を足すときは `position: relative; zIndex: 1` が必要」とコメントを残す（`stretchedLinkSx` を切り出すなら、そこに書けば 1 か所で済む）

### 指摘5【軽微】（観点：スコープと依存の切り方／代替案の比較）
- 何が問題か：戻るリンク 7 画面のうち 2 画面だけを手書きで直すと、TaskDetail の「戻る」（`/goals/:goalId` へ戻る＝目標詳細への導線でもある）などとタップ領域がずれる。後で `BackLink` に共通化するとき、今回の 2 か所も書き直すことになる
- 根拠：`grep ArrowBackIosNewIcon` で 7 ファイル。`TaskDetail/Presenter.tsx:21`
- 直し方の提案：次のどちらかに決めて、理由を書く。(A) このチケットからは戻るリンクを外し、「目標カードと IconButton と『目標一覧』リンク」に絞る。戻るリンクは `BackLink` 共通化のチケットで 7 画面まとめて直す（1 チケット 1 関心事になり、手戻りもない）。(B) このまま 2 か所を直すなら、対象外の欄に「TaskDetail の目標詳細へ戻るリンクも対象外」と明記する。批判役としては (A) を勧める

### 指摘6【軽微】（観点：事実か推測か）
- 何が問題か：未検証の項目「カードにある `overflow` の設定と干渉しないか」は、確かめる対象がずれている。カードに `overflow` は無く、あるのはホームのタイトル（ellipsis 用）
- 根拠：`Home/Presenter.tsx:123`、`Goals/Presenter.tsx:97`（カードの sx に overflow なし）
- 直し方の提案：「ホームのタイトルの `overflow: hidden`（省略表示）が `::after` を切り取らないか」に書き直す。仕様上は切り取られない見込み（containing block がカードのため）だが、実画面で確かめる

### 指摘7【軽微】（観点：利用者にとってのメリット・デメリット）
- 何が問題か：フォーカスリングを `::after`（`inset: 0`）に出すと、角丸のカードに四角い枠が出る。タイトル自身のフォーカスリングと二重になる可能性もある
- 根拠：カードは `borderRadius: radius.md`（`Goals/Presenter.tsx:19`）。`::after` は角丸を継承しない
- 直し方の提案：`::after` に同じ `borderRadius` を付ける。タイトル側の既定の outline は `&:focus-visible { outline: none }` で消すと設計に書く
