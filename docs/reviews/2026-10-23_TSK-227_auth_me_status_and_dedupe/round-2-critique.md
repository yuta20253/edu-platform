## 確かめた事実
- `me.ts` を読みました。
  - 現状は 401・`!ok`・壊れた JSON のどれでも `null` を返します。
  - `fetch` に try/catch が無いので、通信失敗はすでに例外です。
  - 草案の記述と一致します。
- 呼び出し元の `try/catch` を確認しました。**`try/catch` で `null` を期待している箇所は 0 件です。**
  - `account-link/page.tsx` は `me?.account_linked`、`admins/[adminId]/page.tsx` は `me?.id ?? null` です。どちらも optional chaining だけで、`try/catch` はありません。
  - 3つのレイアウトも `!user` の分岐だけです。
  - `UserProfile` / `EditUserProfile` は、現状では `!user` のときスピナーを返します。TSK-222 が `redirect` に変えます。
  - 例外に変えても、例外はそのまま伝わり、レイアウト側の分岐は影響を受けません。
- `error.tsx` の位置を確かめました。
  - `app/(main)/layout.tsx` は同期の関数で、`ThemeProvider` と `Footer` を持ちます。例外を投げません。
  - `(main)/error.tsx` はその内側に入ります。レイアウトの例外は、1つ上の境界で受けられます。
  - したがって、エラー画面でも MUI のテーマとフッターは残ります。「サイドバーが出ない」のは教員と管理者だけです。生徒の `(authenticated)` レイアウトはサイドバーを持たず、フッターは `(main)/layout.tsx` にあります。
  - **草案は生徒でもサイドバーが消えるように読めるので、ロール別に書き分けてください。**
  - `(teacher)/layout.tsx` と `(admin)/layout.tsx` も存在します。`teacher/error.tsx` と `admin/error.tsx` はその内側に入るので、成立します。
- `redirect()` の扱い：`redirect()` が投げる `NEXT_REDIRECT` は error boundary には捕まりません。401 のログイン遷移は影響を受けません。
- Next は 15.5.4 です。`startTransition(() => { router.refresh(); reset(); })` は、公式が勧める定番の形です。

## 指摘（重要な順）

### 指摘1【重要】（観点：テスト計画）
- 何が問題か：Red の「レイアウト: `getMeFromBackend` が例外を投げたとき、`/login` に `redirect` せず例外がそのまま伝わる」は、**現行コードでも通ります**。
  - レイアウトには `try/catch` が無く、モックが reject すれば、そのまま `await Layout()` も reject します。
  - 現行で通るなら、これは回帰防止です。Red ではありません（TSK-211 の教訓の類型）。
- 根拠：3つのレイアウトのコード。例外の握りつぶしはありません。
- 直し方の提案：
  - この項目は「回帰防止」の欄に移してください。
  - Red は `me.ts` の 500・壊れた JSON と、共通エラー表示（新規ファイルなのでインポートが失敗する）の2種に絞ります。
  - 「障害のときに `redirect` が0回」を本当に確かめるには、`me.ts` から `fetch` までを通す結合寄りのテストが要ります。500 の `fetch` モックでレイアウトを呼び、reject と `redirect` 0回を確かめます。モックの階層を草案に書いてください。

### 指摘2【重要】（観点：事実か推測か）
- 何が問題か：背景に「レイアウトとページが同じ `/me` を2回取っている」と事実のように書いてありますが、「検証済みの前提」の表にも「未検証の前提」の表にもありません。
  - Next.js には fetch のリクエスト・メモ化があります。同じレンダリングの中で、同じ URL・同じオプション・同じヘッダーの GET はまとめられる見込みです（推測。`cache: "no-store"` を指定していてもメモ化の対象と理解しています）。
  - すでに共有されている可能性があります。その場合、`cache()` は何も変えません。
  - 「実験は `cache()` を入れてから fetch の数を数える」と読めます。**入れる前の数が基準になっていません。**
- 根拠：`me.ts` は `cookieHeader` を `Cookie` ヘッダーに入れた GET で、レイアウトとページから同じ引数で呼ばれます。TSK-217 の教訓（前提が未検証）と同じ形です。
- 直し方の提案：
  - 実験は2段にしてください。(1) `cache()` なしで、バックエンド側の `/api/v1/me` のログ（Rails のログ）を数えます。(2) 2回なら、`cache()` ありで数え直します。
  - (1) が1回なら、`cache()` と案 B・C の議論はチケットごと不要です。その場合、チケットのタイトルから「二重取得を解消する」を外してください。

### 指摘3【重要】（観点：スコープ／規約との整合）
- 何が問題か：
  - **(a) 影響範囲：** `(main)/error.tsx` は `/me` 以外の例外もすべて受けます。`/login`・`signup`・`password` の例外、`getPrefectures` の失敗なども同じ画面になります。草案は「境界が広がるだけで害は無い」と書いていますが、利用者に見える変化なので、デメリット欄に書いてください。
  - **(b) 規約：** 文言を「固定文（『読み込みに失敗しました』など）」と書いています。`frontend/CLAUDE.md` の規約4は文言の直書きを避け、`ErrorState` の初期値を使うことを求めています。`ErrorState` の初期値「データの取得に失敗しました」を使うか、メッセージを変える理由を書いてください。
  - **(c) 契約の例外：** 403 や 404 も例外になる点を書いてください。
- 直し方の提案：上の3点を草案に1行ずつ足してください。

### 指摘4【軽微】（観点：完了条件が測れるか）
- 何が問題か：完了条件「呼び出し元7か所が変更後も動く（`grep` で確かめる）」は測れません。`grep` は `!user` の有無しか分かりません。
- 直し方の提案：「`!user` の分岐を残した7か所で、`null` を返すモックの回帰テストが通る」など、テストで測れる形にしてください。実際に必要なのは3レイアウトのテストです。ページ側は、`null` のときの挙動を変えていません。

### 指摘5【軽微】（観点：失敗の想定）
- 何が問題か：エラー画面に出口が再試行しか無く、障害が続くとき、利用者は再試行を繰り返すしかありません。本番の `error.message` は伏せられ、`digest` だけが渡ります。サーバーのログと突き合わせられるよう、`MeFetchError` に HTTP ステータス（通信失敗では原因）を持たせると、障害の調査がしやすくなります。
- 直し方の提案：`MeFetchError` にステータスを持たせる、と1行書いてください。ログイン画面へのリンクを置くかは、オーナーの判断です（置かなくても進められます）。
