# 批判：getMeFromBackend の 401/5xx 区別と /me 二重取得の解消（第1周）

## 総評
直す価値のある問題（一時障害でログイン画面に飛ばされる）を正しくつかんでいます。ただし次の 3 点が弱いです。(a) 設計の中心である `error.tsx` の置き場所が Next.js の仕様と合っていません。(b) 戻り値を 3 値にすると、TSK-222 のコードが警告なしで壊れる恐れがあります。(c) 呼び出し元の数など事実の誤りがあります。もっと小さい代替案（後述）があるのに比べられていません。

## 判定
**直せば進めてよい**。問題の捉え方は正しい。ただし設計の核（`error.tsx` の位置、戻り値の形）を直さないと、書いたとおりには動かないか、TSK-222 と衝突します。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒・教員・管理者） | バックエンドが一時的に 5xx のとき、ログイン済みの全ロールがログイン画面に飛ばされず、再読み込みの案内を見られる。入り直しても同じ失敗が続く状況がなくなる。 | 5xx のとき、これまでの「ログイン画面」が「エラー画面」に変わる。`error.tsx` を置く位置次第でサイドバーが消える。本番ではエラーの文言が伏せられる。`reset` だけでは Server Component が再取得されない（指摘 2）。 |
| 開発チーム | 401 と障害を区別できるようになり、Go 移行後も同じ契約で使える。`/me` の取得が 1 回に減る。 | 3 値化すると 7 か所が書き換わり、TSK-222 とファイルが重なる。`error.tsx` を 3 か所に足すことになる。`cache()` の単体テストは作りにくい。 |

- 両方にメリットがあるか：**ある**。ただし利用者側のメリットは、障害時のみ起きる一点に限られる。二重取得の解消は利用者にはほぼ見えない（レイアウトとページは並列に取得するため待ち時間はあまり変わらない。推測）。これは開発側のメリットとして扱うべき。
- やらないことのデメリット：
  - 利用者が失うもの：障害のたびにログイン画面に飛ばされる。頻度は未確認（草案も推測と書いている）。1 校規模ならまれな可能性が高い。
  - 開発チームが失うもの：TSK-222 で「許容」とした挙動が残り続ける。Go 移行のときに認証まわりを見直すので、その時にまとめる案 D も成り立つ。ただし D を「放置」と退けるなら、頻度の根拠が要る。
- 草案に無いデメリット：
  - `{status:"unauthorized"}` は真値なので、`if (!user)` が常に false になる（指摘 1）。
  - 本番の Server Component の例外はメッセージが伏せられ、`digest` だけが渡る。
  - `error.tsx` はクライアントコンポーネントでなければならない。

## 確かめた事実
- **呼び出し元は 7 か所で、8 か所ではありません。** `grep -rn getMeFromBackend frontend` の結果は次の 7 件です。生徒レイアウト、`account-link/page.tsx`、教員レイアウト、管理者レイアウト、`admins/[adminId]/page.tsx`、`UserProfile`、`EditUserProfile`。草案の列挙も 7 件で、数字だけが違います。完了条件「8 か所を grep で確かめる」は直してください。
- **未検証の前提（1）は確認できました。** 教員・管理者のレイアウトも `!user` で `/login` に `redirect` します。ただし生徒と違う点が 2 つあります。
  - 教員は `!user || user.user_role?.name !== "teacher"`、管理者は `"admin"` も条件に入っています。ロール違いは 401 でも 5xx でもないのに `/login` に飛びます。この分岐は今回のチケットでは変えない、と草案に明記してください。`unauthorized` と混ぜないよう注意が要ります。
  - 教員・管理者のレイアウトは UI（サイドバー）を持ちます。`error.tsx` の置き場所次第で、エラー時にサイドバーが出るか消えるかが変わります。
- **`me.ts` の現状と草案の食い違い：**
  - ネットワークエラーのとき `fetch` は reject します。`.catch` は JSON 解析にしか付いていないので、`null` は返らず、すでに例外になります。草案の「ネットワークエラー → `error`」は新規の挙動ではなく、現状は Next.js の既定のエラー画面です。
  - 200 でも JSON が壊れていれば `null` になり、ログイン画面へ飛びます。これも `error` 側に寄せる決定が必要です。
- `app/` に `error.tsx`・`global-error.tsx`・`middleware.ts`・`proxy.ts` はありません（確認済み）。

## 残すべき強み
- 問題の再現手順と、実画面での確認を完了条件に入れていること。
- 未検証の前提を表に分けて、確かめ方まで書いていること（TSK-217 の教訓が生きています）。
- 401 は従来どおり `/login` に飛ばす、と回帰防止の Red に入れていること。
- 案 E を退けた理由（Server Component は `ErrorState` の `onRetry` を持てない）は妥当です。
- TSK-222 との関係を隠さず書いていること。

## 指摘

### 指摘1【致命的】（観点：失敗の想定／規模・依存）
- 何が問題か：
  - 戻り値を `{status, user}` に変えると、TSK-222 が先にマージされた場合、UserProfile／EditUserProfile／既存コードの `if (!user) redirect(...)` が常に false になります。型エラーが出ない書き方だと、未ログインでも画面が描画されて `user.xxx` で落ちます。
  - 草案は「呼び出しの形は変えない」と言いますが、戻り値の型を変えれば呼び出しの形も変わります。この記述は矛盾しています。
- 根拠：`me.ts` の戻り値は `MeUser | null`。7 か所すべてが `!user` 型の分岐です（レイアウト 3 件を確認）。
- 直し方の提案（**比較されていない案 F を推奨**）：
  - **案 F：戻り値の型は `MeUser | null` のまま。401 だけ `null`、5xx・ネットワーク失敗・JSON 失敗は例外を投げる。**
  - 7 か所の呼び出し元はほぼ無改修で済みます（`!user` は「未ログイン」だけの意味になる）。TSK-222 の実装とも衝突しません。変更は `me.ts` と `error.tsx` が中心です。
  - Go 移行後も「401 は null、障害は throw」という契約はそのまま引き継げます。
  - 3 値化を選ぶなら、関数名を変える（例：`getMeResult`）か、判別共用体を使って旧名を削除し、typecheck で全箇所を強制的に拾う形にしてください。TSK-222 のマージ順は「TSK-222 を先」と固定してください。
  - 案 F を比較表に加えてください。

### 指摘2【致命的】（観点：設計が成立するか）
- 何が問題か：
  - **「各ロールの `(authenticated)` 配下に `error.tsx` を置く」は、レイアウトが投げた例外を捕まえません。** `error.tsx` は同じセグメントの `layout` の子として働きます。
  - 今回の 5xx の大半は layout の `getMeFromBackend` で起きます。そのため `(authenticated)/error.tsx` には届かず、上位の境界か既定のエラー画面に落ちます。
  - つまり、完了条件「5xx のとき `error.tsx` の再読み込みの案内が出る」は、書いたとおりでは満たされません。
- 根拠：Next.js の error boundary の仕様（草案もこの点は問うています）。`app/` に `error.tsx` が 1 つも無いことを確認済み。推測の余地はありますが、仕様上はこの理解で合っています。
- 直し方の提案：
  - 置き場所は、レイアウトの**1 つ上**のセグメントにします。
    - 生徒：`app/(main)/error.tsx`（`(authenticated)` の親。ログイン画面などの子も同じ境界に入る）。
    - 教員：`app/(teacher)/teacher/error.tsx`。
    - 管理者：`app/(admin)/admin/error.tsx`。
    - 3 ロールに同じ文言の `error.tsx` を 3 つ置くより、共通の中身コンポーネントを 1 つ作り（`ErrorState` を使う）、各 `error.tsx` はそれを呼ぶだけにします。
  - この位置だとレイアウトのサイドバーごと置き換わるので、エラー画面にはサイドバーが出ません。それでよいか、オーナーに確認してください。許容できないなら、`getMeFromBackend` を呼ぶ処理を layout の子コンポーネントに移し、`(authenticated)/error.tsx` の内側で例外を起こす構成にします（その場合サイドバー自体が出せないのは同じなので、通常は許容でよい）。
  - `reset()` は、Server Component の再取得をしません。`router.refresh()` と `startTransition` の中で `reset()` を呼ぶ形が必要です。これを入れないと「再試行しても直らない」エラー画面になります。この挙動を単体テストと実画面の確認項目に入れてください。
  - 本番ではエラーメッセージが伏せられ、`digest` だけが渡ります。文言は `error.message` に頼らず固定文にしてください。
  - 完了条件の実画面確認は「バックエンドを止める」だけでなく、「レイアウトの例外でもページの例外でも、案内が出て、再試行で復帰する」まで書いてください。オーナーの了承待ちにせず、実装前に最小の再現（`throw` を一時的に入れる）で、境界の位置だけ先に確かめるのが安上がりです。

### 指摘3【重要】（観点：事実か推測か）
- 何が問題か：`cache()` の共有を「推測」と置いたのは誠実です。ただし、確かめ方の「単体テスト」は成立しにくいです。
- 根拠：
  - React の `cache()` はサーバーのレンダリング環境でだけ有効です。vitest／jest の通常環境では、おそらく毎回呼び出されて共有されません（推測。テストで確認できます）。「同じ Cookie で 2 回呼んで `fetch` が 1 回」の単体テストは、Red にも Green にもならない可能性があります。
  - 一方、同じレンダリングの中で、レイアウトとページが共有することは仕様上期待できます。ただし、キャッシュのキーは引数の同一性なので、`cookieHeader` が文字列（プリミティブ）であることが前提です。今の形は満たしています。
  - Route Handler や Server Action の呼び出しでは共有されません。今回の 7 か所はすべて Server Component なので影響はありません。
- 直し方の提案：
  - 単体テストでは `cache` をモックするか、テスト対象から外します。「`fetch` が 1 回」の確認は、実画面（サーバーのログか `/api/v1/me` の呼び出し回数）に一本化します。
  - 先に最小の実験（レイアウトとページに `console.log`）で共有を確かめてください。実装前にできます。
  - 共有されなかった場合に、案 B 相当（区別のみ）で出荷できるよう、`cache()` の部分は別コミットにしてください。

### 指摘4【重要】（観点：スコープと依存／規模）
- 何が問題か：「ロール別にコミットを分ける」と書いていますが、変更の本体は `me.ts` 1 つ、`error.tsx` 3 か所、呼び出し元 7 か所で、案 F なら 1 PR で十分に収まります。3 値化を選ぶと呼び出し元 7 か所が全部変わります。
- 根拠：7 か所のうち 2 か所（`UserProfile`・`EditUserProfile`）は TSK-222 が触るファイルです。他に 5 か所は他のチケットと重ならない見込みです（推測）。
- 直し方の提案：
  - 案 F なら 1 PR で良いです。ただし二重取得の解消（`cache()`）は、利用者に見えない内部整理で、実画面で効果を確かめる必要があるので、**別コミット（できれば別 PR）**にして、独立に戻せるようにしてください。
  - 案 B の不採用理由「同じ 8 か所を 2 回触る」は、案 F と `cache()` なら触るのは `me.ts` だけで、理由として成り立ちません。比較表を直してください。
  - 3 値化を選ぶ場合は「型の変更＋生徒 → 教員 → 管理者」でもよいが、途中のコミットで全箇所が typecheck を通る順序にしてください（旧名と新名の併存）。

### 指摘5【重要】（観点：利用者のメリット／やらないこと）
- 何が問題か：利用者のメリットは「障害のときだけ」で、頻度の根拠が無い一方、デメリット（エラー画面の見た目の変化、サイドバーの有無）が書かれていません。二重取得の解消は利用者に見えるメリットとして書くべきではありません。
- 根拠：草案「未検証の前提」の 2 行目（頻度は推測）。レイアウトとページの並列取得は、待ち時間をほとんど変えないと見られる（推測）。
- 直し方の提案：
  - 「利用者に見える変化」に、エラー画面でサイドバーが出るか否か、本番の文言、`reset` の挙動を足してください。
  - 二重取得の解消は「開発側のメリット（Rails への `/me` の負荷が半減する）」と明記し、利用者のメリットとは分けてください。
  - 案 D（Go 移行時にまとめる）を退ける理由は、「頻度は不明だが、案 F なら変更量が小さいので今やっても損がない」に変えるほうが正直です。

### 指摘6【軽微】（観点：移行計画との整合）
- 何が問題か：「Go 移行で引き継げる」とあるが、何が契約か書かれていません。ロール違いで `/login` に飛ぶ分岐は Rails／Go どちらでも同じ扱いにできるかが不明です。
- 直し方の提案：契約を 1 行で書いてください。「`/me` が 401 なら未ログイン、それ以外の失敗は障害、200 なら `user`」。`error.tsx` と `cache()` は Workers でも動きます（推測）。Cloudflare に載せる際は `cache()` の効果を再確認してください。

### 指摘7【軽微】（観点：テスト計画）
- 何が問題か：Red の「レイアウトが `error` のとき例外を投げる」は、Server Component の非同期レイアウトを単体テストで呼ぶ形（`await Layout({children})`）になります。`redirect` のモックの漏れ（未消化の `mockResolvedValueOnce`）に注意が必要です。また、「`error` のとき `/login` に飛ばない」を、`redirect` が呼ばれないことで確かめる Red は、例外を投げないと失敗しない書き方にしてください（`expect(...).rejects` と `redirect` の呼び出し 0 回の両方）。
- 直し方の提案：テストの前に `vi.resetAllMocks()`（または `mockReset`）を入れる。ネットワークエラー（`fetch` が reject）と、200 で壊れた JSON のケースも Red に足してください。

4. 実画面での確認（`cache()` の共有、`error.tsx` の境界、`reset` の挙動）に、開発サーバーとバックエンドの停止を使ってよいか。
5. 200 で壊れた JSON は「障害」として扱ってよいか（今はログイン画面へ飛ぶ）。
