# 批判：getMeFromBackend の 401/障害の区別（第3周・最終）

## 前回の指摘の扱いの確認
`libs/server/me.ts`、3つのレイアウト、`(main)`・`(teacher)`・`(admin)` の各 `layout.tsx`、`components/ui/ErrorState.tsx` を開いて確かめました。
- Red と回帰防止の振り分け：**直った**。500 と壊れた JSON は現行で `null` を返すので Red のままです。レイアウトの reject と結合寄りのテストは、現行でも通るので回帰防止の欄に移っています。
- 二重取得を未検証にして2段で実験：**直った**。背景、未検証の表、やることの3か所がそろっています。
- デメリット・規約4・403/404：**直った**。
  - `ErrorState` の初期値は「データの取得に失敗しました」で、草案の記述と一致します。
  - `(main)` の下には `login`・`signup`・`password` があります。`(teacher)/teacher` には `signup`、`(admin)/admin` にも `signup` があります。
  - `/me` 以外の例外も同じ画面になる、という記述は事実です。
- 完了条件：**ほぼ直った**。ただし下の指摘1が残ります。
- MeFetchError のステータス：**直った**。
- 生徒ではサイドバーが消えない：**直った**。
  - 生徒の `(authenticated)/layout.tsx` は `<>{children}</>` を返すだけです。
  - 教員のサイドバーは `(authenticated)/layout.tsx` 内の `TeacherSidebar` です。管理者も同じ構成のはずですが、私は管理者側のレイアウトを開いていません。
  - 外側の `(main)/layout.tsx` が持つのは `ThemeProvider`・`ToastProvider`・`Footer` です。`(teacher)/layout.tsx` と `(admin)/layout.tsx` が持つのは `ThemeProvider` などです。これらは同期のレイアウトで、例外を投げません。
  - よって `error.tsx` の配置位置は成立します。

## 総評
設計の核（案 F、`error.tsx` を1つ上に置く）は実コードと整合しています。第2周の指摘は漏れなく直っており、新しい致命的な欠陥はありません。残るのは、実験を任意にしてしまっている点と、細かい軽微な点です。

## 判定
**直せば進めてよい**。理由は、設計の成立を決める実験が「オーナーの了承しだい」で飛ばせる書き方になっているためです。それ以外は軽微です。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者 | 一時障害のとき、ログイン画面に飛ばされず、再試行の案内を見られる | 教員・管理者はサイドバーなしの画面になる。`login`・`signup`・`password` などの例外も同じ画面になる。403・404 もエラー画面になる |
| 開発チーム | 呼び出し元が無改修。契約が Go 移行後も引き継げる | `error.tsx` が3つ増える。`cache()` の効果は単体テストで測れない |

- 両方にメリットがあるか：**ある**。利用者のメリットは障害時だけで、頻度は不明です。変更が小さいので許容できます。
- やらないことのデメリット：
  - 利用者が失うもの：一時障害のたびにログイン画面へ飛ばされます。
  - 開発チームが失うもの：401 と障害を区別できないままになります。
- 草案に無いデメリット：指摘3を参照してください。

## 確かめた事実
- `me.ts` は 401・`!ok`・壊れた JSON を `null` にしています。`fetch` に try/catch は無いので、通信失敗はすでに例外です。草案と一致します。
- `getMeFromBackend` を import しているファイルは、`me.ts` 以外に5つです（3レイアウト、`account-link`、`admins/[adminId]`）。草案の「7か所」は、まだマージされていない TSK-222 の2画面を含めた数で、矛盾はありません。
- ログイン画面は `getMeFromBackend` を呼びません。ログイン画面自体が `/me` の障害で壊れることはありません。
- 教員のレイアウトは `!user || role !== "teacher"` の1分岐です。草案が「ロール不一致は変えない」と書いているのは事実どおりです。

## 残すべき強み
- 案 F：型を変えず、障害だけを例外にします。
- 案 A（3値化）の不採用理由：`if (!user)` が壊れるため。
- `error.tsx` を `(authenticated)` の1つ上に置くこと。
- 契約の1行化。
- 別コミットにした `cache()`。
- Red と回帰防止の区別。
- 未検証の前提を表にして、確かめ方を添えていること。

## 指摘

### 指摘1【重要】（観点：5 事実か推測か・11 完了条件）
- 何が問題か：設計の成否を決める2つの前提があります。「レイアウトの例外を1つ上の `error.tsx` が受ける」ことと、「再試行で復帰する」ことです。これらを確かめる実験が、「オーナーの了承を得て」の任意扱いになっています。完了条件にも「行わなかった場合は未検証と明記」とあり、未検証のままマージできる書き方です。
- 根拠：TSK-217 の教訓です。未検証の前提から設計し、実画面で外れました。単体テストは `error.tsx` の境界を再現できません。ユニットで緑でも、本番で効かない可能性が残ります。
- 直し方：境界の実験だけは「マージの前提条件」にします。実験で `throw` を入れて、`error.tsx` が受けることと、再試行で復帰することを確かめます。二重取得の実験（`cache()` 側）は任意のままで構いません。オーナーの了承が得られなければ、チケットをブロックします。

### 指摘2【軽微】（観点：10 テスト計画）
- 何が問題か：結合寄りテストは、`me.ts` の `import "server-only"` を vitest で扱う手当てが書かれていません。ほかのサーバー側のテストと同じ方法（`vi.mock("server-only")` など）の確認が要ります。
- 根拠：推測（`me.ts` 冒頭の `import "server-only"` と、既存のテスト設定を確かめていません）。
- 直し方：既存のサーバー側テストでの扱いを確認して、1行で書き添えます。

### 指摘3【軽微】（観点：1 利用者のデメリット）
- 何が問題か：`ErrorState` の初期値「データの取得に失敗しました」は、認証まわりの障害を表すには曖昧です。管理者が `signup` などで例外に当たると、文言とずれます。
- 根拠：`ErrorState.tsx` の初期値。
- 直し方：規約4を守りつつ、`ErrorState` の初期値で十分かをオーナーに聞きます（下の問い2）。

### 指摘4【軽微】（観点：6 対策の重複）
- 何が問題か：`startTransition(() => { router.refresh(); reset(); })` の呼び出し順は、実験で確かめる前提です。草案は設計欄に断定で書いています。
- 直し方：設計欄に「実験で確認後に確定」と一言添えます。
