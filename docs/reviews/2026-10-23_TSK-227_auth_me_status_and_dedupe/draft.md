## 概要

サーバー側の `getMeFromBackend`(`/api/v1/me` の取得)が、401(未ログイン)と、障害(5xx・通信失敗・壊れた JSON)を区別していない。そのため、バックエンドの一時障害のときも、レイアウトとページが利用者を**ログイン画面に飛ばす**。

戻り値の型は `MeUser | null` のまま変えず、**401 のときだけ `null`、障害のときは例外を投げる**ようにする。例外は、レイアウトの1つ上のセグメントに置く `error.tsx` で受け、ログイン画面ではなく、再読み込みの案内を出す。あわせて、同じ `/me` をレイアウトとページで2回取っているかを**先に実験で確かめ**、2回取っていれば `cache()` で1リクエスト内に共有する(別コミットにする)。1回なら、二重取得はスコープから外す。

TSK-222(UserProfile・EditUserProfile)で「別件として記録する」とした件。

## 背景(調査結果)

- `getMeFromBackend` は、`response.status === 401` でも `!response.ok` でも `null` を返す。200 でも JSON が壊れていれば `null` を返す(`.json().catch(() => null)`)。**通信失敗(`fetch` の reject)は、すでに例外になる**(`fetch` に try/catch が無いため)。
- 呼び出し元は**7か所**。いずれも `!user` の分岐で、`null` を「未ログイン」として扱う。
  - レイアウト: 生徒 `app/(main)/(authenticated)/layout.tsx`、教員 `app/(teacher)/teacher/(authenticated)/layout.tsx`、管理者 `app/(admin)/admin/(authenticated)/layout.tsx`
  - ページ・画面: `account-link/page.tsx`、`admin/.../admins/[adminId]/page.tsx`、生徒の `UserProfile` / `EditUserProfile`(TSK-222 が `!user` を `redirect("/login")` にする)
- 教員・管理者のレイアウトは、`!user` に加えて、**ロールの不一致**(教員は `user_role?.name !== "teacher"`、管理者は `"admin"`)でも `/login` に `redirect` する。ロールの不一致は、401 でも障害でもない。
- したがって、バックエンドが一時的に 5xx を返すと、ログイン済みの利用者が**ログイン画面に飛ばされる**。ログイン画面から入り直しても、同じ失敗が続くことがある。
- 生徒のプロフィール画面などでは、レイアウトとページが同じ `/me` を呼んでいる。**実際に2回の HTTP が出るかは未検証**(Next.js の fetch のリクエスト・メモ化で、すでに1回にまとまっている可能性がある)。
- `app/` に `error.tsx`・`global-error.tsx`・`middleware.ts` が無い。サーバー側の例外は Next.js の既定のエラー画面になる。
- Next.js の `error.tsx` は、同じセグメントの `layout` の**子**として働く。そのため、`(authenticated)/layout.tsx` が投げた例外は、`(authenticated)/error.tsx` では受けられず、**1つ上のセグメントの `error.tsx`** が受ける。

## 設計(案 F)

### `libs/server/me.ts`

- **戻り値の型は `MeUser | null` のまま**にする。
  - `401` → `null`(未ログイン)。
  - `!ok`(5xx など)、200 で壊れた JSON → **例外**(`MeFetchError` など、障害だと分かる型)を投げる。
  - 通信失敗(`fetch` の reject)は、現状どおり例外。
  - **403・404 なども 401 以外なので障害（例外）になる**（例: `API_ORIGIN` の設定ミスでもログイン画面ではなくエラー画面になる）。契約の帰結として受け入れる。
  - `MeFetchError` に **HTTP ステータス**（通信失敗では原因）を持たせる。本番ではメッセージが伏せられ `digest` だけが渡るので、サーバーのログとの突き合わせに使う。
- 契約(Go 移行後も引き継ぐ): **「`/me` が 401 なら未ログイン(`null`)。それ以外の失敗は障害(例外)。200 なら `user`」。**
- 7か所の呼び出し元は、**ほぼ無改修**(`!user` は「未ログイン」だけの意味になる)。TSK-222 の実装とも衝突しない。
- 教員・管理者のレイアウトの**ロール不一致で `/login` に飛ばす分岐は、変えない**(401 でも障害でもなく、別の扱い)。

### `error.tsx`(レイアウトの1つ上のセグメント)

- 置き場所: 生徒 `app/(main)/error.tsx`、教員 `app/(teacher)/teacher/error.tsx`、管理者 `app/(admin)/admin/error.tsx`。`(main)` の下には `login`・`signup`・`password` もあり、**`/me` 以外の未処理の例外（`getPrefectures` の失敗など）も同じ画面になる**。これは利用者に見える変化なので、下のデメリットに書く。
- 中身は、共通のクライアントコンポーネント1つ(`ErrorState` を使う)にし、各 `error.tsx` はそれを呼ぶだけにする。
  - 文言は `ErrorState` の初期値（「データの取得に失敗しました」。`frontend/CLAUDE.md` 規約4）を使い、文言を直書きしない。本番ではエラーのメッセージが伏せられ、`digest` だけが渡るので、`error.message` に頼らない。
  - 再試行は、`startTransition(() => { router.refresh(); reset(); })`（呼び出し順は境界の実験で確認して確定する）。`reset()` だけでは Server Component が再取得されないため。
- この位置だと、レイアウトごと置き換わる。**教員・管理者のエラー画面にはサイドバーが出ない**。生徒の `(authenticated)` レイアウトはサイドバーを持たず、MUI テーマとフッターは `(main)/layout.tsx` にあるので残る(サイドバー自体が `/me` の結果に依存するので許容。オーナー確認済み)。

### `cache()`(別コミット)

- `getMeFromBackend` を React の `cache()` で包み、同じリクエストの中で、同じ Cookie の `/me` の取得を1回にする(キーは `cookieHeader` の文字列)。
- **利用者には見えない内部整理**であり、開発側のメリット(Rails への `/me` の負荷が半減する)として扱う。レイアウトとページは並列に取得するので、利用者の待ち時間はほぼ変わらない見込み(推測)。
- 共有されなかった場合に、`cache()` を外しても出荷できるよう、**別コミット(できれば別 PR)**にする。

### 利用者に見える変化とデメリット

- メリット: バックエンドの一時障害のとき、ログイン済みの利用者(生徒・教員・管理者)が、ログイン画面に飛ばされず、再読み込みの案内を見られる。
- デメリット: 一時障害のとき、これまでの「ログイン画面」が「エラー画面(教員・管理者はサイドバー無し)」に変わる。障害が続くと出口は再試行だけ（ログイン画面へのリンクは置かない。オーナー決定済み）。`(main)/error.tsx` は `login`・`signup`・`password` の例外や `/me` 以外の例外も受ける。403・404 もエラー画面になる。
- 401(未ログイン)のときは、これまでどおりログイン画面に遷移する。

## 比較した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| F: 戻り値は `MeUser \| null` のまま、障害は例外 | 採用 | 呼び出し元7か所がほぼ無改修で、TSK-222 と衝突しない。変更は `me.ts` と `error.tsx` が中心。Go 移行後も「401 は null、障害は throw」の契約をそのまま引き継げる |
| A: 戻り値を3つ(`ok` / `unauthorized` / `error`)に区別する | 不採用 | `{ status: "unauthorized" }` は真値なので、既存の `if (!user)` が常に false になる。型エラーが出ない書き方だと、未ログインでも画面が描画されて落ちる。7か所すべてを書き換える必要があり、TSK-222 とファイルが重なる |
| B: 区別だけ行い、二重取得は直さない | 不採用 | 案 F では、`cache()` は `me.ts` だけの変更で済む。分ける理由が無い(別コミットにはする) |
| C: 二重取得だけ直す(`cache()`)で、区別はしない | 不採用 | 利用者の不具合(一時障害でログイン画面に飛ぶ)が直らない |
| D: Go 移行のときにまとめて直す | 不採用 | 頻度は不明だが、案 F は変更量が小さいので、今やっても損がない。移行時の見直しにも、契約がそのまま引き継げる |
| E: 障害のとき、各ページが個別に `ErrorState` を出す | 不採用 | サーバーコンポーネントは `ErrorState` の再試行(クライアントの `onClick`)を直接持てない |
| G: `(authenticated)/error.tsx` に置く | 不採用 | レイアウトが投げた例外は、同じセグメントの `error.tsx` では受けられない |
