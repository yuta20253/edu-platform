# 第1周の対応(/me の 401 と障害の区別)

第1周の判定: **直せば進めてよい**

| 指摘 | 重大度 | 対応 | 理由・草案のどこを直したか |
| --- | --- | --- | --- |
| 1. 戻り値を3値にすると、`{ status: "unauthorized" }` が真値になり、既存の `if (!user)` が常に false になる。TSK-222 と衝突する | 致命的 | 採用 | 設計を**案 F**に全面的に変えた: 戻り値は `MeUser \| null` のまま、401 だけ `null`、障害(5xx・壊れた JSON・通信失敗)は例外。呼び出し元7か所はほぼ無改修で、TSK-222 と衝突しない。3値化は案 A として、不採用の理由(既存の `if (!user)` が壊れる)を比較表に書いた |
| 2. `(authenticated)/error.tsx` は、レイアウトが投げた例外を受けられない | 致命的 | 採用 | 仕様どおり。置き場所を、レイアウトの**1つ上**のセグメント(`(main)/error.tsx`、`(teacher)/teacher/error.tsx`、`(admin)/admin/error.tsx`)に直した(`ls` で、各セグメントの構造を確かめた)。共通のクライアントコンポーネントを1つ作り、固定文にする。再試行は `startTransition(() => { router.refresh(); reset(); })`。サイドバーが出ないことはデメリットに書き、オーナーに聞く。実装の前に最小の再現で境界の位置を確かめる項目を足した。案 G(`(authenticated)/error.tsx`)を不採用にした |
| 3. `cache()` の共有は単体テストで確かめにくい | 重要 | 採用 | 単体テストをやめ、実装前の最小の実験(`console.log` で fetch の回数)と、実画面の確認に一本化した。`cache()` は別コミット(できれば別 PR)にして、共有されなければ外せるようにした |
| 4. 規模(7か所×3ロール)。案 B の不採用理由が案 F では成り立たない | 重要 | 採用 | 案 F では、呼び出し元はほぼ無改修で、変更は `me.ts` と `error.tsx` が中心。1 PR に収まる。案 B の理由を直し(`cache()` は `me.ts` だけの変更。別コミットにする)、「8か所」を「7か所」に直した |
| 5. 利用者のメリットは障害時だけ。デメリット(エラー画面の見た目、サイドバーの有無、本番の文言、`reset`)が無い。二重取得は開発側のメリット | 重要 | 採用 | 「利用者に見える変化とデメリット」を書き直し、二重取得は開発側のメリット(Rails への負荷が半減する)として分けた。案 D(Go 移行時にまとめる)を退ける理由を、「頻度は不明だが、案 F は変更量が小さいので今やって損がない」に直した |
| 6. 「Go 移行で引き継げる」の契約が書かれていない | 軽微 | 採用 | 契約を1行で書いた: 「`/me` が 401 なら未ログイン(`null`)。それ以外の失敗は障害(例外)。200 なら `user`」。`error.tsx` と `cache()` が Workers でも動くかは、移行時に再確認すると書いた |
| 7. Red の書き方(非同期レイアウトを `await Layout()` で呼ぶ、`redirect` のモックの漏れ、通信失敗と壊れた JSON のケース) | 軽微 | 採用 | Red に、500・壊れた JSON・レイアウトの reject(`redirect` が0回)・共通のエラー表示を足し、`mockReset` を明記した。通信失敗はすでに例外なので回帰防止に移した |
| (確かめた事実) ロール不一致で `/login` に飛ぶ分岐がある | - | 採用 | 「変えない」と明記した。壊れた JSON は障害として扱う(オーナーに確認) |

2. 案 F(`null` = 未ログイン、障害は例外)でよいか。

4. 実画面での確認(境界の位置、`reset`/`router.refresh()` の復帰、`cache()` の fetch の回数)に、開発サーバーとバックエンドの停止を使ってよいか。
