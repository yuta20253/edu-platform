## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒） | キャンセル復帰での下書き取得失敗時に、空のフォームの代わりにエラー表示と再試行が出る。成功時は「空のフォームから内容が入る」ちらつきが消える。 | 失敗の頻度は低く、実利は小さい。404 では直らない再試行が出る。取得中は、これまでのフォームではなくスピナーになる。 |
| 開発チーム | 黙殺する旧フックを削除できる。初期値の本命が1つになる。Go 移行に無関係な Rails 前提は持ち込まない。 | 分割とテスト整備で PR が大きい。TSK-223 のマージ待ち。`useUnitSelection` の共通フックを触る。 |

- 両方にメリットがあるか：利用者のメリットは小さいが損は無い。開発側のメリットが主。草案もそれを正直に書いている。「内部整理に近い」と見てよい。
- やらないことのデメリット：
  - 利用者が失うもの：まれな失敗のときに、入力が消えたように見える。「キャンセル」をもう一度押せば戻れる。
  - 開発チームが失うもの：黙殺フックと `reset` の二重管理が残る。
- 草案に無かったメリット・デメリット：priority のバグが露出する可能性（指摘1）。

## 確かめた事実
- `useUnitSelection` は引数なしで、`EditTask/index.tsx:40` と `CreateTask/index.tsx:52` の2か所だけが使っている（grep で確認）。`initialIds = []` の省略可能な引数は、型・挙動ともに両方と矛盾しない。
- `EditTask` は、`useUnitSelection` の後に `setSelectedUnitIds(unitIds)`（51行）を呼んでいる。引数なしのままなので影響しない。
- `useSubmit.ts` は `unit_ids: selectedUnitIds` で、フォーム値の `unit_ids` を送信時に上書きする。つまり react-hook-form の `unit_ids` は送信に使われず、実質の本体は `selectedUnitIds` の state である。`defaultValues` に一本化しても、`useUnitSelection(initialIds)` で state の初期値を渡していれば整合する。草案の設計に矛盾は無い。ただし草案は「二重管理が残る」ことに触れていない（指摘4）。
- `DraftTaskType.priority` は **`string`**（`useFetchDraftTask.ts`）で、`CreateTaskConfirm` のテストも `"high"` を使う。一方 `useDefaultValues` と `reset` は `typeof draftTask.priority === "number"` のときだけ採用し、それ以外は `PRIORITY.NORMAL` にする。API が文字列を返すなら、キャンセルで戻っても優先度は常に「普通」に戻る。これは現行の不具合の可能性が高い（推測。API の実レスポンスは未確認）。
- `new/page.tsx` は現状 `Number(draftTaskId)` を渡しており、`isNumericId` を使っていない。Props は `draftTaskId: number`。`isNumericId` は `libs/server/routeParams` にあり、`"0"` も真になる。
- `reset` と `useDefaultValues` の変換ロジックは、本文が完全に同じ（コピー）である。削除は安全。

## 残すべき強み
- 「回帰防止 → 移すだけ → 別コミットで整理」の3段階。戻しやすい。
- 頻度が低く、主な理由は開発側のメリットだ、と正直に書いている点。
- URL 分岐モックと、`draft-tasks` を含む呼び出しが無いことで確かめる新規作成のテスト。
- 案の比較表（A〜G）と、404 を許容して TSK-219 後に再検討するという切り分け。

## 指摘

### 指摘1【重要】（観点：テスト計画）
- 何が問題か：回帰防止の「優先度が現行と同じ」というテストは、priority の型が string か number かで結果が変わる。API が文字列（`"high"`）を返すなら、現行の挙動は「常に普通に戻る」で、テストはそれを固定するか、書いた時点で落ちる。
- 根拠：`DraftTaskType.priority: string` と `typeof ... === "number"` の分岐（コードで確認済み）。実 API の値は未確認（推測）。
- 直し方の提案：テストデータの priority に何を使うかを明記する。実 API の型を Rails の serializer か実レスポンスで確かめて、number が正ならそれに合わせる。string が実態なら「現行の不具合を別チケットで直す。このチケットでは変えない」と書き、テストで固定するかスキップするかを決める。

### 指摘2【重要】（観点：スコープ・整合）
- 何が問題か：やることの「`new/page.tsx` で `isNumericId` で検証する」と、Props の型（`draftTaskId: number`）が噛み合っていない。`page.tsx` は async の Server Component で、`notFound()` は使えるが、「無いとき＝新規作成」と「`0`・`NaN`」の扱いが書かれていない。既存テストは `draftTaskId={0}` を使っており、`"0"` は `isNumericId` で真になるため、`/draft-tasks/0` を取得しに行く。
- 根拠：`page.tsx` と `routeParams.ts`。
- 直し方の提案：Props を `draftTaskId: number | null`（または省略可能）にして、page.tsx が `null` を渡すと決める。既存の7件を `draftTaskId={null}` に直すことも、やることに書く。`0` を有効とみなすかも一言書く。

### 指摘3【重要】（観点：完了条件）
- 何が問題か：完了条件の「単元の初期値が変更の前後で同じ」は、テストの観点が selectedUnitIds（画面に表示される選択状態）で確かめるのか、フォーム値の `unit_ids` で確かめるのか不明。後者は `useSubmit` が上書きするため、確かめても意味が無い。
- 根拠：`useSubmit.ts` の `unit_ids: selectedUnitIds`。
- 直し方の提案：テストでは、「単元がチェック済みで表示される」ことと、送信時の POST ボディの `unit_ids` が下書きの単元になることを確かめる、と書く。

### 指摘4【軽微】（観点：対策の重複）
- 何が問題か：一本化しても、フォーム値の `unit_ids` と `selectedUnitIds` の二重管理は残る（`useSubmit` が前者を捨てる）。草案は「本命は defaultValues の1つ」と書いているが、単元については実質 state が本命。
- 直し方の提案：「単元の二重管理は今回の範囲外。別件」と一文で明記する。あるいは完了条件の「本命が1つ」を「初期値の流し込みが `useEffect` から消える」と言い換える。

### 指摘5【軽微】（観点：進め方）
- 何が問題か：`useUnitSelection` は `hooks/` 配下の共通フックなので、引数追加という共通部品の変更が最後のコミットに混ざる。TSK-213 の教訓（共通部品の拡張を画面の移行に混ぜる）に近い。ただし後方互換で影響は小さい。
- 直し方の提案：そのまま混ぜてよい。ただし PR 説明に「共通フックの変更を含む」と書き、`useUnitSelection` の単体テストを1件足す（`initialIds` が反映される、省略時は `[]`）。

## 本人に確認すべき問い（草案を直さなくても進められるもの）
1. 頻度が低い失敗のために分割する価値があるか。開発側のメリット（黙殺フックの削除）で十分とみなしてよいなら、進める。
2. `reset` の整理を、同じ PR の別コミットでよいか。戻しやすさは保たれており、私は賛成。
3. 404 で直らない再試行を許容するか。草案の根拠は妥当。TSK-219 後に再検討でよい。
4. 実画面確認をやるか。やらないなら「未検証」と明記する2択が既に書いてあるので、草案は直さなくてよい。ただし指摘1（priority の実レスポンス）だけは、実 API か serializer の確認が欲しい。実画面確認をやるなら、同時に確かめられる。

草案を直さないと進められないのは、指摘1〜3。指摘4・5 は軽微で、直さなくても進められる。
