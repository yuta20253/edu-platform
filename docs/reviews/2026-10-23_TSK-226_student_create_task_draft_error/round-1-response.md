# 第1周の対応(CreateTask の下書き取得失敗)

第1周の判定: **直せば進めてよい**

| 指摘 | 重大度 | 対応 | 理由・草案のどこを直したか |
| --- | --- | --- | --- |
| 1. 新設する `CreateTaskForm` が、`types.ts` の型 `CreateTaskForm` と同名で衝突する | 重要 | 採用 | コードで確認した。コンポーネント名を `CreateTaskBody`(`QuestionBody` と揃える)にした |
| 2. 既存の7件は `draftTaskId={0}` で、下書きのある経路を通らない。モックが全 URL に講座一覧を返す | 重要 | 採用 | コードで確認した。回帰防止(最初に書いて現行で緑にする)を、URL で分岐するモックで書くと明記した。新規作成で下書きを取得しないことは、`get` の引数に `draft-tasks` を含まないことで確かめ、呼び出し回数は使わない。Red と回帰防止は混ぜず、コミットも分ける |
| 3. 分割後は `reset` の `useEffect` が `defaultValues` と重複する | 重要 | 採用 | コードで確認した(`useDefaultValues` が、下書きありの値を作っている)。本命を `defaultValues` に決め、`reset` と `setSelectedUnitIds` の `useEffect` を削除する設計にした。単元は `useUnitSelection(initialIds)` の省略可能な引数で渡す(EditTask の呼び出しは変わらない)。進め方は「回帰防止 → 移すだけ → 別コミットで整理」の3段階にし、整理が問題なら1コミットだけ戻せるようにした |
| 4. 404 の扱いが無い。再試行が何度も失敗するときの行き場が無い。代替案の比較が浅い | 重要 | 採用(許容を明記) | 「404 の扱い」の節を足した。`useApiQuery` は 401 以外を区別しないので、直らない再試行が出るが、まれなので許容し、TSK-219 のマージ後に再検討する。「新規作成へ」のリンクは案 E として比較し、`AsyncBoundary` に追加アクションを渡す仕組みが無いため保留にした。案 C の不採用理由を「下書きの内容が消えたと誤解させる」に直した |
| 5. `draftTaskId` が変わると前の data が残る可能性 | 重要 | 採用 | 「遷移で作り直されるため `key` は不要(TSK-217 の構造)」と1行書き、実画面確認の項目に `draftTaskId` を変えての遷移を足した |
| 6. 完了条件が測りにくい(TSK-216、実画面確認) | 軽微 | 採用 | 実画面確認は「行って PR に書く」か「未検証と PR に明記する」の2択にした。TSK-216 は「依存」の確認事項に移した |
| 7. `useDefaultValues.ts` の import を、どちらのチケットで直すかが曖昧 | 軽微 | 採用 | 「TSK-223 で直す。このチケットはその後を前提にする」と背景と依存に書いた |

加えて、批判の「頻度が極めて低い」を受けて、背景に「頻度は低く、主な理由は黙殺する旧式フックを消して規約に揃える開発側のメリット」と正直に書いた。

## 本人に確認すべき問い(手順5で聞く)

1. 頻度が低い失敗のために、フォームの分割を伴う変更をする価値があるか(最小版は、`enabled` が要るので #206 待ちになる)。
2. `reset` の整理は、同じ PR の別コミットでよいか(別 PR にもできる)。
3. 404 のとき、直らない再試行が出ることを許容するか(TSK-219 後に再検討)。
4. 実画面確認を行うか。
