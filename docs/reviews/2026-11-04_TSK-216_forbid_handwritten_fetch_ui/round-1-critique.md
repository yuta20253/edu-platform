# 批判：TSK-216 ローディング・エラー表示の直書き禁止ルール(見直し版)(第1周)

## 総評

調査をやり直して「許可リスト消化済み」「文字列禁止は推奨パターンを誤検出」と分かった点は良い仕事です。ただ ESLint のスコープが `index.tsx` だけで、直書きが `Presenter.tsx` やフックに逃げられる穴を、草案は検討していません。

## 判定

直せば進めてよい。走査テストをやめて ESLint 1 本にする判断は妥当です。ただし、ルールの精度(穴)と、`eslint-disable-next-line` が JSX テキストで効くかが未検証です。

## 必須観点の判定

|                            | メリット                                                                                         | デメリット                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 利用者(生徒・教師・管理者) | 見える変化なし。無限スピナーや文言のばらつきの再発が減る(間接的)。草案はこの点を正直に書いている | 変化なし。CreateStudent の失敗表示(再試行ボタンなし)は別チケットまで残る                                                            |
| 開発チーム                 | 書いた時点で lint が止める。許可が違反の行にあり、消し忘れも lint が教える。仕組みが 1 つで済む  | 規約との整合は ESLint の精度に依存する。穴が多いと「守られている」という安心感だけが残る。CreateStudent 用に別チケットが 1 本増える |

- 両方にメリットがあるか：利用者に損がない内部整理。
- やらないことのデメリット：
  - 利用者が失うもの：新しい画面でまた無限スピナーや文言のずれが入り、取得失敗で画面が止まるリスク。
  - 開発チームが失うもの：移行 20 本近いチケットの成果が再び崩れる。CLAUDE.md だけでは再発する(案 D の理由は妥当)。
- 草案に無いデメリット：ESLint を弱い形で入れると、禁止事項 4 つのうち実際に守れるのは 1.5 個程度。それを「禁止ルールを入れた」と呼ぶことの誤認リスク(指摘 1)。

## 確かめた事実

- `CircularProgress` が `index.tsx` に残るのは 4 本(Calendar、InterviewCalendar、CreateInterview、CreateStudent)で、草案と一致しました。
- `eslint.config.mjs` にカスタムルールはありません。既存の `eslint-disable` は 3 件(EditTask、TeachersTab、Schools)で、草案どおりです。
- `useInterviewCalendar.ts` の 14〜16 行に、Calendar と同じハイドレーション回避のコメントがあり、`today` と `month` は `useState(null)` です。**草案の「未検証」は、ファイルを 1 つ読めば解消します**。恒久的な例外で確定してよいです。
- 「取得に失敗」を含む非テストファイルは `index.tsx` 以外にもあります。`Presenter.tsx`(student/admin Analytics、teacher/StudentDetail、CreateInterview)、`Step1FileSelect.tsx`、`useFetchDashboard.ts`、`useFetchAdminDetail.ts`、`TeachersTab.tsx`、`useTeacherInvitations.ts` などです。草案のルールは `features/**/index.tsx` 限定なので、これらは対象外です。
- `index.tsx` の「取得に失敗」リテラルは、EditTask、EditGoal、NoticeEdit、Schools、AnnouncementEditor の 5 本と CreateStudent(JSX テキスト)で、草案と一致します。

## 残すべき強み

- ESLint 1 本 + 違反の行の `eslint-disable`(理由つき) + `reportUnusedDisableDirectives: "error"` という構成。許可リストを 2 か所に持たない整理です。
- 検証済みと未検証の表を分けていること。「`Alert severity=error` 禁止」を `Login` と `SignUp` の誤検出で退けたこと。
- 「機械で守れないもの」を隠さず書いていること。
- CreateStudent を本物の違反として切り出し、このチケットを小さく保つ判断。

## 指摘

### 指摘1【重要】(観点：テスト計画 / 失敗の想定)ルールの対象が `index.tsx` だけで、逃げ道が広い

- 何が問題か：禁止は `features/**/index.tsx` 限定です。しかし現状でも、エラー文言は `Presenter.tsx`(Analytics 2 本、StudentDetail、CreateInterview)やフック・タブコンポーネントに実在します。次に画面を書く人がローディング・エラー分岐を Presenter に移せば、ルールをすり抜けます。また草案は「`index.tsx` に分岐を置く」という前提を明示していません。
- 根拠：上記の grep(確かめた事実)。元チケットも「禁止事項は `features/**/index.tsx` では」と限定していたので、元の仕様どおりではあります。
- 直し方：次のどちらかを選び、草案に理由を書きます。
  - (a) 範囲を意図的に `index.tsx` に限定すると明記し、「Presenter への逃げは今は許容、レビューで見る」を CLAUDE.md の機械で守らない項目に入れる。
  - (b) `CircularProgress` の import 禁止だけは `features/**/*.tsx`(テスト除く)に広げ、現在の違反を数えて例外に出す。本数が少なければ、CreateStudent と同じく別チケットにする。
  - 少なくとも、`features/**/*.tsx` に広げた場合の違反件数を一時設定で数えてから決めてください。

### 指摘2【重要】(観点：テスト計画 / 事実か推測か)`JSXText` ルールの見逃しと `eslint-disable` の置き場所

- 何が問題か：
  - `JSXText[value=/取得に失敗/]` は、`{"…取得に失敗…"}`(Literal)、テンプレートリテラル、変数経由の文字列、`message=` 属性を見逃します。`errorMessage` のように属性で渡すのは許可なので、これは仕様として理にかなっています。ただし `<Alert>{"取得に失敗しました"}</Alert>` で簡単に回避できます。
  - JSXText ノードは、開始タグの直後(同じ行)から始まります。CreateStudent の文言が次の行にある場合、報告行は文言の行ではなく開始タグの行になる可能性があります(推測)。`eslint-disable-next-line` は JSX 内では `{/* … */}` の形で、報告行の直前に置く必要があります。位置を誤ると「違反が消えない + 不要な disable でエラー」の二重エラーになります。
  - 草案の未検証表は「`index.test.tsx` に効くか」「vitest で ESLint を動かせるか」だけで、この点を扱っていません。
- 直し方：「やること」の最初に、実際に `CreateStudent/index.tsx` へ `{/* eslint-disable-next-line … -- 理由 */}` を付けた一時ファイルで lint が通ることを確かめ、結果を「検証済み」に入れてください。通らなければ、`CreateStudent` だけ `eslint-disable`(ブロック)に変えるか、`overrides` の `files` で個別に外します。見逃しは仕様として CLAUDE.md の「機械で守らない」に 1 行入れる、で十分です。

### 指摘3【重要】(観点：テスト計画)ESLint の設定を vitest でテストする計画の費用対効果が不明

- 何が問題か：「ESLint の設定をテストする(`lintText`)」は未検証で、「遅すぎれば諦める」と逃げ道もあります。完了条件に「ESLint の設定のテストが通る」が入っているため、諦めた場合に完了条件が満たせなくなります。ルールの検証としては「実際の CI で `npm run lint` が 4 例外を含めて通る」と「使い捨てファイルで違反が出ることを PR に書く」で、このチケットの規模なら足りるはずです。
- 根拠：完了条件 5 と、未検証表の 3 つ目の矛盾(推測)。
- 直し方：テストを完了条件から外し、「`lintText` のテストは実装時に試し、実行時間が 1 秒程度なら入れる(任意)」とします。入れるなら `ESLint` に `overrideConfigFile` で本物の設定を読ませる形にします。設定を複製して書くと、設定とテストがずれます。

### 指摘4【軽微】(観点：スコープ / 完了条件が測れるか)例外のコメントの一覧化と `no-restricted-imports` の例外の置き方

- 何が問題か：例外の見つけ方は `grep -rn "eslint-disable.*no-restricted"` で、`import` 行に付ける例外は `no-restricted-imports` の `eslint-disable-next-line` で足ります。一方 JSX 内のテキスト違反は `no-restricted-syntax` です。grep の `no-restricted` で両方に当たるのでよいですが、**将来、別の理由で書かれた `eslint-disable no-restricted-*` も拾う**ため、一覧が「禁止ルール由来の例外」と一致しません。
- 直し方：理由欄に固定のタグ(例：`-- loading-exception:` / `-- TSK-xxx で移行予定`)を付けて grep するか、一覧に出てよいものに限ると CLAUDE.md に書く。軽微なので、そのままでも可です。

### 指摘5【軽微】(観点：事実か推測か / 完了条件)未検証の `InterviewCalendar` は、読めば確定できる

- 何が問題か：未検証表に残っていますが、`useInterviewCalendar.ts` の 14〜16 行に Calendar と同じコメントがあり、検証できました。
- 直し方：「検証済み」へ移し、恒久的な例外で確定。「やること」の読む作業は消してください。

### 指摘6【軽微】(観点：スコープ)CreateStudent の別チケット起票を、マージの前提にしない書き方

- 何が問題か：`eslint-disable` の理由に「新しく起票するチケットの番号」を書く設計です。この番号は、起票してからでないと書けません。起票を後回しにすると、理由が空欄か「TSK-???」になり得ます。
- 直し方：実装の最初のタスクに「起票して番号を得る」を置いている点は良いです。それを「このチケットの PR を出す前に必須」と明記してください(依存の欄は「マージには必須でない」としていますが、番号が必要という点でズレています)。

### 指摘7【軽微】(観点：移行計画との整合)

- 何が問題か：ESLint と Cloudflare/Go 移行は無関係で、問題ありません。ただし `no-restricted-syntax` で `eslint.config.mjs` が `next/core-web-vitals` 側と競合しないか(同じルールを別の config が上書きしないか)は、一時設定の検証で通っています。ここは確認済みなので問題なしです。
- 直し方：不要。

## 本人に確認すべき問い

1. 元の方針は 10/23 に「走査テスト + ESLint」でした。これを ESLint 1 本にしてよいですか。根拠は、(1) 許可リストを 2 か所に持たない、(2) `reportUnusedDisableDirectives` で消し忘れを防げる、(3) CI は `npm run lint` を実行する、の 3 点です。ESLint を使わない運用(エディタ外の確認)に走査テストが必要か、という観点で承認をお願いします。私は妥当と考えます。
2. ルールの範囲は、元仕様どおり `features/**/index.tsx` だけでよいですか。Presenter やフックへの逃げをレビューに任せる判断（指摘 1 の (a)）か、`CircularProgress` の import だけは広げる判断（(b)）かは、オーナーの好みです。
3. `CreateStudent` を別チケットにして、このチケットでは `eslint-disable` に留める判断でよいですか。違反の画面を 1 つ残したまま「禁止ルール導入済み」とすることになります。
4. 「ESLint の設定のテスト」を完了条件に入れますか(指摘 3)。入れない場合は PR に一時ファイルでの確認結果を書く形で足りますか。
