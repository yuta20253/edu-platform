## 確かめた事実

frontend/ に一時ファイルと一時設定を作って確認し、削除済み。`git status` は docs/reviews の未追跡フォルダのみ。

- `StudentDetail/Presenter.tsx` の 115〜122 行は、`{error ? ( <Typography variant sx > データの取得に失敗しました </Typography> ) : ...}` という複数行の開始タグで、三項演算子の中にある。
- 同じ形を再現して `JSXText[value=/取得に失敗/]` を当てた。
  - 報告された行は、`<Typography` の行でも文言の行でもなく、開始タグを閉じる `>` の行(再現では 7 行目)だった。
  - `<p` の直前に `// eslint-disable-next-line` を置くと、「不要な disable」と「違反」の二重エラーになった。
  - 属性の末尾、`>` の直前の行に `// eslint-disable-next-line` を置くと、エラーは消えた。
  - `{/* */}` は三項演算子の括弧の中では JSX の子ではないので、そもそも置けない。
- `features/**/index.tsx` に `loading ||`、`|| loading`、`if (loading)`、`if (!data)` は 0 件(grep)。

  - 草案の「機械で守らない」はテンプレートリテラルと変数には触れているが、`.ts` フックには触れていない。
- `Literal[value='データの取得に失敗しました']` は、非テストの features に今は 0 件(grep)。ErrorState の既定文言は `components/ui` にあるので対象外。
- `frontend/CLAUDE.md` の StudentDetail の例外の記述(23 行)は草案の説明と一致している。

## 指摘

### 指摘1【重要】(観点:事実か推測か/失敗の想定)

- 何が問題か:「`{/* eslint-disable-next-line */}` を開始タグの行の直前に置く」という検証済みの規則は、単行タグの CreateStudent の `<Alert>` でしか確かめていない。例外にする StudentDetail/Presenter.tsx は複数行の開始タグで、三項演算子の中にある。この形では、報告行は `>` の行になり、`{/* */}` はそもそも書けない。書かれた手順どおりにすると、二重エラーか構文エラーになる。
- 根拠:上記の再現。
- 直し方の提案:
  - 設計の 2 を次のように直す。disable は「報告される行(= 開始タグを閉じる `>` の行)の直前に置く」。複数行タグでは属性の末尾に `// eslint-disable-next-line …`、単行タグでは直前の `{/* */}`。三項演算子の中では `{/* */}` は使えない。
  - 手順を決め打ちにせず、「実装時に `npm run lint` が通ることで確かめる」と書く。
  - 検証表に StudentDetail の形(複数行 + 三項)を足す。実装の最初の 1 件目を StudentDetail にして先に確かめるとよい。
  - 代案として、実装が汚くなるなら、StudentDetail は文言を `ErrorState`(再試行つき)に直せないか、または `/* eslint-disable */` と `/* eslint-enable */` で囲む方式を比べる。

### 指摘2【重要】(観点:対策の重複/規約との整合)

- 何が問題か:StudentDetail の「タブ切替後の失敗」を、再試行ボタンの無い手書きの `Typography` のまま「恒久」の例外にしようとしている。CLAUDE.md の規約4(`ErrorState` + `onRetry`)に反する実装を、恒久と固定することになる。CLAUDE.md が書いている例外の理由は「ヘッダーを残す」ことで、「再試行を付けない」ことではない。
- 根拠:`StudentDetail/Presenter.tsx` 115〜122 行。`ErrorState` を使っていない。
- 直し方の提案:`ErrorState` にヘッダーを残したまま表示できるか(Presenter の中で `<ErrorState message onRetry>` を出すだけで足りるか)を確かめる。足りるなら、例外にせず直すほうが小さい。足りないなら、「恒久」ではなく「一時」にして、チケットを起票するか、理由に「再試行は別途」と書く。

### 指摘3【重要】(観点:完了条件が測れるか)

- 何が問題か:設定テストを任意にしたことで、完了条件 5 が「テスト(任意)か、使い捨てファイルでの確認結果(PR に記載)」という、どちらでも通る条件になった。「PR に記載」は、いつ・誰が確認するかが決まっていない。また、完了条件 1〜3 は一度きりの手動確認になり、その後ルールを壊す変更(ESLint の設定変更)が起きても気づけない。
- 根拠:草案「完了条件」の 5 番目、「やること」の 2 番目。
- 直し方の提案:次のどちらかに決める。
  - 設定テストを実装の最初に 1 本書いて時間を測り、1 秒程度なら必須にする(「任意」を外す)。
  - 遅いなら、検証用の入力をリポジトリに置かず、PR 本文に「入力と `eslint` の出力」を貼ることを完了条件にし、確認者はオーナーの PR レビューと書く。
  - 完了条件 8(`npm run lint` / `test` / `typecheck` / `format:check` が通る)は、「実装後の main で」に直す(今の書き方は「現在の main」で、変更前の状態にも読める)。

### 指摘4【軽微〜重要】(観点:完了条件が測れるか/失敗の想定)

- 何が問題か:固定の見出し `表示規約の例外` は、lint が強制しない。見出しを書き忘れた、または表記が揺れた disable は、lint を通るのに一覧に出ない。「一覧が grep で出る」ことが、静かに崩れる。
- 根拠:`no-restricted-*` の disable は、理由の書式を ESLint の標準機能では検査しない(推測。`eslint-comments` 系プラグインの `require-description` は書式まで見ない)。
- 直し方の提案:新しい依存を入れず、CLAUDE.md の確認項目に次の 1 行を足す。`grep -rn "eslint-disable.*no-restricted" frontend/features | grep -v 表示規約の例外` が空であること。完了条件の「4 本 + StudentDetail」の確認にも同じコマンドを使う。

### 指摘5【重要】(観点:対策の重複/代替案の比較)

- 何が問題か:機械で守らない禁止事項の筆頭が `loading || !data` と「手書きの取得フック」。前者は、現状 `features/**/index.tsx` に 0 件なので、`index.tsx` に限ったセレクタなら誤検出ゼロで機械化できる可能性が高い。「機械で守れない」と決める前に、試した形跡がない。
- 根拠:grep で `loading ||`、`|| loading`、`if (loading)`、`if (!data)` が index.tsx に 0 件。
- 直し方の提案:`index.tsx` 限定の `no-restricted-syntax` を一時設定で当て、`loading` を含む分岐の件数を数える。0 件なら 1 本足す(または、誤検出が出るなら、出た画面を書いて「機械化しない」と理由を書く)。足さない場合も、「試した結果」を比較表(案 I)に残す。

### 指摘6【軽微】(観点:CLAUDE.md の内容として十分か)

- 何が問題か:禁止事項の一覧は、次の 3 点が足りない。
  1. `.ts` のフックで失敗文言を `setError("…取得に失敗しました")` と書く経路(上記の 3 本)が一覧に無い。これは「手書きの取得フック」の別の見え方で、ルールが `.tsx` 限定なので漏れる。
  2. 「JSX 属性の文字列(`message="…"`)は、`ErrorState` に渡す限り許可」という、許可側の書き方が無い。CsvImport と admin/Analytics が既に使っている。
  3. 例外を足してよい基準(誰が、どういうときに `eslint-disable` を足してよいか)が無い。基準が無いと、例外が増える抜け道になる。
- 直し方の提案:CLAUDE.md の確認項目に 3 点を足す。基準は「恒久は理由が取得状態でないこと(ハイドレーション待ち、初期選択)、一時は移行チケットの番号があること」の 2 行で足りる。

### 指摘7【軽微】(観点:利用者へのデメリット/失敗の想定)

- 何が問題か:CreateStudent の移行チケットは Backlog 起票だけで、優先度も期限も無い。「一時」の例外は、放置されると恒久になる。草案の効果(「禁止ルール導入済み」)と、違反の画面が 1 つ残る現実とがずれる。
- 直し方の提案:PR 本文と CLAUDE.md に「CreateStudent は一時の例外で残っている」と書く。「一時」の例外の一覧を、定期的に見る場所(例:次の振り返り)を決める。
