## 確かめた事実

frontend/ に一時ファイルは作らず、読み取りだけで確かめた。`git status` は docs/reviews の未追跡フォルダのみ。

- `CreateStudent/index.tsx` は `loading: teacherLoading` とリネームして受け取り、`if (teacherLoading)` で `CircularProgress` を出している。名前が `loading`・`isLoading` と完全一致するセレクタでは、この既存の本物の違反に当たらない。草案の「0 件」は、既知の違反に当たることを確かめたものではない。
- `useApiQuery` は `loading` フラグを持たない(`data` と `error` だけ)。新しい画面が規約どおり `useApiQuery` を使うと、`loading` が分岐に現れる経路自体がほぼ無い。この規則が効くのは、手書きの取得フックが `loading` を返す場合だけ。
- `eslint.config.mjs` には `no-restricted-*` が無く、ignores だけがある(競合なし)。
- 「データの取得に失敗しました」のリテラルは、`features` の非テストコードには無い(テストだけ)。`Literal` ルールは今は誰にも当たらない。
- `StudentDetail/Presenter.tsx` 115〜122 行は草案どおり。三項演算子の中で、複数行の `<Typography>` に失敗文言がある。

## 指摘

### 指摘1【重要】(観点:事実か推測か/失敗の想定)

- 何が問題か: `loading` 分岐のセレクタは、(a)名前で当てるのでリネームに弱く、(b)セレクタの形が草案に書かれておらず、誤検出の有無を判断できない。
  - (a)は `CreateStudent` が実例。`loading: teacherLoading` で受け取るので、名前一致のセレクタは見逃す。`/[Ll]oading$/` のような正規表現にすれば当たるが、そのとき `CreateStudent` の `if (teacherLoading)` にも disable が要る(例外の数と grep の件数が変わる)。
  - (b)は、`IfStatement` の子孫に `Identifier[name=loading]` を当てると、`if (x) { return <P loading={loading} /> }` や `cond ? <P loading={loading}/> : null` の本体側まで引っかかる。現状 0 件でも、将来の正当な props 受け渡しを誤検出する。`.test` や左辺・右辺に限る書き方が要る。
- 根拠: `CreateStudent/index.tsx` 13 行と 19 行。`useApiQuery.ts`(`loading` フラグが無い)。草案「設計」3 と検証表の 45 行は「セレクタ 6 つ」とだけ書いている。
- 直し方の提案:
  - セレクタを草案に具体的に書く。`IfStatement > .test`、`ConditionalExpression > .test`、`LogicalExpression` の左右、のように、条件の位置に限る。
  - 名前の形(`loading`・`isLoading` か、`/[Ll]oading$/` か)を決める。後者なら `CreateStudent` に disable が 1 件増えるので、件数を直す。前者なら、リネームで逃げられることを CLAUDE.md の「機械で守らない」に書く。
  - 設定のテストの入力に、`const {loading: x} = …; if (x)` と、`cond ? <P loading={loading}/> : null`(出ない)を足す。
  - 約束できる効果は「手書きフックが `loading` を返す新画面」だけだと、PR 本文に正直に書く。

### 指摘2【軽微〜重要】(観点:完了条件が測れるか)

- 何が問題か: 完了条件の「`grep -rn "表示規約の例外" frontend/features` で 5 件」は、数が合わない可能性が高い。`CreateStudent` は `index.tsx` の import(`no-restricted-imports`)と `<Alert>`(`no-restricted-syntax`)で 2 か所の disable が要る。恒久 3 本 + `CreateStudent` 2 + `StudentDetail` 1 = 6 件になる。`Presenter` の `loading` 分岐(指摘1の後者)を足すと 7 件。
- 根拠: `CreateStudent/index.tsx` の `CircularProgress` の import と `<Alert severity="error">`。草案の完了条件 4 番目と設計 5。
- 直し方の提案: 件数を「例外ごと」でなく「行ごと」で数え直す(6 件)。または件数を書かず、「一時の例外のチケット番号が、フォローアップ 1 種類だけ」であることを確認項目にする。

### 指摘3【軽微】(観点:テスト計画/規模)

- 何が問題か: 設定のテストの入力に「`StudentDetail` の形(複数行+三項)で disable が通る」と、「二重エラーの回避」が入っていない。置き場所は実装の最初に `npm run lint` で確かめるとあるが、回帰を防ぐのは単行タグ・複数行タグの両方の例外入力だけ。`Literal` ルールは今 0 件で、効いていることを示すのはテスト入力だけなので、入力は必須。
- 直し方の提案: 「出ない(例外)」の入力を 2 形(単行・複数行+三項)にする。

### 指摘4【軽微】(観点:スコープと依存/失敗の想定)

- 何が問題か: フォローアップ 1 本に、`CreateStudent`(取得フックの書き直し)と `StudentDetail`(教師画面の見た目の変更)が入る。性質も大きさも違い、片方が止まると両方の一時の例外が残る。
- 直し方の提案: 起票は 1 本でよいが、子項目を分けて書き、片方を先にマージできると明記する。`eslint-disable` の番号は共通のまま。
- 補足: 「一時」を定期的に見る場所は未決。次の振り返りか、`grep "表示規約の例外(一時)"` を PR テンプレートに入れるかをオーナーに聞く。

### 指摘5【軽微】(観点:規約との整合)

- 何が問題か: `.ts` のフックの失敗文言 4 本は「レビューで確認」で、実際に気づく手段が人しか無い。`TeacherInvitation` のように、一覧に `loading`・`error` を返す手書きフックを引き続き使う画面が、新しく作られる可能性は残る。
- 直し方の提案: 現状どおり、対象外でよい。ただし CLAUDE.md の確認項目に「新しい取得は `useApiQuery` を使い、`apiClient.get` を直接呼ばない」を 1 行足す(`git grep` でレビュー時に確かめられる)。

## このまま実装に進んでよいか

進んでよい。上の指摘1〜3 は草案に数行足せば足り、設計をやり直す種類ではない(セレクタの具体化、件数、入力例の追加)。過去の答え合わせでも、最終周の「軽微のみ」は実装中の確認で収まっている。実装の最初にやるのは、(1)設定テストの実行時間、(2)`CreateStudent` と `StudentDetail` の disable の置き場所、(3)`no-restricted-syntax` の置き換え、の 3 点。
