# 批判：TSK-215 student 配下の取得画面を共通部品に移行する（第1周）

## 総評

範囲の切り方、フックの残し方（TSK-214 踏襲）、検証済み／未検証の分離がよくできている草案です。弱いのは次の4点です。生徒へのメリットを裏付ける実画面確認が未実施であること。Question の組み方が `EMPTY` 定数で苦しいこと。Red にならないテストが混ざっていること。範囲外 8 画面が TSK-216 を長期間ブロックする構造になっていること。

## 判定

**直せば進めてよい**。生徒（再試行・ちらつき解消）と開発チーム（直書き 9 箇所と 2 行フックの削減、TSK-216 の前提づくり）の両方にメリットがあります。指摘はいずれも改訂で直せます。

## 必須観点の判定

|                | メリット                                                                                                                                                     | デメリット                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 利用者（生徒） | 取得失敗時に再試行できる（今は 11 画面すべてでゼロ）。Goals / Tasks / 詳細系 / Question / 確認画面で、初回に出るエラーや「問題が存在しません」が出なくなる。 | ローディングの高さが `100vh` から `minHeight: 240` に変わる（草案も認識済み）。実画面で未確認。                |
| 開発チーム     | 取得状態の分岐の直書き（9 画面分）と、約 7〜8 個の 2 行フック・テストが消える。TSK-216 の走査テストに近づく。                                                | PR が 2 本。範囲外 8 画面が残り、TSK-216 の着手がそれらに依存する。`frontend/CLAUDE.md` を #207 と同時に触る。 |

- 両方にメリットがあるか：**ある**。ただし生徒側のメリットの大きさは「初回のちらつきが実際に見える」かどうかに左右されます（指摘2）。
- やらないことのデメリット：
  - 利用者が失うもの：失敗時に画面再読込でしか復旧できない。
  - 開発チームが失うもの：9 箇所の直書きが残り、TSK-216 が着手できない。teacher 側（TSK-214）との不一致が続く。
- 草案に無かったデメリット：#207 も `frontend/CLAUDE.md` を変更しており、PR 2 での CLAUDE.md 修正と衝突しうる。

## 確かめた事実

- `Tasks/hooks.ts`：`loading` の初期値は `false`、`data` は `null`。`index.tsx` は `loading && !data` を外れて `!data || error` に入り、一瞬エラー文言が出る。草案の記述どおり。
- `Question/hooks/useGetQuestions.ts`：`questions` の初期値は `[]`、`loading` は `false`。初回に「問題が存在しません」が出る。草案どおり。
- `QuestionConfirmation`：`questionHistories` の初期値は `[]`、`loading` は `false`。初回に「問題履歴がありません」が出る。草案どおり。
- `Announcements/index.tsx` と `Interviews/index.tsx`：`!data` ならスピナーで、**ちらつきは出ない**。草案の背景でもこの 2 画面はちらつき対象に挙がっていません。ところが PR 1 のタスクには「初回描画で `alert` が出ない」が全画面共通で入っています。
- 確認画面の `page.tsx` は async のサーバーコンポーネントです。`answeredQuestionIds` はサーバー側で作られて props で渡るため、従来の配列参照依存でも無限再取得は起きていませんでした。草案の「配列比較」の検証は有効ですが、リスクとしては小さいです。
- `useApiQuery` は現状 `enabled` なし。#206 と #199 は OPEN で、`hooks/useApiQuery.ts` を変更している。草案どおり。
- 範囲外 8 画面にも `CircularProgress` が残っている（`grep` で確認）。草案の調査と一致。
- #207 は OPEN で `frontend/CLAUDE.md` を変更している。

## 残すべき強み

- 「検証済み」と「未検証」を表で分け、確かめ方まで書いている。
- `useApiQuery` と `AsyncBoundary` を変更せず、#206 と衝突しない。
- Analytics / InterviewDetail を範囲外にした理由がコードで裏づけられている。案 B（合成）を退けた理由も妥当。
- 完了条件を「取得状態の分岐」に限定し、0 件表示や送信失敗を対象外と明記している。この言い換えは妥当で、TSK-216 の走査対象（`CircularProgress` の import と固定文言）とも一致します。
- 案 D で TSK-216 の走査との整合を理由に `100vh` を捨てた判断。

## 指摘

### 指摘1【重要】（観点：テスト計画）

- 問題：PR 1 の「初回描画で `alert` が出ない」テストは、Announcements と Interviews では現行コードでも通ります。Red になりません（TSK-211 の教訓）。
- 根拠：上記の確かめた事実。
- 直し方：このテストは、実際にちらつく画面（Goals / Tasks / AnnouncementDetail / GoalDetail / TaskDetail / Unit / Question / QuestionConfirmation）にだけ「Red 確認済み」として付けます。Announcements と Interviews は「回帰防止」と明記して区別します。Red になることは、実装前にテストだけを書いて落ちるのを見て確かめます。API を保留にしたまま、`alert` が出ないことと `progressbar` が出ることの両方を判定します。非同期の待ち不足による偽陽性にも注意してください。

### 指摘2【重要】（観点：事実か推測か）

- 問題：「初回のちらつき」が生徒向けメリットの柱なのに、実画面確認がありません。確認の方法も単体テストでの再現に寄っていて、実際の見え方を確かめていません。
- 根拠：草案の未検証表。TSK-217 では実画面確認で前提が崩れました。推測ですが、`"use client"` のコンポーネントは SSR されるため、初期 HTML にエラー文言が含まれ、ハイドレーションと effect が走るまで見える可能性があります。ちらつきではなく、もっと長く見える可能性があります（逆に dev での確認が難しい）。
- 直し方：実装前に、`curl` で SSR の HTML に「データの取得に失敗しました」が含まれるか確かめます。ログイン済みの Cookie が要るので、これはオーナーの了承が要ります。あわせて、ID が変わる遷移でページが作り直されるかの確認も、PR 2 の着手前に済ませます。確認コストが低く、TSK-217 の教訓が直接当てはまります。結果を「検証済み」表に移し、メリットの書き方（「一瞬」か「ハイドレーションまで」か）を実測に合わせます。ちらつきが目に見えないなら、メリットは再試行だけになり、判定の根拠が弱まります。

### 指摘3【重要】（観点：共通化の方針・規約との整合 / 代替案の比較）

- 問題：Question の `useQuestion({ questions: data ?? EMPTY })` は、`AsyncBoundary` の外で「空配列の状態」を持ち続けます。`EMPTY` 定数は回避策で、`currentQuestion` 不在と取得前の区別を、読み手が追わないと分かりません。
- 根拠：`useQuestion.ts` は `questions.length` と `questions[currentIndex]` に依存しています。
- 直し方：`AsyncBoundary` の children 内で `QuestionBody` のような内側のコンポーネントを描画し、そこで `useQuestion({ questions: data })` を呼びます。`data` は常に配列なので `EMPTY` が要りません。`currentQuestion` 不在（0 件）と `hasError`（送信失敗）の分岐は内側に収まります。外側は `useApiQuery` と `AsyncBoundary` だけになります。`useQuestion` の状態は取得完了後にしか生まれないので、「取得前の state」が消えます。この案を比較した案の表（案 G）に足してください。内側分離をやめるなら、その理由を書きます。
- 補足：テストに「`useApiQuery` の再取得で `data` が差し替わっても `currentIndex` が巻き戻らない」ケースは今は不要ですが、`refetch` を Question に付けない（成功時に再取得しない）ことは明記してください。

### 指摘4【重要】（観点：スコープと依存の切り方 / 移行計画との整合）

- 問題：範囲外 8 画面（約 4 チケット）が TSK-216 の依存になり、その全部が終わるまで走査テスト・ESLint が入りません。別チケットが後回しになると TSK-216 が止まります。
- 根拠：草案の「やること」最終項目、grep で範囲外 8 画面に `CircularProgress` が残ること。
- 直し方：どちらかを選んで草案に書きます。(a) TSK-216 の走査に一時的な許可リストを持たせ、範囲外画面を列挙して、チケットが消化されるたびに外す。この場合、TSK-216 の依存は増やしません。(b) 範囲外チケットの優先度と順序を決めて TSK-216 に依存させる。個人的には (a) を勧めます。TSK-216 が新規画面への直書きを止める価値は、残りの移行を待たずに得られるためです。
- 範囲外チケットには、それぞれ生徒にとって何が良くなるかを 1 行ずつ書いてください（特に UserProfile 系は「静的スピナーで止まる」という実害があるので、優先度を上げる理由になります）。

### 指摘5【軽微】（観点：スコープと依存の切り方）

- 問題：`frontend/CLAUDE.md` の修正が PR 2 にあります。しかし「Interviews の再試行は未対応」が古くなるのは PR 1 のマージ時点です。#207 も同じファイルを変更しています。
- 直し方：修正は PR 1 に入れます。#207 のマージ後に、最新の main から差分だけ当ててください。衝突したら、Tasks への参照先差し替えだけにします。

### 指摘6【軽微】（観点：利用者のデメリット）

- 問題：スピナーが `100vh` 中央から `minHeight: 240` に変わり、Question や確認画面ではレイアウトが上寄りになります。草案は未検証として挙げていますが、判断の期限が書かれていません。
- 直し方：PR 1・PR 2 それぞれの PR 説明に、移行前後のスクリーンショットを添える完了条件を足します。許容できないなら、Question 画面だけ `fallback` に要素を渡す選択肢があります（ただし TSK-216 の走査で例外が要る）。

### 指摘7【軽微】（観点：完了条件が測れるか）

- 問題：「初回表示でエラーや空の表示が一瞬出ない」の確認方法が、単体テストだけです。完了条件としては、実画面で確かめるかどうかが決まっていません。
- 直し方：指摘2の実画面確認の結果を、完了条件の確認方法として書きます（「実画面で Goals / Question を確認」）。
