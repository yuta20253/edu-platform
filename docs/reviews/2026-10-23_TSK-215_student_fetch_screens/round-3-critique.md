- `Tasks/index.tsx`：`loading && !data` で前回の data を残す。初回描画は `!data` に入る（Red になる）。`status !== "active"` のときだけ `status` を付ける。草案どおり。
- `Interviews/hooks`：`loading` を持たない。`status !== "all"` のときだけ付ける。エラー時は `setData(null)`。草案どおり。
- `CreateInterview/index.tsx`：`errorMessage` の文言は草案どおり。`ErrorState` を使い、`onRetry` は無い。
- `QuestionConfirmation/index.tsx`：`!loading && length === 0` で「問題履歴がありません」。草案どおり。
- `Question/index.tsx`：外側で `useQuestion({ questions })` を呼んでいる。「`QuestionBody` に分ける」案は妥当。
- `useApiQuery.ts`：params を JSON 文字列で比較する。再取得中は data を残す。エラー時に data を消さない。`enabled` は無い。草案どおり。

## 指摘（草案を直さないと進められないもの）

### 指摘1【軽微】（観点：事実か推測か）

- 何が問題か：「詳細系ルートでも ID 遷移で前の内容が残らない」が、検証済み表（L37）と未検証表（L43）の両方に載っている。L37 の根拠は「構造が TSK-217 と同じ」で、これは推論であって実画面での確認ではない。読み手は、確認済みと取り違える。
- 直し方：L37 の行の結果欄を「構造は同じ（コード上）。実画面は未確認 → 未検証表へ」に直す。または行を未検証表だけに残し、検証済み表には「ルートが動的セグメントの下にあること」だけを書く。
- 補足：構造上の根拠はおおむね妥当。ただし、`useApiQuery` のコメントは「url が別の対象に変わると前の内容が残る」としている。この前提が成り立つのは、同じ route の別 ID に remount なしで遷移できる場合に限られる。TSK-217 の結果と同じなら起きない。

### 指摘2【軽微】（観点：事実か推測か）

- 何が問題か：L12「対象13画面は、すべて `index.tsx` に…直書きしている」が古い。範囲は11画面で、Analytics と InterviewDetail は直書きではなく独自の取得処理を持つ。第2周で指摘1が背景を直し忘れた件と同じ型の食い違いが、別の箇所に残っている。
- 直し方：「当初の対象13画面のうち、範囲内の11画面は…」に直す。Notion に貼る前に、「13」「11」「9」の数字を全文で grep して揃える。

### 指摘3【軽微】（観点：失敗の想定 / テスト計画）— 草案に1行足せば済む。判断は不要

- 何が問題か：現行の Tasks / Interviews / Goals は、エラー時に `setData(null)` する。`useApiQuery` は data を残すので、「取得成功 → 失敗 → 再試行または絞り込み切替」のとき、失敗の前の古いリストが、新しい取得が終わるまで表示される。これは Tasks の status 切替で目立つ（別 status のリストが残る）。`AsyncBoundary` が error を先に判定するなら、エラー表示は正しく出る。問題は再試行後に起こる。
- 根拠：`Tasks/hooks.ts` の `setData(null)` と `useApiQuery.ts` の catch を比べた結果。`AsyncBoundary` の error 優先順位は、今回は冒頭までしか読んでいないので、挙動は推測。
- 直し方：「利用者に見える挙動の変化」の節に1行足す。テストは「成功 → 失敗 → 再試行」の中間状態を1本足す程度でよい。
