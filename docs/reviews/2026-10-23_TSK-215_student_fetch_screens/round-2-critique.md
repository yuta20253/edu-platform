## 総評

前回の指摘の大半はきちんと直っています。残る弱点は次の2点です。未検証のまま進めたとき、ID が変わる遷移で前の内容が残る危険を、草案が設計上どこにも受け止めていません。それと、Goals で利用者に見える挙動の変化が書かれていません。

## 確かめた事実

- `hooks/useApiQuery.ts`：`data` は再取得中も保持される。コメントにも「url が別の対象に変わる場合も前の内容が残る」とある。草案の引用と一致。
- `Goals/hooks.ts` と `index.tsx`：`setLoading(true)` の後、`index.tsx` が `if (loading)` を先に判定してスピナーを出す。つまり現行の Goals は、ページ切替・削除後の再取得でスピナーに置き換わる。移行後は前のリストが残り、スピナーは出ない。
- `Tasks/index.tsx`：すでに `loading && !data` で前回データを残している。Tasks は挙動が変わらない。
- `QuestionConfirmation/page.tsx`：async のサーバーコンポーネントで、`split(",").map(Number)` はサーバー側で実行される。草案 L33 の「毎回作り直される」は、クライアント側の再描画では起きない。前回の事実確認の指摘が、対応表では扱われていません。リスクは小さいですが、検証済み表の記述が実態とずれています。
- `useCompleteStudyLog` は取得の成否と無関係に動く。草案は「変更しない」で、既存の挙動のまま。
- `frontend/CLAUDE.md` L65 の記述、#207 が `frontend/CLAUDE.md` を変更していること、#206・#199 が `useApiQuery.ts` / Analytics を変更していることは、草案どおり。

## 指摘

### 指摘1【重要】（観点：事実か推測か / 失敗の想定）

- 何が問題か：詳細系7画面（AnnouncementDetail / GoalDetail / TaskDetail / Unit / Question / QuestionConfirmation / CreateInterview）で「ID が変わっても前の内容が残らない」は未検証のままです。草案はこの前提が崩れたときの設計を持っていません。`useApiQuery` は url が変わっても前の data を残すので、崩れると前の目標・課題の内容が一時的に表示されます。単体テストでは見つかりません。
- 根拠：`useApiQuery.ts` のコメント、草案 L36・L42。TSK-217 の教訓（前提が当たった側と外れた側の両方があった）。
- 直し方：実画面を使わずに確かめられる範囲を先にやります。student の詳細ルートが `[goalId]` などの動的セグメントの下にあるかを `app/` で確認します（確認画面は `[taskId]/units/[unitId]` の下にある）。そのうえで、TSK-217 の結果と同じ構造であることを検証済み表に移します。実画面確認が済まないまま PR 2 を出す場合の保険も、草案に書きます。たとえば「前の内容が残ると分かったら、その画面だけ `key={id}` を付ける追補 PR を出す」、あるいは「PR 2 の説明に未検証と明記する」です。完了条件の「実画面での確認」には Goals / Question しか挙がっていません。詳細系の ID 遷移は完了条件に入っていないので、足してください。

### 指摘2【重要】（観点：事実か推測か）

- 何が問題か：未検証と言いつつ、背景の見出し・本文はちらつきを断定しています。L13「初回表示でエラー（または空）の表示が一瞬出る」、L14-17「一瞬出る」。対応表の「断定しない形にした」と食い違います。さらに SSR の可能性が当たると「一瞬」ではなく、ハイドレーションまで見える可能性があります。
- 根拠：L13-17 と L43。
- 直し方：背景を「コード上は初回描画でエラー・空の分岐に入る（実画面での見え方は未確認）」に直します。Notion に出る本文でも同じ言い方にします。生徒向けメリットの柱は、確実な「再試行」と、コード上確認できた「初回にエラー・空の文言が描画される」にします。ちらつきの長さは実測後に追記します。
- 補足：`curl` での SSR 確認はログイン Cookie が要りますが、開発サーバーなしで済む可能性があります（本番・ステージング相手の場合など）。オーナーに聞く手順で、実画面と分けて聞くと了承が取りやすいはずです。推測です。

### 指摘3【重要】（観点：利用者のデメリット）

- 何が問題か：Goals でページ切替・削除後の再取得時の表示が変わります。現行は再取得のたびに全画面スピナーに置き換わりますが、移行後は前のリストが残り、スピナーは出ません。遅い回線では、クリックしても何も起きないように見えます。削除後は、削除済みの目標がリストに残り続ける時間もあります。草案はこれを利用者のデメリットとして書かず、テストも「前の画面が残る」を望ましい挙動として扱っています（L122）。Tasks は現行と同じなので影響しません。Announcements / Interviews は未確認です。
- 根拠：`Goals/hooks.ts` の `setLoading(true)` と `index.tsx` の `if (loading)` の順序。`Tasks/index.tsx` L12 のコメント。
- 直し方：Announcements / Interviews も含めて現行の再取得時の挙動を確かめ、変わる画面（少なくとも Goals）を草案の利用者デメリットに書きます。許容するか（TSK-214 の teacher 側と同じ扱いか）をオーナーに聞く問いに足します。許容できないなら、削除後の再取得だけでもリストを残してよいか、操作中の表示が要るかを決めます。あわせて、見た目の変化の判断者と基準（誰が・何を見て許容と決めるか）を L144 に書きます。

### 指摘4【軽微】（観点：対策の重複 / 読みやすさ）

- 何が問題か：L76「Question には `refetch` を付けない（失敗時の再試行は `onRetry` に渡す）」は読み手が混乱します。`onRetry` に渡すのは `refetch` そのものです。
- 直し方：「成功後に `refetch` を呼ぶ契機（削除・送信後の再取得）を作らない。`refetch` は `AsyncBoundary` の `onRetry` にだけ渡す」と書き直します。あわせて、Question の失敗→再試行→成功でも `QuestionBody` が新しく作られて `currentIndex` が 0 から始まるテストを1本足すと、`QuestionBody` 分離の意図が固定されます。

### 指摘5【軽微】（観点：事実か推測か）

- 何が問題か：検証済み表 L33 の「`page.tsx` で都度 `split` するので配列が毎回作り直される」は、サーバーコンポーネントの実態とずれています（前回 確かめた事実で指摘済み）。
- 直し方：記述を「サーバー側で作られ、props で渡る。従来のフックでも無限再取得は起きていなかった。`useApiQuery` は値で比較するので、今後も安全」に直します。テスト「同じ内容の配列を渡し直しても再取得しない」は残して構いませんが、回帰防止と明記します（実装前から通るため Red になりません）。
