## 確かめた事実（今回）

- `Admin::AnnouncementSerializer`：
  - 現行は `attributes ... :targets` とメソッド `targets` を併存させている。
  - 同じ作りは、すでに動いている実装そのもの。
  - AMS 0.10 は、serializer にメソッドがあればそちらを先に呼ぶ。そのため改名後も動く見込みが高い（推測。AMS の内部実装は読んでいない。request spec で確かめられる）。

## 指摘（重要な順）

### 指摘1【軽微】（観点：完了条件が測れるか）
- 何が問題か：最後の完了条件「別チケットか Go 側の Issue を起票してある」は、起票先がオーナーの回答待ち。草案としては、未定のまま書くより「既定の行き先」を決めておいたほうが測れる。
- 根拠：Go 側のリポジトリは、このリポジトリからは触れない（草案も認めている）。Notion のカンバンなら、このワークフローでエージェントが起票できる。
- 直し方の提案：既定を「Notion のカンバンに別チケットを起票する」とし、Go 側の Issue に移すかどうかはオーナーの判断に任せる。完了条件は「起票してあり、ID が PR 説明に書かれている」のまま変えない。これで、オーナーの回答が遅れても測れる。

### 指摘2【軽微】（観点：前提の検証）
- 何が問題か：完了条件に「本番が無いこと」の確認が入っていない。本番があれば案 C を見直すのに、確認が手順 5 だけで、完了条件では追えない。
- 根拠：第1周の指摘2は「直った」と判定したが、完了条件には反映されていない。
- 直し方の提案：着手前の条件を一行足す。「着手前：本番が無く、外から API を使う者がいないことをオーナーに確認済み（確認結果を PR 説明に書く）」。

### 指摘3【軽微】（観点：テスト計画）
- 何が問題か：設計の「どちらも今の実装では Red」は正しいが、「`announcement_targets` が配列で返る」の Red は、spec の 64 行目の必須項目の例とも重なる。Red の例が 3 つに分かれすぎ、「他校の行を含まない」の例は、キー名が無ければ `nil.pluck` で落ちる。理由が「Red」としては弱い。
- 根拠：spec の 82〜88 行目は、キー名を直すと、今のキーでは `nil` で落ちる。これは「期待の違い」ではなく、キー不在による例外。
- 直し方の提案：「他校の行を含まない」の例が、キー不在の例外ではなく、絞り込みの失敗でも落ちることを確かめる。具体的には、Green にしたあと、`high_school_id` の絞り込みを一時的に外して落ちることを確認する（実装時の確認として一行足す）。これは重い作業ではなく、既存の spec を残したまま確かめるための補強。

### 指摘4【軽微】（観点：規模・移行）
- 何が問題か：grep のコマンドは `.ts`・`.tsx` だけを見る。API の応答を使うのは、BFF の `route.ts` やテストの JSON 固定値でも起きうるが、それらは `.ts` に含まれる。範囲は足りている。ただ、`.json` や `.md` の API 仕様書にある `targets` は見ない。
- 根拠：`docs/` 配下に API の仕様や設計メモがあるかは、今回確かめていない。
- 直し方の提案：`docs/` と `rails/` 配下（`doc` や `swagger` の類）を、一度 `grep -rnw targets` する。該当が無ければ、PR 説明に「無かった」と書く。

## 3 つの判断への回答

1. 指摘3（一部採用）に同意できる。
   - 同意する点：Red の説明の訂正は正しい。ブロック形式を採らないのも妥当。使用例が無く、現行のメソッド形式が動いているので、増やす理由が無い。
   - 残る点：「Red の説明を変えた」のに、完了条件や手順 1 の書き方に、まだ古い趣旨が混ざっていないか。手順 1 は「Red を確認」とだけで、問題は無い。指摘3（上記）の補強だけを足せばよい。
2. 元の受け入れ条件の変更は妥当。
   - フロントを変えない PR で、フロントのテストが通ることは証拠にならない（CI は動かない）。
   - `git diff origin/main...HEAD -- frontend` が空であることと、grep の結果の限定は、どちらも機械的に確かめられる。測れる条件になっている。
   - ただし grep の期待値は「`features/teacher/AnnouncementEditor/` 配下だけ」。将来そこに管理者向けの使用が増えた場合は見分けられない。今回は問題にならない。
3. Go 設計書の確認の完了条件は、測れる。起票先が未回答でも、指摘1の既定を足せば草案として十分。
4. 草案の事実の誤りは、見つからなかった。
