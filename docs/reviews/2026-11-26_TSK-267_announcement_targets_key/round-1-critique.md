# 批判：TSK-267 お知らせの配信先配列のキー名を announcement_targets に統一する（第1周）

## 総評
範囲が小さく、前提の検証も丁寧で、主要な事実はコードと一致した。残る弱点は次の3つ。
- Go 設計書の扱いが「確認する」だけで、完了条件が測れない。
- 利用者のメリットが無いことを内部整理として認める根拠が薄い。
- テスト計画に細かい穴がある。

## 判定
**直せば進めてよい**。コード変更は妥当。ただし、完了条件の1項目と PR 説明の書き方を直す必要がある。

## 必須観点の判定

|  | メリット | デメリット |
|---|---|---|
| 利用者（生徒・教師・管理者） | なし（草案も認めている） | 目に見える変化はない。管理者の高校別一覧 API のキーが変わるが、フロントは読んでいない（確認済み）。 |
| 開発チーム | 同じ配信先の名前が、リクエスト・DB・モデル・教員側の応答と揃う。Go 設計書との突き合わせで引っかからなくなる。 | PR 1本分のレビュー。外から使われていないという前提（本番が無いこと）は未確認。キー名は揃うが、行と項目の違いは残る。 |

- 両方にメリットがあるか：**利用者に損がない内部整理**。
  - 利用者に損がないことは、コードで確かめられた（下記）。
  - 開発側のメリットは小さいが、変更も小さい。
  - 採否の理由が「名前が揃う」と「Go 設計書との突き合わせ」の2つだけなので、メリットは強くはない。
- やらないことのデメリット：
  - 利用者が失うもの：なし。
  - 開発チームが失うもの：キー名の揺れが残る。Go 側が `targets` のまま実装するリスクがある。ただし本番がまだ無いなら、後から直す費用も同程度。
- 草案に無いデメリット：
  - 本番が無いなら今が最安で、本番ができたあとはキーの変更が破壊的変更になる。これは「やる理由」として草案に書くとよい（草案に無い）。
  - 開発チームのデメリット（キー名は揃うが、行と項目の違いは残る）は、草案に書かれていない。

## 確かめた事実
- `Admin::AnnouncementSerializer` の利用箇所は1か所。`rails` を grep して確かめた。
  - `::Admin::AnnouncementSerializer` を使うのは `admin/high_schools/announcements_controller.rb` だけ。
  - 他の `AnnouncementSerializer` は、トップレベルの `AnnouncementSerializer`（student・teacher の controller）。
  - `admin/announcements_controller.rb` は `Admin::AnnouncementDetailSerializer` を使う。
  - 草案の記述どおり。
- Rails 内で `targets` 単体を使う箇所は、この serializer と request spec だけ。他の `targets_of_type` などは別物。
- フロントの `\btargets\b` は `features/teacher/AnnouncementEditor/` 配下のフォーム値だけ（`package-lock.json` を除く）。
  - `features/admin/SchoolDetail/types.ts` の `Announcement` に配信先の項目は無い。
  - `AnnouncementsTab.test.tsx` のモックにも `targets` は無い。
  - 草案のリポジトリ外の記述（Go 設計書）以外に、リポジトリ内で `targets` を参照するファイルは無い（`docs/` も、E2E も無い）。
- request spec の該当箇所（64・75〜88 行）は草案どおり。
- 要素 serializer の差は草案どおり。管理者は `user_name` なし、教員は `user_name` あり。
- controller は `includes(:publisher, :announcement_targets)`。`user_name` を管理者に足すと `includes(:user)` が要る、という案 D の理由は妥当。
- Notion の Go 設計書の所在は、今回は開いていない。草案どおり「未検証」として扱った。

## 残すべき強み
- 前提を「検証済み」と「未検証」に分け、確かめ方まで書いている。
- 案 B（教員側を改名）を退ける理由が具体的。リクエストの `announcement_targets` と揃わなくなる、という点が効いている。
- 案 D（要素の形まで揃える）を、`includes(:user)` と無駄な項目で切っている。
- 「`targets` が返らない」を確かめるテストを入れている。
- スコープを serializer 1つと spec 1つに絞っている。

## 指摘

### 指摘1【重要】（観点：完了条件が測れるか／スコープと依存の切り方）
- 何が問題か：
  - 5つ目の完了条件「Go 設計の該当記述について、所在と担当を持ち主に確認し、結果を PR かチケットに書く」は、測れない。
  - 確認する相手が書かれていない。返事が来ない場合に、PR を止めるのか通すのかも決まっていない。
  - 他の4項目は rspec・git diff・CI で測れるのに、この1項目だけ人待ちになっている。
- 根拠：草案の完了条件 75 行目と、「未検証」の第1項。
- 直し方の提案：
  - 完了条件を2つに分ける。
    - (a) PR 説明に、キー名の変更と影響先（Go 設計書の管理者お知らせ管理機能・高校学年参照機能）を書く。これは本チケットの完了条件にする。
    - (b) 所在の確認は、別チケット（または Go 側の Issue）を起票するところまでを完了とし、起票先を ID で書く。返事は待たない。
  - 「持ち主」が誰かは、オーナーに聞く（下記の問い）。

### 指摘2【重要】（観点：事実か推測か／失敗の想定）
- 何が問題か：
  - 「本番環境がまだ無い」が未検証のまま、改名を安全とする前提に使われている。
  - 利用者のデメリットは「なし」だが、その根拠は「フロントが読んでいない」だけ。外部の API 利用者（スクリプト・モバイルなど）が本当にいないかは、コードからは言えない。
  - 草案の他の記述は検証済みなのに、この1点だけ聞くことにしている。聞けば1分で済むので、着手前に決める方がよい。
- 根拠：草案「未検証」の第2項。
- 直し方の提案：着手前にオーナーへ確認し、結果を草案に「検証済み」として書く。確認できるまでは、案 C（2つのキーを併存）の不採用理由が成り立つ条件だと明記する。

### 指摘3【重要】（観点：テスト計画）
- 何が問題か：
  - 「`announcement_targets` が返る」は Red になる（今は `targets` なので失敗する）。「`targets` は返らない」は Red にならない（今は返らない、と読めるが、実際は今 `targets` が返っているので、Red になる。問題は逆で、改名後の `targets` 不在は、serializer に `targets` を残したままでも通ってしまう点）。
  - ここで実際に守りたいのは、「二重に返さない」こと。`expect(data.keys).not_to include('targets')` で足りるので、そのまま採用してよい。ただし草案では、この確認が「Red」の項と混ざっている。
  - もう1点、`attributes :announcement_targets` とメソッド `announcement_targets` の併存が動くか、が未検証として残っている。メソッド名が、`object.announcement_targets`（関連）と同名になる。
    - `object.announcement_targets` は `object` 側を明示しているので衝突はしない。
    - ただし、メソッドの中で `announcement_targets` と書くと、serializer 自身を再帰して呼ぶ。実装時の事故になりやすい。
- 根拠：`rails/app/serializers/admin/announcement_serializer.rb` の 10〜13 行目（`object.announcement_targets.select`）。
- 直し方の提案：
  - 「`targets` は返らない」を、Red（新キー）と回帰防止（旧キー不在）に分けて書く。
  - 実装メモに「メソッド内では必ず `object.announcement_targets` と書く」と入れる。`scoped_targets` の変数名はそのままで衝突しない。
  - もっと確実な形は、メソッド名を `announcement_targets` にせず、`attribute :announcement_targets do ... end`（ブロック形式）で書くこと。AMS のバージョンで使えるかは、実装時に確かめる。

### 指摘4【重要】（観点：代替案の比較／共通化の方針）
- 何が問題か：
  - 揃えない判断（行と項目の違い）は妥当だが、改名で「同じキー名なのに中身が違う」状態を、かえって作ってしまう。
  - コメント1〜2行だけでは、Go 側・フロントの新しい読み手に伝わらない。
  - 草案は「これまでは名前が違うことで違いに気づけた」という逆のデメリットを書いていない。
  - 教員側は全行、管理者側は高校で絞った行、という違いは、PR 説明・Go 設計書の側にも書く必要がある。
- 根拠：草案 14〜19 行目（違いの表）と設計 3。
- 直し方の提案：
  - 違いの表を PR 説明にそのまま載せる（指摘1の (a) に含める）。
  - 草案に「改名で違いが見えにくくなる」というデメリットを書き、コメントと PR 説明で補うと明記する。
  - 管理者側の絞り込みを `scoped` のような名前の処理に切り出す案は、規模が増えるので採用しなくてよい。理由を比較表に1行足す。

### 指摘5【軽微】（観点：完了条件が測れるか）
- 何が問題か：
  - 元の受け入れ条件にあった「serializer spec」と「フロントのテスト・型チェック」の扱いが、草案の本文に理由つきで書かれていない。
  - 草案では、serializer spec は「無い」と確認しているだけで、新しく足さない理由が無い。
  - フロントのテスト・型チェックは「CI で確認する」とあるが、`git diff` で `frontend/` が空なら CI も走らない可能性がある（推測。`.github/workflows` の `paths` 設定を確認すること。TSK-228 では `paths` が `rails/**` だけで CI が動かなかった実例がある）。
- 根拠：草案 66 行目・74 行目、答え合わせ表の TSK-228 の行。
- 直し方の提案：
  - serializer spec を足さない理由を書く。高校で絞る振る舞いは、request spec で確かめられているため。
  - 完了条件 4 の「フロントの CI も通る」は、`frontend-ci.yml` の `paths` を確認して、動かないなら項目ごと外す。外す場合は、代わりに「grep で `targets` の管理者側参照が 0 件」を完了条件にする。
  - 元の受け入れ条件との差分は、Notion を更新するときに本文へ明記する（オーナーが元の条件を読み返せるように）。

### 指摘6【軽微】（観点：前提の検証）
- 何が問題か：
  - 検証済みの前提の中で、「フロントの grep」は再実行で確かめた。ただ、同じ grep が漏れる読み方がある。
  - 例：`frontend/app/api/admin/schools/[schoolId]/announcements/route.ts` のテストや、フロントの MSW・フィクスチャで、配列の `.targets` を別の形（`["targets"]`、分割代入のエイリアス）で読む場合。
  - 今回は `\btargets\b` の grep で全文を見たので漏れは無い（確認済み）。実装時の再 grep も、同じコマンドを草案に書いておくと再現できる。
- 直し方の提案：再 grep のコマンドを、完了条件の中に1行で書く（`grep -rnw targets frontend --exclude-dir=node_modules --exclude-dir=.next` の結果が、`features/teacher/AnnouncementEditor/` 以外で 0 件）。
